## Goal

A signed-in customer adds products to a cart, checks out, pays on a fake provider page and gets a confirmation email; stock never oversells. Done means:

- Cart, checkout, order history and order detail work in all three stacks; checkout re-prices on the server, snapshots prices on order lines and reserves stock atomically.
- `StockRaceIT`: N threads racing for limited stock never oversell, and `reserved` always equals the sum of active reservations.
- A repeated `Idempotency-Key` creates at most one order; the same key with another body gets 422.
- Reservations expire and are released in `FOR UPDATE SKIP LOCKED` batches, safe with several replicas.
- The payment webhook rejects forged, stale, tampered and replayed requests; a payment after expiry is re-reserved or refunded.
- A paid order sends one confirmation email to Mailpit through the Spring Modulith event publication registry; a Mailpit outage delays it, never loses it.
- Customers can register themselves in Keycloak, with email verification through Mailpit.
- `make ci` and `make cluster-down cluster-up deploy cluster-e2e` pass, and a second `cluster-e2e` on the same database passes too. ADR 0008 (and 0009 if split), the threat model's checkout and webhook sections, README and test docs are updated.

**Problem Details.** New `type` values in `Problems`, all with `errors: [{field, message}]`: `tag:shop.dev,2026:cart-changed` (409, cart version differs or the cart is empty), `price-changed` (409, recomputed total differs from `expectedTotalMinor`), `out-of-stock` (409, one error per short line, `field` = product slug), `cart-full` (409), `too-many-pending-orders` (409), `order-state` (409), `idempotency-in-progress` (409, `Retry-After: 1`), `idempotency-key-reused` (422), `webhook-signature` (401, one fixed detail whatever failed). Messages never echo input. Lock timeouts keep 3b's 503.

**Checkout transaction [4a]** (`CheckoutService.checkout(CurrentUser, key, input)`, one `READ COMMITTED` transaction; lock order is fixed to rule out deadlocks: idempotency row, cart row, product rows by id, stock rows by product id):

1. Validate the key header (UUID, else 400 on `Idempotency-Key`). `requestHash` = SHA-256 hex of `POST /api/checkout\n{cartVersion}\n{expectedTotalMinor}` (parsed values, not raw bytes).
2. `INSERT INTO idempotency_key (customer_subject, key, request_hash, created_at, expires_at) VALUES (...) ON CONFLICT (customer_subject, key) DO UPDATE SET request_hash = EXCLUDED.request_hash, created_at = EXCLUDED.created_at, expires_at = EXCLUDED.expires_at, response_status = NULL, response_body = NULL, order_id = NULL WHERE idempotency_key.expires_at <= :now RETURNING ...`. No row returned means a live key exists: read it; another hash gives 422; otherwise replay the stored 201 and body with header `Idempotency-Replayed: true`. A duplicate arriving while the first is still running waits on the uncommitted unique row (that is the in-progress handling); if the wait passes the 3 s `lock_timeout`, answer 409 `idempotency-in-progress` (catch `PessimisticLockingFailureException` around this statement only). The key row is written in the checkout transaction, so a failed or crashed checkout leaves no key and a retry runs again. Only 201s are stored; 409s are recomputed on retry because stock and prices move.
3. `CartCheckout.lockForCheckout(sub)` (`FOR UPDATE` on the cart row). Missing or empty cart, or `version != cartVersion`: 409 `cart-changed`.
4. Count the customer's `PENDING_PAYMENT` orders with `expires_at > now`; 3 or more: 409. (The cart row lock serialises one customer's checkouts.)
5. `ProductPricing.lockForCheckout(ids)` (`FOR SHARE`): any inactive product: 409 `out-of-stock` for it. Recompute the total from current prices; differs from `expectedTotalMinor`: 409 `price-changed`. An admin price change waits on the share lock, so the snapshot equals the price at commit (closes R29).
6. `StockReservations.reserve(orderId, lines, expiresAt)`: per line by product id, `UPDATE stock SET reserved = reserved + :q WHERE product_id = :id AND on_hand - reserved >= :q`. A row count of 0 makes the method read availability for every line and throw 409 `out-of-stock` listing each short line; the transaction rolls back. On success insert one `reservation` row per line (`ACTIVE`). `version` is not bumped (ADR 0007 rule).
7. Insert `orders` and `order_line` (slug, name, unit price, currency, quantity snapshots), clear the cart lines and bump the cart version, then set the key row's `response_status`, `response_body` (jsonb of the `Order`), `order_id`.

**Reservations and the expiry job [4a].** `expires_at = now + shop.checkout.reservation-ttl` (15m). All times come from the injected `Clock` and are passed to SQL as parameters (never `now()`), so ITs move time with `MutableClock`. `ReservationExpiryJob` (`@Scheduled(fixedDelayString = "${shop.checkout.expiry-interval:30s}")`, `@EnableScheduling` in `order`) loops: in one transaction, `SELECT id FROM orders WHERE status = 'PENDING_PAYMENT' AND expires_at <= :now ORDER BY expires_at LIMIT :batch FOR UPDATE SKIP LOCKED` (batch 100), then for each order `StockReservations.release(orderId)` (`reserved = reserved - q` per line by product id, reservation rows `RELEASED`) and status `EXPIRED`; commit; repeat while a full batch came back. Replicas each take disjoint batches; a row being paid or cancelled is locked and skipped. `cancel`, `payment start` and the webhook lock the order `FOR UPDATE` and treat an expired `PENDING_PAYMENT` order as expired on the spot (release inline). `MaintenanceJob` (hourly) deletes expired idempotency keys in batches of 1 000 (`ctid IN (SELECT ... LIMIT ... FOR UPDATE SKIP LOCKED)`). Jobs log counts only. ITs disable scheduling (`shop.jobs.enabled=false`) and call `runOnce()`.

**Order state machine** (`OrderService`, every transition under the order row lock, in a table-driven method, unit-tested exhaustively):

| From | Trigger | To | Stock |
|---|---|---|---|
| (none) | checkout [4a] | `PENDING_PAYMENT` | reserve |
| `PENDING_PAYMENT` | customer cancel [4a] | `CANCELLED` | release |
| `PENDING_PAYMENT` | expiry job or lazy expiry [4a] | `EXPIRED` | release |
| `PENDING_PAYMENT` (even past `expires_at`, still reserved) | `payment.succeeded`, amount and currency match [4b] | `PAID` | consume: `on_hand -= q, reserved -= q, version + 1` |
| `PENDING_PAYMENT` | `payment.failed` [4b] | `PENDING_PAYMENT` (payment `FAILED`; customer may pay again) | none |
| `EXPIRED` | `payment.succeeded` [4b] | `PAID` with `latePayment = true` if every line can be taken, else `REFUND_PENDING` | `takeLate`: lock the rows `FOR UPDATE` by product id, check `on_hand - reserved >= q` for all, then `on_hand -= q, version + 1` for all, or nothing |
| `CANCELLED` | `payment.succeeded` [4b] | `REFUND_PENDING` | none |
| `PAID` | `payment.succeeded` for another payment [4b] | `PAID`; that payment refunded | none |
| any | amount or currency mismatch [4b] | unchanged; payment refunded, logged as an anomaly | none |
| `REFUND_PENDING` | refund done [4b] | `REFUNDED` | none |

Consuming changes `on_hand`, so it bumps `stock.version` (ADR 0007): an admin's open stock form then gets 409 instead of silently undoing a sale. Every transition into `PAID` publishes `OrderPaid`; into `REFUND_PENDING` (or a refund of an extra payment) publishes `RefundRequested`. Orders store `email` at checkout from the ID token: the `email` claim only when `email_verified` is true, else null (no mail).

**Payment [4b].** `PaymentController.start`: `OrderPayments.payable(sub, orderId)` (locks the order, 404 for others, 409 unless awaiting payment and not expired) returns amount; reuse an open `CREATED` payment, else call `PaymentProvider.createPayment(paymentId, amount, currency)` outside any transaction, then insert `payment(id uuid, order_id, provider, provider_payment_id UNIQUE, status, amount_minor, currency, created_at, updated_at)` with a partial unique index on `(order_id) WHERE status = 'CREATED'` (a double click returns the first). `RefundProcessor` (`@ApplicationModuleListener` on `RefundRequested`) calls `PaymentProvider.refund(providerPaymentId, amount, idempotencyKey = paymentId)` and then `OrderPayments.refunded(orderId, paymentId)`; the fake refunds synchronously and idempotently.

**Webhook [4b].** Format (Stripe-like): header `Shop-Signature: t=<unix seconds>,v1=<64 lowercase hex>`, `v1 = HMAC-SHA256(secret, t + "." + rawBody)`. Body `{"id": "evt_<uuid>", "type": "payment.succeeded" | "payment.failed", "created": <unix>, "data": {"providerPaymentId", "amountMinor", "currency"}}`. `WebhookController` reads the raw body itself (at most 64 KiB, else 413; `Content-Type` must be `application/json`, else 415), then `WebhookVerifier`: exactly one `t` and one `v1` (else 401), `|now - t| <= 300 s` (else 401), compare with `MessageDigest.isEqual` on the decoded bytes (else 401), and only then parse JSON (400 if malformed or an unknown `type`). One transaction: `INSERT INTO payment_webhook_event (event_id, type, received_at) ON CONFLICT DO NOTHING`; a duplicate id answers 200 with no effect. Then lock the payment by `provider_payment_id` (unknown: 200, logged, no effect, so the provider stops retrying), update its status and call `OrderPayments`. The fixed 401 detail never says which check failed; logs record the reason without the header value. Secret: `shop.payment.webhook-secret` (`SHOP_PAYMENT_WEBHOOK_SECRET`), validated at startup (at least 32 characters), redacted in `toString`; the fake signs with the same property.

**Webhook chain [4b].** `WebhookSecurityConfiguration` in `auth`: `@Order(1)` `SecurityFilterChain` with `securityMatcher(PathPatternRequestMatcher` for `POST /api/payments/webhook`)`, `permitAll` (HMAC is the authentication), `SessionCreationPolicy.STATELESS`, `NullSecurityContextRepository`, `NullRequestCache`, `csrf.disable()` (D27; the only CSRF exemption in the app), no `oauth2Login`, `RevalidationFilter` or timeout filters, same Problem Details entry point. The main chain keeps `denyAll` for everything else, so `GET` or an encoded variant of the path is refused there. Tests: no `Set-Cookie` on any webhook response, a session cookie sent along is ignored, CSRF still required on every other unsafe route (`CsrfIT` adds the new routes).

**Fake provider [4b].** Table `fake_psp_payment(provider_payment_id text PK ('pay_' + uuid), token text UNIQUE, merchant_reference uuid, amount_minor, currency, status PENDING|SUCCEEDED|DECLINED|REFUNDED, return_url, created_at)`. `complete` moves `PENDING` once (409 otherwise) and publishes `FakePaymentCompleted(providerPaymentId)` in the same transaction. `WebhookSender` (`@ApplicationModuleListener`) builds the event with a new `evt_` id, signs it and posts it with `RestClient` (2 s connect, 5 s read) to `shop.payment.fake.webhook-url` (`SHOP_PAYMENT_FAKE_WEBHOOK_URL`, default `http://localhost:8080/api/payments/webhook`, the pod itself). A non-2xx or I/O error throws, so the publication stays incomplete and is retried. The fake never has state the `payment` module reads directly.

**Outbox [4b].** `spring-modulith-starter-jdbc`; schema by Flyway (`V10`), `spring.modulith.events.jdbc.schema-initialization.enabled: false`, `completion-mode: delete`, `republish-outstanding-events-on-restart: false` (multi-replica), `staleness.published: 2m`, `staleness.processing: 5m`, `staleness.resubmitted: 5m`. `EventRetryJob` (in `order`, every 60 s): in a transaction holding `pg_try_advisory_xact_lock(<fixed key>)` (skip when not acquired, so one replica resubmits), `FailedEventPublications.resubmit(ResubmissionOptions.defaults().withBatchSize(50).withMinAge(1m).withFilter(p -> p.getCompletionAttempts() < 10))`; verify the 2.1.2 method names in the sources and record deviations. Publications at 10 attempts stay `FAILED` and are counted in a log line (manual resubmission is documented). Listener ids are class and method names: renaming a listener orphans its open publications (README note). Events are records with ids only (`OrderPaid(UUID orderId)`, `RefundRequested(UUID orderId, UUID paymentId)`, `FakePaymentCompleted(String providerPaymentId)`), so no personal data sits in `serialized_event`. `@EnableAsync` in one configuration class.

**Email [4b].** `OrderConfirmationMailer` loads the order through `OrderPayments.summary(orderId)`; no email address: complete without sending. Otherwise insert `order_email(order_id, kind) ON CONFLICT DO NOTHING` (already sent: complete), then send plain text from `shop.mail.from` (`orders@shop.test`), subject `Your order <first 8 of id> is confirmed`, body lines with names, quantities, prices, total and the order URL from `SHOP_PUBLIC_ORIGIN`. Names are product data, not user input, and the body is text, not HTML. Send failures throw so the registry retries; a crash between send and commit can send twice (at-least-once, documented). `spring.mail.host`/`port` from `SPRING_MAIL_HOST`/`SPRING_MAIL_PORT` (`mailpit`/`1025`), 2 s connect, 5 s read and write timeouts; `management.health.mail.enabled: false`, so readiness never depends on Mailpit.

## Known traps

- `orders`, not `order` (reserved word). `gen_random_uuid()` is built in; generate ids in Java anyway, for tests.
- `lock_timeout` (3 s) applies to the unique-index wait in step 2; catch it only there for the in-progress 409; elsewhere it stays 3b's 503.
- Spring ignores `isolation` on a joined transaction; checkout is the outermost one. No self-invocation through proxies; jobs call a separate bean's `@Transactional` method per batch.
- `@ApplicationModuleListener` is async after commit in a new transaction; ITs wait with Awaitility. Without `@EnableAsync` it runs synchronously and tests pass for the wrong reason: assert the listener thread differs.
- The webhook controller must read the raw bytes before any JSON binding; `@RequestBody` of a record would verify a re-serialised body. Never log the signature header.
- Jackson 3 (`tools.jackson.*`) for stored responses and events; the 3b coercion rules apply to new inputs (`quantity: 1.5` gives 400).
- Testcontainers 2 names; `GenericContainer` for Mailpit. Spring Boot 4 starter names; check `spring-boot-starter-mail` resolves under 4.1.2.
- CodeQL flags `csrf.disable()` (D27); the 3a test-only case was removed for the same alert.
- The kind node needs `make cluster-down cluster-up` for port 8026; `cluster-up` must say so.

## Top risks

1. Oversell or stuck `reserved` from a missed path: one conditional update, CHECK constraints, the race IT and an invariant check (`reserved = sum(active reservations)`) asserted after every concurrency IT.
2. Deadlocks between checkout, admin writes, expiry and webhooks: the fixed lock order and the concurrent ITs.
3. Webhook bypass through parsing differences or the wrong chain: raw-byte HMAC, exact path matcher, `WebhookIT` negatives.
4. Lost or duplicated side effects: registry retries with an advisory-locked job; email dedupe table; refunds idempotent by payment id.
5. E2E flakiness from async payment: poll the order and Mailpit with deadlines, never sleep blindly.

### 4b: API (`services/api`) [API-PAYMENT]

- **F25 (G8, G9, G10, S1, S2, S15; merged) [4b].** Payment states, monotonic, checked under the payment row lock before any order transition: `CREATED → SUCCEEDED | FAILED`, `FAILED → SUCCEEDED`, `SUCCEEDED → REFUND_PENDING → REFUNDED`. An event for a payment already in its target or a later state is a no-op, 200, logged at info (so a second `payment.succeeded` for the same payment, or `payment.failed` after success, changes nothing). V9 adds `payment.received_amount_minor`, `orders.payment_status text NULL` (CHECK on the payment statuses; the latest payment's status, written only through `OrderPayments` under the order lock) and `orders.paid_payment_id uuid`. Order rules replacing the body's 4b rows: (a) `PENDING_PAYMENT`, `expires_at > now`, success, amount and currency match: consume, `PAID`, `paid_payment_id` set. (b) `PENDING_PAYMENT` past `expires_at` (job not yet run): this is a late payment (S15 over G8, so the outcome never depends on whether the job has run): if within the late window and every product active (F28), consume the held reservation (`PAID`, `latePayment = true`); otherwise release it and go to `REFUND_PENDING`. Each stock row is touched once. (c) `EXPIRED` + success: `takeLate` within the window with all products active, else `REFUND_PENDING`. (d) `CANCELLED` + success: `REFUND_PENDING`. (e) `PAID`, `REFUND_PENDING` or `REFUNDED` + success of a payment other than `paid_payment_id`: order unchanged, that payment refunded. (f) Amount or currency mismatch in any order state: order unchanged (a pending order keeps its reservation and expires normally), payment refunded for `received_amount_minor`. (g) Any order state + `payment.failed`: order unchanged. (h) `OrderPayments.refunded(orderId, paymentId)` always moves that payment to `REFUNDED` and moves the order `REFUND_PENDING → REFUNDED` only when no payment of the order is still `SUCCEEDED` or `REFUND_PENDING`; it is idempotent. Full interface: `payable(sub, orderId)`, `paymentSucceeded(orderId, paymentId, amount)`, `paymentFailed(orderId, paymentId)`, `refunded(orderId, paymentId)`. `OrderStateMachineTest` and `PaymentStateMachineTest` enumerate every (state, trigger) pair, no-ops included. `WebhookIT`: the same payment's success twice under two event ids (one effect, no refund, stock consumed once); `payment.failed` after success (no change). `LatePaymentIT`: mismatch on a pending order leaves it pending, the job later expires it.
- **F26 (S4) [4b].** Webhook: read `payment.order_id` without a lock, lock the order (`FOR UPDATE`), lock the payment, re-check the payment still belongs to that order. `payable()` never locks a payment. ADR 0009 restates F6's order. `PaymentRaceIT` also races the webhook against payment start and against a refund on the same order.
- **F27 (G27, S13; merged) [4b].** Payment start inserts `payment` (`CREATED`, `provider_payment_id NULL`) under the partial unique index and commits; on a unique violation it returns the winner's session. Then it calls `createPayment` outside any transaction and sets `provider_payment_id`. Webhook `data` gains `merchantReference` (= `payment.id`); the webhook finds the payment by `providerPaymentId`, else by `merchantReference`. A payment found by neither: roll back the dedupe insert and answer 404 problem+json so the provider retries, and record `payment_webhook_unmatched(event_id, provider_payment_id, received_at)` in its own transaction. ADR 0009 notes a real provider must retry on 404.
- **F28 (S8) [4b].** `fake_psp_payment.expires_at = order.expires_at + shop.payment.fake.session-grace` (5 min); `complete` after it gives 409 and the page shows `This payment has expired` (fixed UI text). The late rule (F25 b, c) takes stock only when the success arrives within `shop.checkout.late-payment-window` (30 min) after `expires_at` and every product is active (`ProductPricing`, `FOR SHARE`, before stock per F6); otherwise refund. `LatePaymentIT`: outside the window refunds; a deactivated product refunds.
- **F29 (S10) [4b].** `shop.payment.provider` has no default in `application.yaml`; startup fails when unset (`@Validated`, `@NotBlank`, allowed value `fake`). It is `fake` only in compose, the e2e compose, `overlays/local` and the IT config. With `fake`, one WARN at startup: `fake payment provider: no money is taken`. A test asserts `/api/fake-psp/**` is 404 when the fake is off. README and ADR 0009 say a cloud overlay must set a real provider and that `fakepsp` ships in the binary.
- **F30 (S1, S14, G29; merged) [4b].** `fake_psp_payment.event_id text NOT NULL UNIQUE` is set once by `complete`; `WebhookSender` always sends it. `FakePspIT`: the first send times out after the API commits; the retry carries the same id. `WebhookVerifier`: exactly one `Shop-Signature` header; elements split on `,`; exactly one `t` (1 to 10 ASCII digits, parsed after that check) and one `v1` (exactly 64 `[0-9a-f]`); unknown keys give 401; HMAC input is the bytes `t` + `.` + raw body, never a decoded string; the secret is UTF-8 bytes; `Content-Type` parsed with `MediaType.parseMediaType`, `application/json` with any charset, missing or unparsable gives 415; the body is read through a counting stream that stops at 64 KiB + 1 whatever `Content-Length` says, and a declared length over 64 KiB is refused before reading. The signer and verifier share one `WebhookSigner`. The body's `created` field is informational; the header `t` is authoritative.
- **F31 (S12, S D27; merged) [4b].** `WebhookIT` adds: Valkey unreachable (dedicated context class, one extra context) and a session cookie sent: 200 and the order is paid; the webhook chain's filter list holds no `RevalidationFilter`, `AbsoluteSessionTimeoutFilter`, `CsrfFilter` or `OAuth2LoginAuthenticationFilter`; trailing slash, `//`, case variants and other methods on the path fall to the main chain's `denyAll`.
- **F32 (G2) [4b].** `EventRetryJob` resubmits with `withBatchSize(200)` (default `maxInFlight`) and a backoff filter on `getLastPublicationDate()`: 1, 2, 4, 8 minutes, doubling, capped at 30. Before resubmitting it moves `FAILED` rows with `completion_attempts >= shop.events.max-attempts` (48, about a day) into `event_publication_dead_letter` (same columns plus `moved_at`, in V10) and deletes them from `event_publication`, so dead rows never fill the `LIMIT`; each move is logged with counts. Manual resubmission is an `INSERT ... SELECT` back (README). The Goal line becomes: "a Mailpit outage of up to about a day delays it; beyond that it is parked in a dead-letter table and logged". `OutboxIT` adds: no resubmit within the backoff; the dead-letter move; a newer publication still resubmitted while 200 or more rows were dead-lettered.
