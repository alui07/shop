# Fix: API test stability (branch `fix-test-stability`)

Owner decided 2026-11-25: fix the two open problems from the PR #12 investigation in a small branch before `fix-add-to-cart-increments`.

## Problems

1. **`ReservationExpiryIT` flake.** `ReservationExpiryIT.twoJobsRunningTogetherReleaseEveryOrderExactlyOnce` failed in 3 of 4 local `api-test` runs at `--cpus=2` (47, 59, 50 of 250 orders; logs `build/reports/slice-5c-pr12/repro-cpus2-run*.log`). Cause: `spring-modulith-moments` 2.1.2, pulled in transitively by the Modulith starter, auto-configures `MomentsAutoConfiguration`, which carries `@EnableScheduling`. So every `@Scheduled` job (`ReservationExpiryJob`, `MaintenanceJob`, `PaymentMaintenanceJob`, `EventRetryJob`) runs in every test context even though `@IntegrationTest` sets `shop.jobs.enabled=false`, the switch on `web/SchedulingConfiguration`. The context's scheduler expired orders mid-race. The project does not use moments (`grep -rn moments services/api/src` finds nothing).
2. **`CatalogCacheOutageIT` CI hang.** In CI run 45714530877 the `ci` job hung in that IT from 22:39:34 until the 45-minute job timeout, with no stack. The cause is unknown and does not reproduce locally. A hang should fail fast and leave a thread dump.
3. **Fork exit allowance (related).** The Failsafe fork JVM exceeds the default 30 s `forkedProcessExitTimeoutInSeconds` while about 20 cached Spring contexts close at about 2.5 s each. Failsafe then kills the fork. JaCoCo writes `jacoco.exec` from a JVM shutdown hook, so a killed fork can lose coverage data and make the coverage gate flaky.

## Design

### D1. Remove moments
Exclude `org.springframework.modulith:spring-modulith-moments` from the Modulith starter dependencies in `services/api/pom.xml`: every starter that brings it in, whether `spring-modulith-starter-jdbc` and/or `spring-modulith-starter-test`, through `spring-modulith-starter-core`. Excluding the jar beats a property: it is unambiguous, it removes an unused dependency that publishes hourly events, and it cannot be undone by a profile. `SchedulingConfiguration` stays the only place that enables scheduling, as its Javadoc already claims.

Regression test: a new IT under `src/test/java/dev/shop/api/web/` (for example `SchedulingOffInTestsIT`) annotated `@IntegrationTest`, so it reuses the shared cached context and costs nothing extra. It asserts the context has no `ScheduledAnnotationBeanPostProcessor` bean. It fails on the current `main` and passes after D1. The implementer must show both. `SchedulingConfigurationTest` already proves production turns scheduling on.

### D2. Default timeout with a thread dump
Create `services/api/src/test/resources/junit-platform.properties` with:
```
junit.jupiter.execution.timeout.default = 2 m
junit.jupiter.execution.timeout.threaddump.enabled = true
```
Keep the default thread mode (`SAME_THREAD`). `SEPARATE_THREAD` would run the method off the thread where Spring's test listeners set ThreadLocals (security context, transactions). In `SAME_THREAD` mode JUnit 6.0.3 (the version in use; the property exists in its `Constants`) prints a dump of all threads to stdout when the timeout fires, then interrupts the test thread. The dump appears even if the thread is blocked uninterruptibly. Surefire and Failsafe do not redirect test output, so the dump lands in the CI log. Two minutes is about 7 times the slowest test (16.1 s, `CatalogCacheOutageIT`) and well inside the 45-minute job timeout.

Verify on purpose: a throwaway test that sleeps past a short `@Timeout` produces the dump and fails. Delete it afterwards and paste the output into the report.

### D3. Fork exit allowance
Set `<forkedProcessExitTimeoutInSeconds>180</forkedProcessExitTimeoutInSeconds>` on the Failsafe plugin. Consider Surefire too: the unit tests start no contexts, so it is probably not needed there; say so. Confirm in the log that the "exceeded exit timeout" style warning is gone.

### D4. CI artifacts
In `.github/workflows/ci.yaml`, `ci` job: on `failure() || cancelled()`, upload `services/api/target/failsafe-reports` and `services/api/target/surefire-reports`. Use the same pinned `actions/upload-artifact` SHA already in the file. A timed-out job counts as cancelled, so the reports of a future hang survive.

From the hang design (2026-11-25). The owner put the `CatalogCacheOutageIT` hang in scope; A10 overrides "Out of scope". Source evidence: spring-data-redis 4.1.2 `RedisMessageListenerContainer` (RMLC) saved at `build/reports/fix-test-stability/design/src/RMLC.java`. Its line numbers match `hang-jstack.txt` frame for frame.

- **A10 (scope).** Fix the hang's root cause: closing a context, or a pod's graceful shutdown, must finish promptly whatever state Valkey is in. Before the first success, `CatalogChangedSubscriber` stays the only owner of retry and backoff.
- **A11 (confirmed mechanism).**
  1. Lettuce gets the async `Subscriber` (RMLC 835; `ConnectionUtils.isAsync` is an `instanceof LettuceConnectionFactory` check). `Subscriber.initialize` runs inside `doInLock`, a `ReentrantLock` (1266, 1486).
  2. If `getConnection()` throws on the first attempt, the container fails fast (`InitialBackoffExecution`, 1290-1293), `start()` throws, and our backoff runs. If `getConnection()` succeeds but `subscribe` throws, `handleSubscriptionException` runs whatever the backoff type (1286-1288). For a `RedisConnectionFailureException` while running it calls `potentiallyRecover`. With the default `FixedBackOff(5000, UNLIMITED)` (145) and no `ScheduledExecutorService` (the subscription executor defaults to the `SimpleAsyncTaskExecutor`, 305-310), that method does `Thread.sleep(5000)` and then `lazyListen` → `doSubscribe` → `initialize` again (956-960). It recurses on our thread with the lock still held and never returns while Valkey is down, so our loop never regains control.
  3. Lettuce's `getConnection()` does no I/O once the shared native connection exists: `LettuceConnectionFactory` 1056, and `SharedConnection` validates only with `validateConnection`, which defaults to false. `subscribe` opens a new pub/sub connection, and that connection is refused. `run2.log` (pid 174) shows exactly this. The container logs "Restarting subscription task after 5000 ms" at 02:58:59.4, 59:04, 59:09 and 59:14. Our "Valkey is unreachable" WARN never appears. Four recoveries give the five nested levels in the jstack.
  4. The deadlock. `close()` → `stop()` sets `started=false` (491). `doUnsubscribe` treats `prepareListening` as active (514, 1158), waits 2 s (518), sets the state to `prepareUnsubscribe` (520), and then blocks in `unsubscribeAll` on `lock.lock()` (522); the sleeping recovery holds that lock. The next recovery's `doSubscribe` sees `prepareUnsubscribe` and calls `containerUnsubscribeFuture.join()` (427-429). Only `Subscriber.doUnsubscribe` inside `unsubscribeAll` completes that future (1353ff), and it needs the lock. The result is a lock-versus-future deadlock that stays even after Valkey returns. The recovery runnable never re-checks `isRunning()`.
  5. Refinement of the hypothesis. The hang needs a narrow window, not just any in-progress subscription: the shared connection exists (created moments earlier with Valkey up) and the pub/sub connect then fails. If Valkey is down before the first connection, the container fails fast. That is why `CatalogCacheValkeyDownAtStartIT` passes.
  6. Production impact. The same thing happens in a pod when Valkey refuses or times out the pub/sub connect after the shared connection exists, for example a rollout during a Valkey restart. The recursion grows one level every 5 s while holding the lock. On SIGTERM, `DefaultLifecycleProcessor.doStop` calls the container's synchronous `stop(Runnable)` on the closing thread, so `timeout-per-shutdown-phase` (20 s) does not bound it, and the kubelet sends SIGKILL at the end of the grace period. `destroy()`/`shutdownNow` runs after the lifecycle stop, so it cannot help.
  7. After the first success, with Lettuce, `handleSubscriptionException` can only be reached from `initialize` (1287, 1294; 1530 and 1547 belong to the Jedis `BlockingSubscriber`). Re-subscription after a dropped connection is done by Lettuce itself (`ConnectionWatchdog` reconnects, then it re-subscribes), not by the container's BackOff. Changing the BackOff therefore does not affect ADR 0012's promise to re-subscribe after a drop. ADR 0012 currently credits the container for it, which is inaccurate.
  8. Upstream. spring-data-redis #2822 (Jan 2024, closed) reports the same recursion (`handleSubscriptionException` → `potentiallyRecover` → `lazyListen`) keeping test JVMs alive after Redis dies. The maintainer said this is by design since #2782 (BackOff unlimited by default) and recommended configuring a BackOff with limited attempts. I found no upstream report of the lock-versus-`unsubscribeFuture` deadlock.
- **A12 (fix, configuration first).**
  1. `CatalogCacheConfiguration`: `container.setRecoveryBackoff(new FixedBackOff(0, 0))`, with a one-line comment saying `CatalogChangedSubscriber` owns retries and Lettuce re-subscribes after a drop. Verified with javap against spring-core 7.0.10: `FixedBackOffExecution.nextBackOff` returns `STOP` on the first call. `potentiallyRecover` then returns false without sleeping (950-951), the attempt fails with `IllegalStateException("Subscription attempts exceeded")`, `start()` throws `CompletionException`, and our `catch (RuntimeException)` → `container.stop()` returns at once (state `notListening`). The lock is held for at most one connect attempt (`connect-timeout` 2 s, `timeout` 2 s). Also `container.setPhase(SmartLifecycle.DEFAULT_PHASE - 1)`.
  2. `CatalogChangedSubscriber` implements `SmartLifecycle` plus `ApplicationListener<ApplicationReadyEvent>` and drops `DisposableBean`. `start()` only sets `running = true`; subscribing still begins on `ApplicationReadyEvent`. `stop()` sets `running = false`, calls `executor.shutdownNow()` and `awaitTermination(stopTimeout)`, logs one WARN if the thread is still alive, and on `InterruptedException` sets the interrupt flag again. Add `isRunning()`. `getPhase()` returns `DEFAULT_PHASE`, so the subscriber stops before the container. Its retry loop then never calls `container.start()` during or after the container's stop, and an attempt in flight finishes before `container.stop()` begins. That avoids a second race: a `doSubscribe` that joins an `unsubscribeFuture` which `doUnsubscribe` replaces without completing when `connection` is null (427-429, 524-529). New constructor parameter `Duration stopTimeout`; the config passes 5 s. Update the Javadoc.
  3. `SecondApiContext`: add `.registerShutdownHook(false)`, so a stuck close in a red run cannot block JVM exit. Every caller already closes the context explicitly.
  - Rejected: `setSubscriptionExecutor(ScheduledExecutorService)` (956-957) moves recovery off the lock and off our thread, but the container keeps its own unlimited 5 s retry loop with ERROR stack traces. `start()` would then time out after 2 s while that recovery runs in parallel with ours, and a scheduled recovery ignores `isRunning()`, so it can re-subscribe after `stop()`. `setTaskExecutor` only affects message dispatch. Reimplementing the container is unnecessary.
  - Trade-offs: one more lifecycle bean. Invalidations stop slightly earlier during shutdown; that is already true today because the container's phase is MAX, and the TTL bounds the staleness. Worst-case extra close time is the 5 s stop timeout, if a Lettuce connect ignores the interrupt. Accepted edge case: an interrupt during `lazyListen`'s 2 s wait makes `start()` return normally (383-385), so "Subscribed" may be logged during shutdown.

From the challenge of A10 to A18 (2026-11-25), all accepted. The mechanism and the fix were confirmed against `RMLC.java`.

- **A19 (blocker, A14 to A16 helper).** Do not publish a probe message to count subscribers. Delivery is async and clears every local cache (`CatalogCacheInvalidation`), which would flake `CatalogCacheOutageIT`'s "still Desk Lamp" assertion. Count subscribers read-only with `PUBSUB NUMSUB <channel>` (reply `[channel, count]`). Switch the existing `CatalogCacheIT` helper (~233-235) to it. In A15, await two subscribers before `otherPod.product(LAMP)`.
- **A20 (A16).** Assert the `CLIENT KILL TYPE pubsub` reply (clients killed) is at least 2. After the kill, assert the output has neither "Restarting subscription task" nor "Subscription(s) recovered".
- **A21 (logging).** On the STOP path the container logs `SubscriptionTask aborted with exception:` at ERROR, with a stack trace, on every failed attempt: at most one every 15 s with our backoff, down from one every 5 s today. Record this in A12's trade-offs and ADR 0012. A14 asserts this text appears after the trigger on new code, which proves the STOP path ran.
- **A22 (A12.2).** Correctness depends on STOP (A12.1) and A23, not on the 5 s stop wait. One attempt can take about 6 s (shared connect 2 s, pub/sub connect 2 s, registration wait 2 s). If the wait expires, the container stop overlaps the attempt; that is bounded at about 2 s and does not deadlock. Say this in the code comment and the ADR.
- **A23.** The retry loop checks a volatile `running` flag before each `container.start()` and after each `pause()`. It never restarts the container once `stop()` has begun, even if a library swallows the interrupt.
- **A24 (A13).** The interrupted-caller test keeps the worker busy (latch-blocked container mock) while `stop()` is called from an interrupted thread, then releases the latch. An idle pool's `awaitTermination` returns without checking the interrupt.
- **A25.** `onApplicationEvent` returns early when not running. `stop()` is idempotent. Keep `DisposableBean.destroy()` → `shutdownNow()` as a backstop.
- **A26 (follow-up, not this fix).** The pre-existing shutdown budget, about 54 s (preStop 10 s + web 20 s + task executor 15 s + subscriber 5 s + container about 4 s), exceeds `terminationGracePeriodSeconds: 40`. Note it in ADR 0012's consequences and record it as a follow-up in `STATUS.md`. No k8s change here.
- **A27.** `container.setPhase(DEFAULT_PHASE - 1)` stays as belt-and-braces. Dependency-ordered stop is the mechanism; say so in the comment.
- **A28 (A13 hygiene).** Stop and destroy the real container in `finally`. Stub `subscribe(any(), any(byte[][].class))`.
- **A29 (A14).** Make A14 a second method in `CatalogCacheOutageIT` with `@DirtiesContext(classMode = AFTER_EACH_TEST_METHOD)` if that keeps the context count the same; otherwise keep the new class. Run the old-code red check with `-Dit.test=<that class>` only.
