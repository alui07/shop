## Goal

The API and Keycloak see the real client address, and no client can choose it. Abuse is bounded at two layers: Envoy limits per client IP (floods, login starts, Keycloak login and registration posts, checkout bursts across accounts, the public webhook), and the API limits per account with Bucket4j on Valkey so the limit holds across replicas (checkout, order actions, cart writes, admin writes). Envoy caps request bodies; the API caps admin bodies. Every SQL statement has a `statement_timeout`, and a timeout is a 503 Problem Details, not a 500. Prometheus in kind evaluates alert rules for a stalled expiry job (R50) and dead-lettered events (R53), tested by `promtool` in `make lint`. Load tests, `make e2e` and `cluster-e2e` stay green with the limits on, and new tests prove 429, 413, spoof refusal and the timeout mapping.

## What exists today (read from the code, 2026-11-24)

- **Client IP.** `server.forward-headers-strategy: native`, so Tomcat's `RemoteIpValve` runs with Boot 4.1.2's default `server.tomcat.remoteip.internal-proxies` (CIDRs `10/8, 192.168/16, 169.254/16, 100.64/10, 172.16/12, 127/8, ::1, fc00::/7, fe80::/10`; verified in `spring-boot-tomcat-4.1.2.jar` metadata). Base `gateway.yaml` already has a `ClientTrafficPolicy` `shop` on the whole Gateway with `clientIPDetection.xForwardedFor.numTrustedHops: 0`, so Envoy's own view of the client is the TCP peer, but Envoy still **appends** the peer to a client-sent `X-Forwarded-For`. The kind peer (`172.18.0.x` on the `kind` network, or the Docker gateway for `127.0.0.1:8088`) is inside `172.16/12`, so the valve skips it as an internal proxy and takes the spoofed entry to its left: that is R20. The EnvoyProxy Service uses Envoy Gateway's default `externalTrafficPolicy: Local` (v1.10 API reference), so the source address survives the NodePort. The compose e2e nginx (`tests/e2e/gateway.conf`) already **replaces** `X-Forwarded-For` with `$remote_addr`; the Vite dev proxy sends none. Nothing reads the client IP today. Keycloak runs without `proxy-headers`, so its events and brute-force log show the gateway address (R3); its lockout is per user, not per IP (realm `bruteForceProtected: true`, defaults).
- **Network.** `api-from-gateway` allows API port 8080 only from Envoy pods; the fake PSP's `WebhookSender` calls the pod's own port and never passes Envoy. Pod CIDR `10.244.0.0/16` (`deploy/kind/cluster.yaml`).
- **Valkey.** Lettuce through `spring-boot-starter-session-data-redis` (Lettuce 7.5.2.RELEASE managed by Boot 4.1.2); used by Spring Session, revalidation locks (`StringRedisTemplate`) and the catalog pub/sub listener (which starts after readiness, 5b R1). `maxmemory 96mb`, `volatile-lru`.
- **Limits that exist.** 5b's per-pod `MintLimiter` (stays, R61). `RequestBodyLimitFilter`: 16 KiB on `/api/**` except `/api/admin/**` and the exact webhook (own 64 KiB counting stream); 415 for non-JSON. Admin bodies are bounded only by Jackson (R25). K10 caps per account (3 pending orders, 20 lines, 10 per line, 10 per product).
- **Database.** Hikari `data-source-properties.options: "-c lock_timeout=3s"`, pool 15/min-idle 5 (C4). Migrations start with `SET LOCAL lock_timeout = '5s'`. `ApiExceptionHandler.handleDataAccess` maps `55P03` to 503 with `Retry-After: 3`, everything else to 500. No `statement_timeout` (R34). Admin audit pages go to `OFFSET 1 000 000` (page 10 000 x size 100).
- **Observability.** Prometheus chart 29.47.2 (app v3.16.0), server only, Alertmanager off, OTLP ingest; `serverFiles.alerting_rules.yml` is empty. Series: `shop_events_dead_letter_rows` (gauge, NaN on DB failure, cached one step), `shop_reservations_released_units_total`, `tasks_scheduled_execution_seconds_count` (Boot's `@Scheduled` observation). The chart's `cm.yaml` renders `serverFiles` values with `toYaml`, so a rule file passed with `--set-file` would become a quoted string; it must arrive as structured values.
- **Load and e2e traffic shape.** All k6 traffic comes from one container IP on the `kind` network; k6 checkout VUs place an order every few seconds each and flash-sale VUs retry checkout every second. Playwright (both stacks) comes from one IP, with default workers and `retries: 0`.

## Design

### 1. Client IP (R20 first)

1.1 **Envoy replaces, never appends.** The existing `ClientTrafficPolicy` `shop` gains `headers.earlyRequestHeaders.remove: [X-Forwarded-For, X-Real-IP, Forwarded]`. Envoy then appends the TCP peer (numTrustedHops stays 0), so every upstream request carries exactly one `X-Forwarded-For` entry: the real peer. The policy targets the Gateway, so the `idp` and `loadtest` listeners are covered.
1.2 **Tomcat trusts only the gateway.** kind base `api.yaml` sets `SERVER_TOMCAT_REMOTEIP_INTERNAL_PROXIES=10.244.0.0/16` (pod CIDR; the API NetworkPolicy already limits 8080 to Envoy pods, the fake PSP and Keycloak call without XFF). compose `tests/e2e/compose.yaml` keeps the default (its nginx replaces the header). `application.yaml` keeps Boot's default and a comment naming both controls. Implementer confirms Boot 4.1.2 accepts CIDR notation for this property (metadata shows CIDRs) and that the env form binds.
1.3 **Proof.** IT `ClientAddressIT` with a test-only controller (test sources) returning `request.getRemoteAddr()`: with `internal-proxies=10.244.0.0/16`, a request from loopback is not trusted (XFF ignored); a unit-level `RemoteIpValve` test through Boot's customizer covers `XFF "1.2.3.4, 172.18.0.5"` from `10.244.0.9` resolving to `172.18.0.5`. Cluster: section 7.3.

### 2. Rate limits

2.1 **Envoy, per client IP, per Envoy replica.** Two `BackendTrafficPolicy` objects in `gateway.yaml`, targeting HTTPRoutes `shop` and `keycloak` (not `loadtest`, which has the mint limiter, and not Grafana). Rules (strictest match wins; values are starting points, see 2.5):

| Route | Selector (all `sourceCIDR: {type: Distinct, value: 0.0.0.0/0}` plus) | Limit | Covers |
|---|---|---|---|
| shop | none (all requests) | 100 / Second | floods, R1 |
| shop | `GET`, `PathPrefix /oauth2/authorization/` | 30 / Minute | pre-login sessions in Valkey, R2 |
| shop | `POST`, `Exact /api/checkout` | 30 / Minute | checkout across many accounts from one IP, R36 |
| shop | `POST`, `Exact /api/payments/webhook` | 20 / Second | R40 (HMAC and body read cost) |
| keycloak | none | 50 / Second | floods |
| keycloak | `POST`, `PathPrefix /realms/shop/login-actions/` | 30 / Minute | password guessing and lockout of a victim from one IP (R3), registration spam (R52) |

IPv6 needs a second `::/0` selector rule per row only if the listener ever gets IPv6 (kind is IPv4; noted, not added). `responseOverride` on each policy, `source: Local`, status 429: `application/problem+json` body `{"type":"tag:shop.dev,2026:rate-limited","title":"Too Many Requests","status":429,"detail":"Too many requests; try again later","errors":[]}` on `shop`, plain text on `keycloak` (Keycloak pages are HTML; a JSON body would be worse). Implementer checks that Envoy sends `Retry-After` on local 429s (v1.10 has `disableRetryAfterHeader`, implying it does); if not, the override sets `Retry-After: 60` for minute rules and `1` for second rules (separate overrides by path if needed).
2.2 **API, per account, Bucket4j on Valkey.** In module `auth` (the chain lives there): `RateLimitFilter` added after `RevalidationFilter`, so it sees the final principal and runs after CSRF; anonymous requests are never counted (they get 401 first). `RateLimitProperties` (`shop.rate-limit.enabled` default true, per-rule capacity and period lists), `RateLimitRules` (method plus `PathPatternRequestMatcher`, the same matcher type as the chain), `RateLimiter` (Bucket4j `ProxyManager<String>` from `bucket4j_jdk17-lettuce`). Rules (greedy refill; a rule with two bandwidths enforces both):

| Rule | Requests | Per account |
|---|---|---|
| `checkout` | `POST /api/checkout` | 10 / minute and 100 / hour (R36, R37) |
| `order-actions` | `POST /api/orders/{id}/payment`, `POST /api/orders/{id}/cancel` | 30 / minute |
| `cart-writes` | `PUT`, `DELETE /api/cart/lines/{slug}` and any other unsafe `/api/cart/**` | 60 / minute |
| `admin-writes` | unsafe methods on `/api/admin/**` | 30 / minute and 600 / hour (R24 audit growth) |

Key `shop:rate:<rule>:<sub>` (`sub` from the `OidcUser`, minted sessions included; no IP and no email in Valkey). Expiration `ExpirationAfterWriteStrategy.basedOnTimeForRefillingBucketUpToMax` so every key carries a TTL and stays evictable under `volatile-lru`; an evicted bucket starts full again (residual). Bucket4j's time source is a `TimeMeter` over the application `Clock` bean (so `MutableClock` drives ITs; implementer finds the 8.22 API for a client-side clock).
2.3 **Valkey connection.** One `StatefulRedisConnection<String, byte[]>` (UTF-8 key codec, byte-array values) from the native `RedisClient` behind Boot's `LettuceConnectionFactory` (implementer verifies the Spring Data Redis 4 accessor), opened lazily on first use and re-created after a failure, closed on shutdown; never touched during startup or readiness. Command timeout 500 ms (the limiter must not add 2 s to a write while Valkey hangs). D43 governs failures.
2.4 **Response.** 429 `application/problem+json` through `ProblemResponses`, type `tag:shop.dev,2026:rate-limited`, fixed detail `Too many requests; try again later`, `errors: []`, `Retry-After` = whole seconds rounded up from Bucket4j's `nanosToWaitForRefill`, minimum 1. No `X-RateLimit-*` headers. One INFO line per rejection with rule name and route pattern only. Counter `shop.rate_limit.rejected{rule}` (dashboard panel). OpenAPI: every limited operation declares 429 (springdoc customizer like `ServiceUnavailableResponseCustomizer`); `make generate` refreshes the contract and web client.
2.5 **Values and headroom.** The tables are the defaults. Before the values are fixed, the orchestrator runs `make e2e` and `cluster-e2e` once with logging on (Envoy access log, API rejection log) and records per rule the peak count per window from the single Playwright IP and the test accounts; each limit must be at least 3x that peak or the brief's value is raised (an amendment), never the test changed to avoid it. The shared `@IntegrationTest` context sets `shop.rate-limit.enabled=false` (as C12 did for the cache: many ITs check out repeatedly as one subject); only `RateLimitIT` exercises the limiter.
2.6 **Load tests (D44).** `components/loadtest` adds a JSON6902 patch raising every Envoy rule to 100 000 per unit and env `SHOP_RATE_LIMIT_*` raising every API rule likewise. `make k8s-lint` gains a check that `overlays/local` and `overlays/obs` render the base rule values unchanged (no raised limit outside `loadtest*`). k6: a `rate_limited` counter on any 429 outside `setup()`, threshold `count==0`, in every scenario.

### 3. Body limits (R25, R40)

`BackendTrafficPolicy` `shop` and `keycloak` set `requestBuffer: {limit: 64Ki, mode: BufferAndLimit}` (also shields the API from slow uploads); `responseOverride` for 413, `source: Local`, gives the `body-too-large` problem body on `shop`. `RequestBodyLimitFilter` keeps 16 KiB for customer routes and the webhook exemption, and applies 32 KiB (`ADMIN_LIMIT_BYTES`) to `/api/admin/**` with the same counting stream and 415 rule. The compose e2e nginx is not changed (the API filter covers it).

### 4. `statement_timeout` (R34, D45)

Hikari `options: "-c lock_timeout=3s -c statement_timeout=5s"` in `application.yaml` (all stacks). `LockFailures` gains `isStatementTimeout` (SQLState `57014`, plus Spring's `QueryTimeoutException`); `handleDataAccess` maps it to 503 with `Retry-After: 5`, detail `The request took too long; try again shortly`, and one WARN with exception class and SQLState only (no SQL text: it can carry product data). Jobs that hit it log as today and retry next run. README and ADR state the migration rule (`SET LOCAL statement_timeout = '...'` at the top of a migration that needs more). The implementer times the seed (`R__seed_catalog.sql`) and the slowest IT queries to confirm 5 s holds with margin, and records the numbers.

### 5. Alert rules (R50, R53, D40, D48)

5.1 Source of truth: `deploy/observability/alerts/shop.rules.yaml` (plain Prometheus rule file, group `shop`, `evaluation_interval` 1 m from the chart) and `deploy/observability/alerts/shop.rules.test.yaml` (`promtool test rules`). `obs-up` turns the rule file into a values file under `build/obs/` (`serverFiles: alerting_rules.yml:` with the file indented below it) and passes it as a second `-f` to the Prometheus release; the `helm_release` stamp includes the rule file's hash so a rule change re-applies. The chart's config-reload sidecar reloads Prometheus.
5.2 Rules (label names after OTLP translation are confirmed by querying the kind Prometheus; `check-metrics.sh` gains every series the rules use):
- `ShopEventsDeadLettered`: `max(shop_events_dead_letter_rows{job="shop-api"}) > 0`, `for: 5m`, warning; runbook: README dead-letter resubmission.
- `ShopReservationExpiryNotRunning`: no successful `ReservationExpiryJob.runOnce` execution in 5 m while the API reports `target_info`: `(sum(increase(tasks_scheduled_execution_seconds_count{job="shop-api",code_function="runOnce",code_namespace=~".*ReservationExpiryJob",outcome="SUCCESS"}[5m])) or vector(0)) == 0 and on() count(target_info{job="shop-api"}) > 0`, `for: 5m`, critical.
- `ShopReservationExpiryFailing`: `sum(increase(...{outcome!="SUCCESS"}[10m])) > 0`, `for: 10m`, warning.
- `ShopReservationsOverdue`: `max(shop_reservations_overdue{job="shop-api"}) > 0`, `for: 5m`, critical (D48; the gauge counts reservations whose expiry passed more than 2 minutes ago, about four job intervals).
5.3 `make prom-lint` (in `make lint`): `promtool check rules` and `promtool test rules` in `PROMETHEUS_IMAGE`. Tests cover each alert firing after its `for`, not firing below it, the gauge's NaN (DB failure) not firing, the no-series case of the expiry job firing only while `target_info` exists, and a pod restart resetting the counter (`increase` handles it).
5.4 Show it firing: `make obs-alerts` prints Prometheus `/api/v1/alerts` (state, name, since) from a `k8s-tools` container; the dashboard gains an "Alerts" panel (`ALERTS{alertstate=~"pending|firing"}`). `tests/manual/README.md`: insert one row into `event_publication_dead_letter` in the kind DB through `make kubectl ARGS="exec ..."` (implementer writes the exact command from `V10__event_publication.sql`), watch pending then firing after 5 m, delete it. Alertmanager stays off; ADR 0010 says how a cloud setup would add it.

### 6. Web (D49)

`failureMessage.ts` and `adminForms.ts` map 429 to `Too many attempts. Try again in N seconds.` (`N` from `Retry-After`, else `a moment`), matching how 503 is handled; tests for both branches. No other web change.

## Top risks (for the challenger)

1. Bucket4j's Lettuce module is built against Lettuce 6.1 and runs here on 7.5.2: binary compatibility is unproven until `RateLimitIT` runs. Fallback if it fails: stop and ask; candidates are a small CAS `ProxyManager` over Spring Data Redis, or pinning `8.21.0` if the break is new.
2. Single-IP test traffic: Playwright and k6 each share one address, so a per-IP limit set too low fails e2e or k6 in ways that look like app bugs. The headroom rule (2.5) and the loadtest overlay (2.6) are the controls; a CI runner with more workers raises the peak.
3. Envoy local-limit details: `Retry-After` presence, `responseOverride` matching Envoy's own 429 and 413, rule interplay (strictest wins), and per-route LRU of 10 000 IPs.
4. Fail-open hides a Valkey problem from the limiter; the counter and panel are the only signal.
5. `statement_timeout` breaking a slow path nobody measured (seed, admin audit deep pages under load, jobs); the 57014 branch must not swallow a cancellation that means something else.
6. A new Valkey use becoming a startup dependency (5b R1).
7. Alert label names after OTLP translation (`code_function`, `outcome`) differ from the guess; promtool tests pass on wrong names, so the live check in 5.2 is required.

- **A1 (C5c-1, blocker):** every Envoy path selector is `PathPrefix` unless the brief justifies `Exact` (`:path` includes the query, so `Exact /api/checkout` misses `?x=1`). Checkout and webhook rules use `PathPrefix`. No `RegularExpression` (the guard awk rejects it). The `/oauth2/authorization/` rule has no `methods` selector (HEAD and OPTIONS also mint a pre-login session); `login-actions` keeps `POST`. `limits-test.js` adds `POST /api/checkout?x=1` (429 within the checkout budget) and `HEAD /oauth2/authorization/keycloak` counting against login start.
- **A2 (C5c-2):** `addFilterAfter(rateLimit, AuthorizationFilter.class)`, not after `RevalidationFilter`. Tests: a 429 carries `Cache-Control: no-store` and the other security headers; a CSRF-less POST from a signed-in customer and a customer request to `/api/admin/**` create no key.

Fail open only on `RedisException`, `BucketExecutionException`, `CompletionException` wrapping them, and `TimeoutException`; a `LinkageError` propagates. `RateLimitIT` uses a second Valkey container for the limiter only and pauses it: a signed-in write still succeeds within 1.5 s, `shop.rate_limit.backend.failures` rises, exactly one WARN; the context also starts with that container paused.
