# Slice 5 implementation brief: observability, k6, HPA and PDBs under load, cache measurement

Branch: `slice-5-load-and-observability` from `main` at `3d8fc5f` (PR #9 merged 4b). Read first: `CLAUDE.md`, `master-plan.md` (Architecture rows Observability, Load testing, Kubernetes, Valkey; Verification), ADR 0005, 0006, 0008, 0009, `docs/threat-model.md`, `tests/README.md`, `deploy/versions.mk` and its comments. Not a high-risk slice: one challenger, one reviewer.

Standing rules for every agent: every tool runs in a container through the `Makefile`; nothing is installed on the host, never install system packages. If Docker fails with a permission error, prefix with `sg docker -c "..."`. No git commands except read-only `git status`, `git diff` and `git log`. Coverage gates are 100% (API line and branch; web lines, branches, functions, statements); the only exclusions are `apps/web/src/routeTree.gen.ts` and `apps/web/src/components/ui/**`; never add one, never add an ignore comment or lower a threshold: stop and ask. Never hand-edit `openapi.json`, `schema.d.ts` or `routeTree.gen.ts`; run `make generate`. Every new image, chart and tool version goes in `deploy/versions.mk`, at least 7 days old; pnpm's release-age gate stays on. Files under 500 lines; reports under `build/`, nothing in the repo root. Never commit or print secrets. Known traps: Spring Boot 4, Java 25, kubelet 1.36 and k6 2.x are newer than most training data, so read official docs; Jackson 3 is `tools.jackson.*`; `RestClient`, never `RestTemplate`; Testcontainers 2 artifact names; no Bitnami; the local kind node is cgroup v1 (`failCgroupV1: false`), CI is cgroup v2.

## Goal

`make obs-up` installs Prometheus, Grafana, Tempo and Loki (plus an OpenTelemetry Collector) in kind; `make dev OBS=1` adds `grafana/otel-lgtm` to compose. The API exports traces, metrics and logs over OTLP with trace IDs shared by logs and spans; one provisioned dashboard shows rate, errors, latency percentiles, connection-pool usage, cache hit ratio and API replica count. The API runs under an HPA with PDBs. `make loadtest` runs three k6 scenarios against kind (catalog browsing, full checkout with fake payment and webhook, flash sale for limited stock), passes thresholds, records the HPA adding pods during the flash sale, and proves zero oversold stock from the database. `make loadtest-cache` measures catalog browsing with the cache off and on; results go in `docs/performance.md`. Framed throughout as mechanism proof and bottleneck finding on one shared host, never capacity numbers.

## What exists today (read from the code, 2026-11-21)

- `spring-boot-starter-opentelemetry` is already a dependency (Boot 4.1.2). `application.yaml` disables all three OTLP exports (`management.tracing.export.otlp.enabled`, `management.otlp.metrics.export.enabled`, `management.logging.export.otlp.enabled` all `false`); sampling is 1.0. `ObservabilityIT` asserts no OTLP beans by default and that the ECS log line carries `traceId` from an incoming `traceparent`.
- Logs: ECS structured JSON on stdout outside `dev`. Management port 8081 exposes health only; probes split (liveness, readiness with `db`); graceful shutdown 20 s phase, 40 s grace, 10 s `preStop` sleep, executor await 15 s.
- `deploy/k8s/base/api.yaml`: `replicas: 1`, requests 250m/512Mi, limits 2 CPU/768Mi, Hikari pool 20. No HPA, no PDB, no metrics-server. Web `replicas: 1`. Valkey limit 200m CPU, `--maxmemory 96mb --maxmemory-policy volatile-lru` (sessions carry a TTL, so they are the eviction candidates).
- Valkey holds Spring Session data and the revalidation locks only. No Bucket4j or any rate limiting exists yet (master plan named it; not built). No catalog cache; `CatalogController` sends `Cache-Control: no-cache`.
- Sessions: `OAuth2AuthenticationToken` with `DefaultOidcUser`; `CurrentUser.of` requires an `OidcUser`. `LoginSuccessHandler` stamps `AUTHENTICATED_AT` and both revalidation instants. `RevalidationFilter` refreshes with Keycloak every 5 min of activity and ends a session with no authorized client (fail closed). `AllowlistDeserializer` allows `org.springframework.security.**` and `dev.shop.api.**`.
- Security: the main chain ends in `anyRequest().denyAll()`; SPA CSRF with `__Host-XSRF-TOKEN` and `X-XSRF-TOKEN`. `RequestBodyLimitFilter` lets a body-less POST through.
- The fake PSP's `WebhookSender` calls the API's own port, so a payment completion produces a signed webhook to the same pod, never through Envoy.
- Gateway: listeners `http` (80, NodePort 30080, host 8088), `idp` (8089), `mail` (local only, host 8026); HTTPRoute `shop` strips `X-Forwarded-Host` on `/api`; an Envoy `HTTPRouteFilter` `not-found` already exists. `deploy-apply` renders only `overlays/local`, with `sed` placeholders for image IDs and secret hashes.
- `Makefile` is 397 lines; the new targets would pass 500.

## Decisions

### 1. Observability

1.1 **Boot-native OpenTelemetry, no Java agent.** The starter is already there and the agent would duplicate Micrometer's instrumentation and need a second JVM flag in every stack. Traces: Micrometer Tracing with the OTel bridge. Metrics: Micrometer's OTLP registry (cumulative temporality, explicit-bucket histograms). Logs: `opentelemetry-logback-appender-1.0` attached to the root logger by an `OtlpLogAppenderConfiguration` that is `@ConditionalOnProperty("management.logging.export.otlp.enabled")` and calls `OpenTelemetryAppender.install(openTelemetry)` (Boot provides the `SdkLoggerProvider` but no bridge). stdout ECS JSON stays as it is, so `kubectl logs` and the existing `traceId` field are unchanged.
1.2 **Export is off by default and switched on by environment only.** `application.yaml` keeps the three `enabled: false` keys. Stacks with a collector set `MANAGEMENT_TRACING_EXPORT_OTLP_ENABLED`, `MANAGEMENT_OTLP_METRICS_EXPORT_ENABLED`, `MANAGEMENT_LOGGING_EXPORT_OTLP_ENABLED=true` and `MANAGEMENT_OPENTELEMETRY_OTLP_ENDPOINT=http://<collector>:4318` (the common endpoint the per-signal ones fall back to; metrics need `MANAGEMENT_OTLP_METRICS_EXPORT_URL=http://<collector>:4318/v1/metrics` if the fallback does not cover the registry, check). Resource attributes `service.name=shop-api`, `deployment.environment` and `service.instance.id` (pod name via the downward API in kind). `management.metrics.distribution.percentiles-histogram.http.server.requests=true`. Caffeine `recordStats` exposes `cache.gets{result=hit|miss}`; Hikari and JVM metrics are already bound by Boot.
1.3 **Push, one OTLP endpoint everywhere.** Compose: `otel-lgtm` (service `otel-lgtm`, OTLP 4318 on the compose network only, Grafana on `127.0.0.1:3000`), under compose profile `obs`; `make dev OBS=1` sets `COMPOSE_PROFILES=obs` and the API's export variables. Cluster: namespace `obs` with an OpenTelemetry Collector (Deployment, core image) receiving OTLP/HTTP and exporting traces to Tempo (OTLP), logs to Loki (`/otlp`, Loki 3 native ingest) and metrics to Prometheus's OTLP receiver (`--web.enable-otlp-receiver`, Prometheus 3). The API never talks to a backend directly, so its config is the same in both stacks.
1.4 **Prometheus chart scope.** Server only plus the `kube-state-metrics` subchart (for the replica-count panel); `alertmanager`, `prometheus-node-exporter` (needs host access) and `pushgateway` off; `emptyDir` storage, 6 h retention; OTLP translation keeps the `_seconds`/`_total` suffixes and promotes `service.instance.id` and `k8s.pod.name` to labels. Loki SingleBinary with filesystem storage, replication 1. Tempo single binary, local storage, 6 h retention. Grafana with sidecar dashboard loading, datasources Prometheus, Tempo (traces to logs by `trace_id` into Loki) and Loki (derived field from `trace_id` to Tempo), provisioned in `deploy/observability/grafana-values.yaml`; admin password from the new `GRAFANA_ADMIN_PASSWORD` secret (Secret `grafana-admin` in `obs`), anonymous Viewer on, bound to loopback through the kind mapping (D33).
1.5 **Dashboard as code.** One file, `deploy/observability/dashboards/shop-api.json`, used by both stacks: compose mounts it into `otel-lgtm`'s dashboard provisioning directory (implementer reads the image's docs for the path); the cluster loads it as a ConfigMap labelled `grafana_dashboard: "1"`, created by `obs-up` from the file. Panels: request rate by route and status, 5xx ratio, p50/p95/p99 from `http_server_requests_seconds_bucket`, Hikari active/idle/pending and max, cache hit ratio, JVM heap and CPU, API replica count (kube-state-metrics; empty in compose), plus a logs panel and a trace search link. The Prometheus datasource is a dashboard variable chosen by type, so no datasource UID is hard-coded. `deploy/observability/check-metrics.sh` queries a Prometheus for every metric name the dashboard uses and fails on a missing one; it runs against both stacks during integration (OTLP-to-Prometheus name translation is the likely mismatch).
1.6 **Trace sampling.** 1.0 stays the default for `dev` and `obs`; the `loadtest` overlay sets `MANAGEMENT_TRACING_SAMPLING_PROBABILITY=0.1` so Tempo and the collector are not the bottleneck being measured. Cache-off and cache-on runs use the same telemetry settings.
1.7 **NetworkPolicy.** `default-deny` covers egress in `shop`, so the `otel` component (2.6) adds `api-to-otel-collector` (egress to namespace `obs`, collector pods, TCP 4318). `obs` gets no policies in this slice (residual in the threat model). metrics-server scrapes kubelets, not pods: no `shop` policy change.
1.8 **Memory budget** (limits; requests about half). Obs: collector 256 Mi, Prometheus 512 Mi, kube-state-metrics 64 Mi, Loki 384 Mi, Tempo 384 Mi, Grafana 256 Mi: about 1.9 GiB. Under load: four API pods at 768 Mi (3 GiB), Keycloak 1 GiB, two Postgres 1 GiB, Calico, Envoy, operators and system about 1.5 GiB, k6 about 0.5 GiB: peak about 8 GiB inside the 12 GiB WSL limit. `make loadtest` refuses to start while the compose dev stack (`shop` project) is running, and the brief's integration step records `docker stats` peaks in `docs/performance.md`.

### 2. Session minting under the `loadtest` profile

2.1 **Shape.** `POST /api/loadtest/sessions`, no body, header `Shop-Loadtest-Token`. Response `201` with `{ "subject": "loadtest-<uuid>" }` and the `__Host-SESSION` cookie. The server chooses the subject; the prefix and hyphenated UUID cannot collide with Keycloak subjects (plain UUIDs). Classes in `dev.shop.api.auth` (they need the package-private `SessionAttributes`): `LoadtestSessionConfiguration`, `LoadtestSessionController`, `LoadtestProperties` (`shop.loadtest.token`, `max-mints-per-second` default 10, `session-timeout` default 5m), `LoadtestGuard`. Every one of them is `@Profile("loadtest")`; the controller is `@Hidden` from springdoc.
2.2 **What a minted session is.** Exactly what a login produces, minus Keycloak: an `OAuth2AuthenticationToken` over a `DefaultOidcUser` built from a synthetic `OidcIdToken` (claims `sub`, `roles: ["customer"]`, `name`, `email` `<subject>@loadtest.invalid`, `email_verified: true`, issued now, expiry now plus `session-timeout`), registration id `keycloak`, saved through `HttpSessionSecurityContextRepository` into a new Spring Session in Valkey (same serializer and JEP 290 allowlist; no new types). It stamps `AUTHENTICATED_AT` and both revalidation instants as `LoginSuccessHandler` does and sets `maxInactiveInterval` to `session-timeout`. Role `customer` only; there is no way to mint `admin` or `support`. No authorized client is stored, so the first revalidation after 5 min finds none and ends the session (fail closed, as for a revoked login). k6 therefore re-mints every 4 min per VU. Keycloak is never on the load path, which the results state.
2.3 **Security chain.** A second `SecurityFilterChain`, `@Order(2)` (the webhook chain is `@Order(1)`), `securityMatcher` = `PathPatternRequestMatcher` for `POST /api/loadtest/sessions` exactly, `permitAll` (the controller authenticates the token), CSRF off (no cookie is read on this route; the token header is the credential, which a cross-site page cannot set), request cache off. The token check hashes both sides with SHA-256 and compares with `MessageDigest.isEqual`; a missing or wrong token gives `401` Problem Details and one WARN line without any header value. A per-pod fixed-window limiter (`max-mints-per-second`, `Clock`-driven, no new dependency) answers `429` with `Retry-After: 1`. Worst case with four pods: 10 x 4 x 300 s = 12 000 sessions; the implementer measures one session's size in Valkey and records that this stays well under 96 MB (or lowers the limit).
2.4 **Fail-fast guards.** `LoadtestProperties` validates `token` `@NotBlank` and length at least 32 by a custom check that never echoes the value (4b's C8 lesson). `LoadtestGuard` fails startup unless `shop.auth.public-origin` has host `localhost` or `127.0.0.1`, so the profile cannot run behind a real hostname (slice 6's cloud overlay included).
2.5 **Never enabled by accident.** No `spring.profiles.group` includes `loadtest`; the Dockerfile sets no profile. Only `deploy/k8s/components/loadtest` sets `SPRING_PROFILES_ACTIVE=seed,loadtest` and the token env (from Secret `shop-loadtest`, key `SHOP_LOADTEST_TOKEN`, a new `SECRET_KEYS` entry; `apply_secrets` creates it; a `shop-loadtest-hash-placeholder` annotation rolls the API when it changes). `k8s-lint` adds a guard that renders `overlays/local` and `overlays/obs` and fails if `loadtest` appears in any env value or `shop-loadtest` is referenced; `compose-lint` does the same on `docker compose config` for both compose files.
2.6 **Network exposure: never on the front door.** Base: the `shop` HTTPRoute gains a `PathPrefix /api/loadtest` rule with the existing `not-found` filter (longest prefix wins over `/api`), and its `/api` rule also removes the `Shop-Loadtest-Token` header, so even a path variant that slips past Envoy's matching reaches the API without a token. The `loadtest` component adds a Gateway listener `loadtest` on port 8090 (NodePort 30090 added to the EnvoyProxy service patch, **no host port mapping**) with an HTTPRoute that matches only `POST` `Exact /api/loadtest/sessions`. k6 runs in a container on the `kind` Docker network and is the only intended client of `shop-control-plane:30090`. The cluster check (6.3) asserts the front door answers `404` for the path, a trailing slash, `%6C`-encoded and upper-case variants, with the token header set.
2.7 **Tests.** `LoadtestSessionsIT` (own context, profiles `loadtest`, a test token, `MutableClock`): mint gives 201 and the cookie; `/api/me` shows the subject and only `customer`; `PUT /api/cart/lines/{slug}` without `X-XSRF-TOKEN` is 403 and with it succeeds (CSRF still enforced on the minted session); missing and wrong token 401 with no token in captured output; GET and a trailing-slash path do not mint; the limiter's 429 and recovery; after advancing the clock past `revalidateAfter` the next request is anonymous. `LoadtestAbsentIT` (the shared `@IntegrationTest` context): no `LoadtestSessionController` bean, and `POST /api/loadtest/sessions` with a token header is refused (403 from `denyAll`), with no `Set-Cookie: __Host-SESSION`. `OpenApiContractIT` asserts no `/api/loadtest` path. `LoadtestGuardTest` (`ApplicationContextRunner`): a non-local origin fails startup; a short or blank token fails without the value in the message.

### 3. HPA, PDBs and metrics-server

3.1 **metrics-server** is installed by `cluster-up` (Helm, `kube-system`, values `deploy/kind/metrics-server-values.yaml`: `--kubelet-insecure-tls` because kind's kubelet certificates are self-signed, `--metric-resolution=15s`), then `kubectl wait --for=condition=Available apiservice/v1beta1.metrics.k8s.io`. On the cgroup v1 node it reads the same kubelet resource endpoint; the integration run confirms `kubectl top pods -n shop` works locally and in CI.
3.2 **HPA** `api` in `deploy/k8s/base/hpa.yaml` (`autoscaling/v2`): min 2, max 4 (D32), CPU utilisation target 60% of the 250m request; `behavior.scaleUp` default (no stabilisation, up to double per 15 s), `scaleDown.stabilizationWindowSeconds: 120`. `replicas` is removed from the `api` Deployment so the HPA owns it under server-side apply (otherwise every `make deploy` resets it). Four pods x Hikari 20 = 80 connections against CNPG's default `max_connections` of 100: within limits; the dashboard's pending-connections panel is where that bottleneck would show, recorded rather than pre-tuned. Web: `replicas: 2`, no HPA.
3.3 **PDBs** `api` and `web`, `maxUnavailable: 1` (`deploy/k8s/base/pdb.yaml`). No PDB for single-replica Keycloak, Valkey or Mailpit (one would block drains forever); CNPG manages its own.
3.4 **Why the flash sale scales on one host.** Utilisation is measured against the 250m request while the limit is 2 CPUs, so sustained flash-sale load pushes each pod well past 150m; metrics-server reports every 15 s and the HPA syncs every 15 s, so a scale-up should appear within about a minute of sustained load. New pods' JVM start-up CPU is ignored by the HPA's CPU initialisation period. The flash sale holds load for 3 min after the sell-out for this reason.
3.5 **Evidence.** During `make loadtest` a sampler container (k8s-tools, background) writes `build/reports/loadtest/<run>/hpa.csv` every 5 s (time, HPA current and desired replicas, current CPU %, ready API pods) and, at the end, `kubectl get events -n shop --field-selector reason=SuccessfulRescale` and `kubectl top pods`. `make loadtest` fails unless the maximum ready API pod count during the flash-sale window exceeds the HPA minimum.
3.6 **PDB proof in CI.** `tests/e2e/cluster/pdb-test.sh`, run by `cluster-e2e` after Playwright: evict one API pod through the Eviction API (expect success), immediately evict the other (expect HTTP 429 from the PDB), wait for the rollout to recover. It also asserts the metrics API returns `shop` pods. Adds well under a minute to the CI job.

### 4. Catalog cache (D34)

4.1 Spring Cache with `@EnableCaching` in a `catalog` configuration; `spring.cache.type=caffeine`, `spring.cache.cache-names=categories,product,productPage`, `spring.cache.caffeine.spec=maximumSize=2000,expireAfterWrite=30s,recordStats`.
4.2 `@Cacheable` on `CatalogService.categories()`, `product(slug)` and `search(...)` **only when `text` is blank** (SpEL `condition`): free-text search is an unbounded key space and an easy way to churn the cache, and its hit rate is low. Not-found results are not cached (exceptions are never cached). Responses are immutable records.
4.3 Invalidation: `ProductAdministration.create` and `update` publish a `CatalogChanged` application event inside the admin transaction; a `@TransactionalEventListener(phase = AFTER_COMMIT)` in `catalog` clears all three caches. A rollback clears nothing; a read that took its snapshot before the commit may re-cache the old row for up to 30 s, as may other pods: documented in the ADR. Stock writes do not touch catalog responses. Checkout already recomputes prices from the database, and the existing `price-changed` problem covers a cart that saw a stale price.
4.4 **Cache off without new code:** `SPRING_CACHE_TYPE=none` gives Boot's no-op cache manager, so cache-off and cache-on run the same build. Overlay `loadtest-nocache` sets it.
4.5 **Test isolation.** `CatalogFixtures.clear` also clears every cache, so existing ITs that truncate and reseed never read stale entries. `CatalogCacheIT`: a direct `UPDATE` through `JdbcTemplate` is not visible within the TTL (proves caching); an admin update is visible right after commit; a rolled-back admin update leaves the cached value; a search with text is never cached; `cache.gets` metrics appear. A test with `spring.cache.type=none` sees the direct update at once.
4.6 **Measurement.** `make loadtest-cache`: deploy `loadtest-nocache`, run `browse` at a fixed arrival rate, snapshot `pg_stat_database` (`xact_commit`, `tup_returned`) before and after and the API pods' CPU; deploy `loadtest`, repeat. Three runs each, medians reported. `docs/performance.md` (committed) records date, commit, host (CPU, WSL memory, cgroup version), settings, and per run p50/p95/p99, achieved rate, error rate, database transactions per request, API CPU, plus the flash-sale and HPA evidence from 3.5 and the bottlenecks seen. Raw k6 summaries stay under `build/reports/loadtest/`.

### 5. k6 scenarios (`loadtest/`)

5.1 Layout: `loadtest/lib/{config,session,shop,checks}.js`, `loadtest/scenarios/{browse,checkout,flash-sale}.js`, `loadtest/sql/{flash-setup,flash-verify,db-stats}.sql`. Plain JavaScript modules for k6 2.4 (read the k6 v2 docs; do not assume 0.x APIs). Each scenario has `handleSummary` writing `summary.json` and a short `summary.md` to `/reports`.
5.2 Session helper: mint on `shop-control-plane:30090`, then `GET /api/me` on the front door to obtain `__Host-XSRF-TOKEN` the way the SPA does; send `Cookie` and `X-XSRF-TOKEN` headers explicitly (k6's jar follows Go's rule of not sending `Secure` cookies over plain HTTP). Re-mint when the session is 4 min old. Mint requests are tagged `name:mint` and excluded from latency thresholds.
5.3 `browse` (anonymous): `GET /`, `/api/me`, `/api/categories`, `/api/products` (pages, category filters, sorts; a small share with text), `/api/products/{slug}`. Constant arrival rate 30 it/s for 2 min. Thresholds: `http_req_failed < 1%`, p95 < 500 ms, checks > 99%.
5.4 `checkout`: ramping 5 to 20 VUs over 3 min; per iteration: add 1 to 2 seeded products to the cart, `POST /api/checkout` with a fresh `Idempotency-Key`, `POST /api/orders/{id}/payment`, `GET` and `POST .../complete` on the fake PSP with outcome success, then poll `GET /api/orders/{id}` (1 s, up to 20 s) until `PAID`. Thresholds: failed < 1% (with `expectedStatuses` for designed refusals), checkout p95 < 1.5 s, `order_paid` rate > 98%, time to `PAID` p95 < 10 s.
5.5 `flash-sale`: `flash-setup.sql` (run through `make kubectl`-style `kubectl exec` into `shop-db-1` with `psql`) creates product `flash-<run>` with `on_hand = 100`. 150 VUs start together; each tries to check out one unit and pays at once on success; `409` out-of-stock is an expected outcome, counted. VUs keep trying and browsing for 3 min after the sell-out to hold load for the HPA. k6 thresholds: `flash_orders_created <= 100`, `flash_orders_paid <= 100`, failed requests (unexpected statuses) < 1%.
