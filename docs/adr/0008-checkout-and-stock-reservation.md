# ADR 0008: Cart, checkout and stock reservation

Status: Accepted (slice 4a). Slice 4 is split: 4a (this ADR) covers cart, checkout, reservations, expiry, idempotency, orders and cancel; 4b adds payment, the webhook, the outbox and email (ADR 0009). "Deviations" at the end lists where the code differs from the first design.

## Context

Slice 3b fixed the stock contract (ADR 0007): `stock(product_id, on_hand, reserved, version)` with `reserved <= on_hand`, and checkout must lock stock rows, re-price and re-check under that lock. Slice 4a builds on it: a signed-in customer fills a cart, checks out, and the API reserves stock for a limited time so that stock never oversells, whatever the concurrency, replicas or retries. 4a ships no payment path, so its orders end only in `CANCELLED` or `EXPIRED`. Authentication, CSRF and role rules are unchanged from ADR 0006.

## Decisions

**Who has a cart (D21).** Signed-in customers only, stored in Postgres by `sub`. Anonymous visitors see `Sign in to buy`. ADR 0006 has no anonymous sessions and sets no cookie for anonymous users; an anonymous cart would need a cookie, unauthenticated writes (CSRF for anonymous, unbounded rows before slice 5c's rate limits) and a merge on login. No server-side merge. A guest cart in `localStorage` was the alternative (more web code, merge rules). A cart must always be emptiable: `DELETE` works for inactive and unknown products (F8).

**Hold time and anti-hoarding limits (D22, F3).** Reservation lasts 15 minutes (`shop.checkout.reservation-ttl`). Limits, all properties: at most 3 orders awaiting payment per customer (409 `too-many-pending-orders`); quantity 1 to 10 per line; at most 20 lines (409 `cart-full`). Per-product cap: a customer's `ACTIVE` reservations on orders still `PENDING_PAYMENT` with `expires_at > now`, plus the new quantity, may not exceed `shop.checkout.max-reserved-per-product` (default 10) for any product; refusal is 409 `reservation-limit` with one error per product (`field` = slug). Without these, one account could hold all stock for free. The caps are per account; accounts are free, so they do not bound one attacker (R36 arrives in 4b with self-registration; rate limits in slice 5c).

**Cart model (F8, F10).** `cart(id, customer_subject UNIQUE, version, updated_at)` and `cart_line(cart_id, product_id, quantity 1..10)`. Every cart write locks the cart row first. `PUT /api/cart/lines/{slug}` upserts the cart with `INSERT ... ON CONFLICT (customer_subject) DO UPDATE SET updated_at = :now RETURNING id, version` (a new cart starts at version 0), counts lines (`cart-full` at 21), writes the line and bumps `version`, so the first `PUT` gives version 1 (a `PUT` that repeats the line's current quantity changes nothing and leaves the version alone) and never equals the "absent cart is version 0" view. `DELETE` locks with `SELECT ... FOR UPDATE`, never creates a cart, and bumps the version only when it removed something. Unknown or inactive slugs: `PUT` gives 404; `DELETE` resolves inactive products too and treats an unknown slug as a no-op 200. `GET /api/cart` runs read-only at `REPEATABLE_READ` so prices and stock come from one snapshot; inactive lines show `available: false`. `available` is `active && on_hand - reserved >= quantity`; customers never see stock numbers. `Add to cart` on the product page sets the line's quantity (`PUT` semantics), it does not add to the quantity already in the cart; the cart page changes quantities the same way.

**Re-pricing and price snapshots.** The client sends `cartVersion` and `expectedTotalMinor`. Checkout locks products `FOR SHARE`, recomputes the total from current prices and answers 409 `price-changed` when it differs. Order lines snapshot slug, name, unit price, currency and quantity, so later admin edits never change an order. An admin price change needs `FOR UPDATE` on the product row and so waits for in-flight checkouts; the snapshot equals the price at commit. This closes R29.

**Global lock order (F6).** One order for every transaction that takes more than one lock, inherited by 4b: idempotency row, cart row, `orders` rows, `payment` rows (4b), product rows (`FOR SHARE`, ascending id), stock rows (ascending `product_id`, each at most once per transaction, across every order the transaction handles). Single-order paths (cancel, lazy expiry, and later consume and `takeLate`) keep ascending product order. Checkout inserts its new `orders` row only after the product locks, which is safe because no other transaction can reach a row that is not yet committed. The expiry job holds many orders in one transaction, so it releases through `releaseAll` (below), which aggregates per product and updates stock in ascending id. `StockRaceIT` includes a crossed-order variant of two expiry batches against concurrent checkouts and asserts that no checkout fails with 503 and that the Postgres log holds no `deadlock detected` or `40P01`.

**Conditional stock update and `InsufficientStockException` (F9).** Per line, by product id: `UPDATE stock SET reserved = reserved + :q WHERE product_id = :id AND on_hand - reserved >= :q`. A row count of 0 makes `reserve` throw `InsufficientStockException(List<Long> shortProductIds)`, a plain public `RuntimeException`; lines reserved earlier in the transaction are not counted short, and for the failing and every later line availability is read without reserving, so the error lists every short line. `CheckoutService` maps ids to slugs from its priced products and answers 409 `out-of-stock` with one error per slug; the transaction rolls back. `reserved` changes never bump `stock.version` (ADR 0007). The `CHECK (reserved <= on_hand)` stays as the last guard.

**Reservations and expiry.** One `reservation` row per order line (`ACTIVE`, `CONSUMED`, `RELEASED`). `orders.expires_at = now + reservation-ttl`; `reservation` has no `expires_at` of its own (F17). All times come from the injected `Clock` and are passed to SQL as parameters, never `now()`. `ReservationExpiryJob` runs every 30 s (`shop.checkout.expiry-interval`) and loops: in one transaction `SELECT id FROM orders WHERE status = 'PENDING_PAYMENT' AND expires_at <= :now ORDER BY expires_at LIMIT 50 FOR UPDATE SKIP LOCKED`, then `StockReservations.releaseAll(orderIds)`, which sums the batch's `ACTIVE` reservations per product (`GROUP BY product_id ORDER BY product_id`), runs one `UPDATE stock SET reserved = reserved - :q` per product in ascending id, marks the reservations `RELEASED` and the orders `EXPIRED`; commit; repeat while a full batch returned. Replicas take disjoint batches, and an order being cancelled is locked and skipped until the next run. `MaintenanceJob` (hourly) deletes expired idempotency keys in batches of 1 000 (`ctid IN (SELECT ... LIMIT ... FOR UPDATE SKIP LOCKED)`). Jobs log counts only.

**Scheduling configuration (F18).** One `web.AsyncAndSchedulingConfiguration` holds `@EnableScheduling`, guarded by `@ConditionalOnProperty(name = "shop.jobs.enabled", matchIfMissing = true)`. ITs set `shop.jobs.enabled=false` and call the jobs' `runOnce()`. 4b adds `@EnableAsync` to the same class. There is no `@EnableAsync` in 4a.

**Named interfaces (F7).** `StockReservations`, `InsufficientStockException` and the reservation line record live in `inventory.reservations` (`@NamedInterface("reservations")`); `ProductPricing` and `PricedProduct` in `catalog.pricing` (`@NamedInterface("pricing")`). `order` allows `cart`, `catalog::pricing`, `inventory::reservations`, `customer`, `web`; `cart` allows `catalog::pricing`, `inventory`, `customer`, `web`. `admin` keeps plain `catalog` and `inventory`, so it cannot reach reservations. `ModularityTest` enforces this, and `ModuleRulesTest` asserts that an `admin` reference to `inventory::reservations` (the test-only `ReservationPeeker`) is reported as a violation. `admin` also allows `catalog::pricing`, because `Money` lives there and a plain `catalog` entry does not cover named interfaces. This also lets `admin` code call `ProductPricing.lockForCheckout`, which it has no need for. Accepted for 4a (no admin code calls it, and `ModularityTest` would not catch one that did); the follow-up option is to move `Money` into its own named interface so `admin` need not allow `catalog::pricing`. `StockReservations` methods carry no `@PreAuthorize` (the expiry job runs without a user), use `Propagation.MANDATORY`, and are called only from `order`; `MandatoryTransactionIT` covers them, together with the product lock in `ProductPricing` and the cart locks.

**Checkout transaction.** One `READ COMMITTED` transaction (checkout is the outermost one; Spring ignores `isolation` on a joined transaction). Steps, in lock order: validate the `Idempotency-Key` header; insert or fetch the idempotency row; lock the cart row (missing, empty or version mismatch is 409 `cart-changed`); count pending orders and per-product reservations for the caps (the cart row lock serialises one customer's checkouts); lock products `FOR SHARE` (inactive: 409 `out-of-stock`) and re-price; insert `orders` and `order_line` (the reservation rows reference `orders`); reserve stock; clear the cart and bump its version; record `order_id` on the key row. `Order.id` is a random UUID generated in Java.

**Idempotency (F11, F12).** `idempotency_key(customer_subject, key uuid, request_hash, response_status, order_id, created_at, expires_at, PK (customer_subject, key))`. `request_hash` is SHA-256 over `POST /api/checkout`, `cartVersion` and `expectedTotalMinor` (parsed values). The key row is inserted in the checkout transaction with `ON CONFLICT (customer_subject, key) DO UPDATE ... WHERE idempotency_key.expires_at <= :now` (an expired key is reusable). A failed or crashed checkout therefore leaves no key, and a retry runs again.

- Only 201 results are stored. 409s are recomputed on retry because stock and prices move.
- A live key with another hash gives 422 `idempotency-key-reused`.
- A replay stores no response body: it renders the order's current state as 201 with `Location` and `Idempotency-Replayed: true`. Clients see the current status, not a stale snapshot; tests compare order id and header, not bytes.
- A duplicate arriving while the first is running waits on the uncommitted unique row; that wait is the in-progress handling. If it passes the 3 s `lock_timeout`, the answer is 409 `idempotency-in-progress` with `Retry-After: 1`. The catch is around that statement only and uses `web.LockFailures.isLockTimeout(DataAccessException)` (Spring's lock exception or SQLState `55P03`), which `ApiExceptionHandler` also uses; elsewhere a lock timeout stays 3b's 503.
- Lifetime 24 hours (`shop.checkout.idempotency-ttl`). The key is a declared `@RequestHeader UUID`, so the generated client types it and a non-UUID gives the standard 400.

**State machine as far as 4a goes.** All transitions run under the order row lock in one table-driven method, unit-tested for every state and trigger.

| From | Trigger | To | Stock |
|---|---|---|---|
| (none) | checkout | `PENDING_PAYMENT` | reserve |
| `PENDING_PAYMENT` | customer cancel, `expires_at > now` | `CANCELLED` | release |
| `PENDING_PAYMENT` | expiry job | `EXPIRED` | release |
| `PENDING_PAYMENT`, `expires_at <= now` | cancel (lazy expiry) | `EXPIRED`, answer 409 `order-state` | release |

V7's `CHECK` already lists all six statuses (`PAID`, `REFUND_PENDING`, `REFUNDED` arrive in 4b), and `orders.email` and `orders.late_payment` exist from the start, so 4b only adds.

**Lazy expiry (F13).** The job runs every 30 s, so an order can sit past `expires_at` still reserved. `cancel` of such an order releases it under the order lock, sets `EXPIRED` and answers 409 `order-state`. Reads present a `PENDING_PAYMENT` order with `expires_at <= now` as `EXPIRED` without writing. The web hides `Cancel order` once `expiresAt` has passed.

**Email capture (F14).** `CurrentUser` gains a nullable `verifiedEmail`, set only when the `email_verified` claim is `Boolean.TRUE`, the address is at most 254 characters and has a basic shape. Checkout stores it in `orders.email` (null when the claim is missing or unverified); 4b refreshes it at payment start and sends mail only to it. The address is personal data at rest (R45).

**Request body limit (F15).** A servlet filter in `web`, ordered before Spring Security, caps request bodies on `/api/**` at 16 KiB, except `/api/admin/**` (R25 stays) and, in 4b, the webhook (its own rule). The filter runs at `HIGHEST_PRECEDENCE + 10`, so an oversized body costs no session lookup and an anonymous caller gets 413 or 415 before any 401. Order of checks: a `Content-Length` over the limit gets 413 `tag:shop.dev,2026:body-too-large` first; then a request that has a body (`Content-Length` above 0 or any `Transfer-Encoding`) whose `Content-Type` is not `application/json` or `application/*+json` (missing or malformed included) gets 415 `tag:shop.dev,2026:unsupported-media-type` before anything is read; otherwise the stream is wrapped and a chunked body is refused at 16 KiB + 1 byte. Both refusals send `Connection: close`. The 415 closes a gap: a urlencoded form body is parsed by Tomcat outside the counted stream (Spring Security's CSRF filter falls back to `getParameter("_csrf")`), so `server.tomcat.max-http-form-post-size` is also set to 16KB as defence in depth. The limit applies where a body is read. A body sent to a route that never reads one (`DELETE /api/cart/lines/{slug}`, `POST /api/orders/{id}/cancel`) is not refused for its size when chunked; Tomcat discards it (up to its swallow limit) and the request succeeds, and the application buffers nothing. `BodyLimitIT` covers: a declared length over the limit gets 413 on all four customer unsafe routes (PUT cart line, DELETE cart line, POST checkout, POST cancel); a streamed body over the limit gets 413 on the two routes that read a body (PUT cart line, POST checkout); a body of exactly 16 KiB is accepted in both forms on those two; chunked urlencoded forms get 415, anonymous without a CSRF token and signed in, on all four routes; a missing or malformed `Content-Type` gets 415; `application/json`, with a charset, and `application/merge-patch+json` pass, and a bodyless `DELETE` passes; admin bodies are not capped; an anonymous caller gets the size refusal before any authentication answer; and a small request works after an oversized one.

**Owner-scoped queries (F16).** `GET /api/orders/{id}` and `cancel` (and 4b's `payable`) select `WHERE id = :id AND customer_subject = :sub`, with `FOR UPDATE` where they lock. They never lock by id and compare afterwards, so another customer's order is a 404 that takes no lock on it. Listing is `WHERE customer_subject = :sub`, newest first.

**Reservation foreign key (F17).** `reservation.order_id REFERENCES orders`, although `inventory` owns `reservation` and `order` owns `orders`. This couples two modules at the table level; the code dependency still runs only `order` to `inventory::reservations`. Integrity (no reservation without an order, no order delete while reserved) outweighs module purity, and the alternative is a dangling-reservation check by job.

**Endpoint rules.** All endpoints send `Cache-Control: no-store`, require `hasRole("CUSTOMER")` in the URL rules and `@PreAuthorize` on the services, and need CSRF on unsafe methods; anonymous 401, signed-in without `customer` 403. New problem types, all with `errors`: `cart-changed`, `price-changed`, `out-of-stock`, `cart-full`, `too-many-pending-orders`, `reservation-limit`, `order-state`, `idempotency-in-progress`, `idempotency-key-reused` (422), `body-too-large` (413). Messages never echo input: a type mismatch (a non-numeric `page`, a non-UUID path id or `Idempotency-Key`) gets 400 `validation` with the fixed detail `The request is not valid` and one error naming only the parameter (`has the wrong type`), and `instance` is the route pattern, not the requested path; `ProblemDetailEchoIT` asserts the sent value is absent from the body on the order, checkout and catalog routes. Migrations V6 (cart), V7 (orders, order lines, reservations) and V8 (idempotency) each start with `SET LOCAL lock_timeout = '5s'`.

## Consequences

- Stock is the one scarce resource, and every path that changes `reserved` uses the conditional update and the lock order above. Hot rows can give 503 past `lock_timeout` (R43).
- Reservations are held until paid or cancelled in 4b; 4a orders stay `PENDING_PAYMENT` until cancelled or expired.
- Cancel-and-reorder churn grows `orders`, `order_line`, `reservation` and `idempotency_key` without bound until slice 5c limits and retention (R37). Idempotency keys are purged after 24 hours.
- `available` and `out-of-stock` reveal free stock up to 10 per account (R44).
- The order and per-product caps count only unpaid orders still inside their hold, so an overdue order that the expiry job has not yet released keeps its stock while no longer counting; for up to the job interval (30 s) a customer can reserve on top of it (K10).
- The expiry job is the only bulk path that returns stock held by overdue orders (cancel releases lazily, reads do not write); if it stalls, reserved stock leaks (R50).
- Customer revocation lags up to `revalidate-after` (R42), as for admin writes (R14).
- `FOR SHARE` on products can delay an admin price change under heavy checkout load (R46).
- A seed re-run during a rolling deploy can break the ascending-id rule; local stacks only (R49).
- `shop-users-0.json` gets fixed user ids, so order history survives the kind realm re-import.
- Residual risks are in `docs/threat-model.md` (checkout section).

## Deviations

Where the code differs from the first design or the brief:

- Checkout inserts `orders` and `order_line` before it reserves stock, because `reservation.order_id` references `orders`. The lock order is unchanged (the new row cannot be contended).
- The pending-order and per-product caps are checked before the product lock; product slugs are looked up only when a cap refuses.
- A `PUT` that repeats the current quantity does not bump the cart version.
- `admin` allows `catalog::pricing` (for `Money`), which also exposes `ProductPricing.lockForCheckout` to it (see Named interfaces). The Java `OrderStatus` has the three 4a values; the database `CHECK` lists all six. There is no `consume` or `takeLate` on `StockReservations` yet (4b).
- `OrderStateMachine` maps each (status, trigger) pair to a status; every transition that leaves `PENDING_PAYMENT` releases stock. ADR 0009 replaces this with a table whose rows carry a stock effect.
- The request hash digest takes the algorithm as a parameter so the unreachable error branch can be tested.
- Test-only code: `ReservationPeeker` (the deliberate violation for `ModuleRulesTest`), `Principals`, `Identity.emailVerified`, and `shop.jobs.enabled=false` in `@IntegrationTest`.
- Web: an unpaid order past `expiresAt` is shown as `Expired` and `Cancel order` is hidden (a timer re-renders at expiry); the client keeps the checkout key on 5xx, network error and 413 and drops it on 201, `cart-changed`, `price-changed` and 422; it retries once after one second on `idempotency-in-progress` with the same key. The `Cart` link shows only for the `customer` role. The order view shows the snapshot unit price and line total.
- Web: while a cart change is pending, the quantity select and `Remove` button are `aria-disabled` and input is ignored (not `disabled`, so focus is not lost); after `Remove` succeeds focus moves to the `Cart` heading.
- Both Keycloak test users have fixed ids in `shop-users-0.json` so order history survives a realm re-import.
