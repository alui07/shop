# ADR 0010: Observability

Status: accepted (slice 5a, 2026-11-21). Checked against the implemented code; the Deviations section lists where it differs from the brief.

## Context

Slices 1 to 4 left the API with Micrometer and an OpenTelemetry starter whose three OTLP exports were switched off, ECS JSON logs on stdout and no place to look at any of it. Slice 5a adds export, a collector and backends in both stacks, one dashboard, and the metrics that ADR 0009 and the threat model (R50, R53) said were missing. It also installs metrics-server, an HPA and PodDisruptionBudgets (ADR 0005). Alert rules are not part of it: they move to slice 5c (D40).

## Decisions

**Boot's OpenTelemetry support, not the Java agent.** `spring-boot-starter-opentelemetry` was already a dependency. The agent would duplicate Micrometer's instrumentation and need a JVM flag in every stack. Traces use Micrometer Tracing with the OTel bridge, metrics Micrometer's OTLP registry, logs `opentelemetry-logback-appender-1.0` (pinned `2.28.1-alpha`: the newest release whose POM declares the `opentelemetry-api` that Boot 4.1.2 manages, 1.62.0; Renovate groups `io.opentelemetry.instrumentation:*` with Boot so they move together). The appender brings no second `jackson-databind`.

**Export is off by default and switched on by environment only.** `application.yaml` keeps the three `enabled: false` keys, so `make test`, `make e2e` and every stack without a collector export nothing. The `obs` kustomize overlay and `make dev OBS=1` set `MANAGEMENT_TRACING_EXPORT_OTLP_ENABLED`, `MANAGEMENT_OTLP_METRICS_EXPORT_ENABLED` and `MANAGEMENT_LOGGING_EXPORT_OTLP_ENABLED` to `true`.

**One endpoint variable, `OTEL_EXPORTER_OTLP_ENDPOINT`.** `MANAGEMENT_OPENTELEMETRY_OTLP_ENDPOINT` does not exist in Boot 4.1.2. Boot's environment post-processor maps `OTEL_EXPORTER_OTLP_ENDPOINT` to the three per-signal properties (appending `v1/traces`, `v1/metrics`, `v1/logs`) and its property source outranks `application.yaml` and every `MANAGEMENT_*` variable. `OTEL_SERVICE_NAME=shop-api` and `OTEL_RESOURCE_ATTRIBUTES=deployment.environment=<stack>,service.instance.id=<pod>` (the downward-API pod name in kind) give the resource. No stack sets another `OTEL_*` variable; in particular `OTEL_TRACES_SAMPLER_ARG` would override Boot's sampling property. Sampling stays at 1.0. `TelemetryExportIT` proves the mapping: the failsafe plugin sets the three `OTEL_*` variables for the integration-test JVM (Boot reads them from `System.getenv` only), a `com.sun.net.httpserver` stub receives `/v1/traces`, `/v1/metrics` and `/v1/logs`, and the service name and `deployment.environment` appear in all three.

**Why a log appender.** Boot provides the `SdkLoggerProvider` but no bridge from Logback, so without one the OTLP log export is empty. `OtlpLogAppenderConfiguration` is conditional on `management.logging.export.otlp.enabled`. It creates, names (`OTLP`), starts and attaches the `OpenTelemetryAppender` to the root logger, and on context close detaches and stops it. `OpenTelemetryAppender.install(...)` is not used: it only wires appenders that already exist, and the root logger is JVM-global across test contexts. stdout stays ECS JSON, so `kubectl logs` and the `traceId` field are unchanged. Log lines exported over OTLP carry the trace and span id, which Grafana uses to jump between a trace and its logs.

**Metric unit and step.** Boot defaults to milliseconds and a one-minute step. Both stacks set `MANAGEMENT_OTLP_METRICS_EXPORT_BASE_TIME_UNIT=seconds` and `MANAGEMENT_OTLP_METRICS_EXPORT_STEP=10s`, so Prometheus sees `http_server_requests_seconds_bucket` and a panel refreshes within a few seconds of a request. `application.yaml` sets `management.metrics.distribution.percentiles-histogram.http.server.requests: true`, so `http.server.requests` is exported with bucket counts; without it Micrometer sends only count and sum, Prometheus gets just the `+Inf` bucket and `histogram_quantile` returns NaN. `check-metrics.sh` therefore requires a bucket with a finite `le`.

**Metrics that answer the threat model.** `shop.events.dead_letter.rows` (`shop_events_dead_letter_rows`) is a gauge over `event_publication_dead_letter` (R53), cached for one export step so a scrape storm cannot query the database more often than the step; the value can lag up to two steps. `shop.reservations.released.units` (`shop_reservations_released_units_total`) counts units the expiry job returns, incremented after each batch commits, so a rolled-back batch does not count (R50). Boot's `tasks.scheduled.execution` timer shows the job runs. Both new names were chosen here; `check-metrics.sh` confirms the Prometheus spelling in both stacks.

**R48: the fake payment token is masked in exported spans.** `FakePspTokenMasking` is an `ObservationFilter` that rewrites the `http.url` high-cardinality value to `/api/fake-psp/payments/{token}` before the span is exported. It canonicalises the raw request URI with the same helper as `ApiRequestFilter` (percent-decoding, `;` path parameters dropped, repeated slashes and dot segments collapsed), so the encoded (`%70ayments`), matrix-parameter, double-slash and `/./` spellings are masked too, including on the 400 spans that the firewall rejects (the observation filter runs before it); a path that cannot be decoded gets a fixed placeholder. `FakePspTokenMaskingTest` covers the plain, `/complete` and those spellings, and `TelemetryExportIT` asserts the masked URL is in the exported traces and that the token appears nowhere in the traces request body. Removing the `@Component` makes the IT fail. The request log already masks the token (ADR 0009).

**Push, one OTLP endpoint everywhere; the stacks differ below the collector.** The API never talks to a backend directly, so its configuration is the same in both.

- Compose: `grafana/otel-lgtm` (pinned in `deploy/versions.mk`), service `otel-lgtm` under compose profile `obs`, OTLP/HTTP 4318 on the compose network only, Grafana on `127.0.0.1:3000` with anonymous Viewer (the image default is Admin); Viewers cannot use Explore, so sign in as `admin` for trace and log navigation (otel-lgtm's built-in login, local only). `make dev OBS=1` starts the profile and sets the export variables; no other target does. `make down` and `make clean` pass the profile so the container is removed.
- kind: separate charts as the master plan says (D36), in namespace `obs`: OpenTelemetry Collector (the `otelcol-k8s` distribution, image pinned by digest, OTLP/HTTP in; traces to Tempo, logs to Loki's native `/otlp`, metrics to Prometheus's OTLP receiver), Prometheus (server only, `emptyDir`, 6 h retention, cAdvisor scrape kept for CPU throttling), Loki (single binary, filesystem), Tempo (single binary, local storage, 6 h retention) and Grafana. Chart versions are in `deploy/versions.mk`; Grafana and Tempo come from the `grafana-community` repository because the `grafana/grafana` and `grafana/tempo` charts are deprecated. `make obs-up` installs them with the idempotent Helm macro of ADR 0005; `make obs-down` removes them. The alternative, `otel-lgtm` in the cluster too, would use about half the memory but is not a production shape.
- `make deploy OVERLAY=obs` applies the `obs` overlay (`local` plus the `otel` component: export variables, the downward-API pod name and the NetworkPolicy `api-to-otel-collector`, egress to the collector in `obs` on TCP 4318). `deploy` defaults to `OVERLAY=local`, which exports nothing.

**Dashboard as code, shared by both stacks.** `deploy/observability/dashboards/shop-api.json` is the only dashboard file. Compose mounts it into `otel-lgtm`'s provisioning directory; `obs-up` creates the ConfigMap `shop-dashboards` from it and Grafana loads it through `dashboardsConfigMaps`, with no sidecar container (saves memory and an image). Panels: replicas (`count(last_over_time(target_info{job="shop-api"}[30s]))`, since OTLP ingestion never marks series of gone pods stale), request rate, 5xx ratio, p50, p95 and p99, Hikari active, idle, pending and max, executor active and queued, dead-letter rows, released units and expiry job runs, JVM heap, CPU, a logs panel and a trace search. There is no cache panel yet (the cache is slice 5b). The Prometheus datasource is chosen by type, so no UID is hard-coded.

**`check-metrics.sh` and `obs-check`.** `deploy/observability/check-metrics.sh` is the single list of metric names the dashboard queries and fails when one is missing, retrying up to 150 s for export steps and the first scheduled-task run. `make obs-check` runs it against the kind Prometheus through the API server's service proxy (it also requires `container_cpu_cfs_throttled_periods_total`); `make obs-check-dev` runs it against `otel-lgtm` on the compose network. OTLP-to-Prometheus name translation is the likely source of a mismatch, so this is the guard.

**Grafana on the existing front door.** `http://grafana.localhost:8088` in kind. The Gateway's `http` listener `allowedRoutes` selects namespaces `shop` and `obs` (`idp` stays `Same`), and `obs-up` applies an HTTPRoute `grafana` in `obs` with host `grafana.localhost` and a `parentRef` to Gateway `shop`. `http://localhost:8088/` still serves the shop. No new host port, no kind mapping, no cluster recreate, no database wipe (this replaced the planned NodePort mapping, D33). Grafana's `root_url` is that address; anonymous Viewer is on (Viewers cannot use Explore or the trace-to-logs links; sign in as `admin`), and the admin password is `GRAFANA_ADMIN_PASSWORD` in `.cache/secrets/shop.env` (Secret `grafana-admin` in `obs`). Compose Grafana is `http://localhost:3000`.

**Footprint (observed on the 15.6 GiB, 12 CPU host, 2026-11-21).** obs memory requests total 816 MiB; `obs-up` fails above 1 GiB or when a container has no request (`obs-memory`). Limits are about 1.9 GiB (Grafana 512 Mi: Grafana 13 was OOM-killed at start with 256 Mi). `kubectl top`, idle, two API pods: Grafana 332 MiB, Loki 60, Prometheus 122, Tempo 40, collector 29; API 259 to 267 MiB each. Compose `docker stats`: `otel-lgtm` 1.07 GiB, API 462 MiB. The kind node used 3.7 GiB (22%) before obs.

**NetworkPolicy.** `default-deny` covers egress in `shop`, so the `otel` component adds the one allow above. `obs` gets no policies in this slice (R55). metrics-server scrapes kubelets, not pods, so `shop` needs no change for it.

## Deviations from the brief

- Grafana loads its dashboard from a mounted ConfigMap, not a sidecar (above); `obs-up` creates the ConfigMap.
- Grafana's memory limit is 512 Mi, not 256 Mi.
- Loki needs an `emptyDir` at `/var/loki`; Tempo keeps the chart's default Jaeger receivers because the chart template fails when they are nulled; neither enforces retention beyond the `emptyDir` lifetime (Tempo 6 h).
- The Loki chart's default image is 3.6.11 (the brief named 3.6.18); charts keep their own image tags, as Envoy Gateway and CNPG do (digests in slice 6).
- The gauge cache uses the export step as its TTL, and the release counter counts in the job after the batch commit, not inside the transaction.
- Only the three `OTEL_*` variables above are set, with the `MANAGEMENT_*` flags, unit and step; the check script and two helper scripts (`hpa-report.sh`, `wait-api-replicas.sh`) live under `deploy/`.

## Consequences

- One dashboard, one set of metric names and one export configuration serve compose and kind; a renamed metric fails `obs-check` instead of leaving an empty panel.
- Telemetry costs about 0.8 GiB of requests in kind and 1.1 GiB in compose, and only when asked for. Without `OVERLAY=obs` or `OBS=1` the API logs no export errors; with the `obs` overlay applied and `obs` uninstalled, it logs export failures until the stack returns or `make deploy` (local overlay, which removes the obs-only NetworkPolicy) restores `local` (the exporters drop data and retry; requests are unaffected).
- A client-supplied `traceparent` sets the trace id of that request (R57), and `obs` has no NetworkPolicies and an anonymous Viewer (R55, R56): both are in the threat model.
- Traces, metrics and logs of two API replicas are separate series by `service.instance.id`; the replica panel counts them.
- Not verified here: that the token is absent from Tempo's stored spans (only the OTLP request body is asserted) and CI behaviour of metrics-server on cgroup v2. Alert rules and Alertmanager are slice 5c; load tests and the cache panel are slice 5b.
