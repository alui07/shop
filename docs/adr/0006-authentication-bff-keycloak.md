# ADR 0006: Authentication with a backend-for-frontend and Keycloak

Status: accepted for slice 3a. Deviations found during implementation are in "Deviations from the design" below.

## Context

Slice 3 adds sign-in, roles and an admin area. The SPA must never hold tokens, and the same flow has to work in three stacks: `make dev` (`http://localhost:5173`), the compose e2e stack and kind (both `http://localhost:8088`). Slice 3 ships as two PRs: 3a (this ADR: sign-in, sessions, CSRF, both logouts, revalidation, `/api/me`, deny-by-default, a read-only admin product list) and 3b (admin writes, stock, audit; ADR 0007).

## Decisions

**Backend-for-frontend (BFF) in the API, not tokens in the SPA.** The API is the OIDC client (authorization code with PKCE S256, confidential client). Access, refresh and ID tokens stay server-side in the session. The browser holds only an HttpOnly session cookie, so an XSS cannot steal a token. The cost is server-side session state (Valkey) and CSRF protection.

**Keycloak 26.8 on its own origin.** `http://localhost:8180` in dev, `http://localhost:8089` in e2e and kind. The app's CSP stays `'self'`, and a script injected into one origin cannot read the other's DOM. Cookies are not port-scoped, so `__Host-SESSION` and `__Host-XSRF-TOKEN` set on `localhost:8088` are also sent to `localhost:8089`, and the XSRF cookie is readable by scripts there. Cookie separation only exists with distinct hostnames (the cloud setup). Locally this is a documented residual risk (threat model).

**No OIDC discovery; public and internal endpoints are split.** Keycloak stamps `iss` from its public hostname, which the API container cannot reach. `ShopAuthProperties` (`shop.auth.*`, validated) builds the `ClientRegistration` in code. The issuer and the authorization and end-session endpoints use the public URL (the browser follows them); the token and JWKS endpoints use the internal `http://keycloak:8080/realms/shop`. Setting `issuer-uri` is forbidden because it triggers discovery against the browser URL. Roles arrive in the ID token (claim `roles`, ID token only), so there is no userinfo call. Authorisation and auditing use `sub`; `name` and `email` are display data the user can edit.

**No host-derived URLs.** The redirect URI, post-logout URI and login success and failure targets are built from `SHOP_PUBLIC_ORIGIN`. Security decisions no longer depend on `Host` or `X-Forwarded-*` (the open question from ADR 0005). Gateways set or clear forwarded headers; `Location` headers come from the path or the configured origin. Keycloak ignores forwarded headers (`KC_PROXY_HEADERS` unset).

**Only `/login/oauth2/` is routed to the API, not `/login`.** The gateways send `/oauth2/`, `/login/oauth2/`, exact `/logout` and `/api` to the API. `/login` stays an SPA path. This deviates deliberately from the master plan's Routing row, which listed `/login`. `/logout/connect/back-channel/...` is not routed; Keycloak calls `api:8080` directly. Publicly routed Keycloak paths are `/realms/shop/` and `/resources/` only; `/admin/`, `/realms/master/`, client registration and the management port are not.

**Cookies and CSRF.** `__Host-SESSION`: `Secure` (forced, since every hop is http), HttpOnly, `SameSite=Lax`, `Path=/`, no `Domain`. The `__Host-` prefix blocks cookie tossing from sibling subdomains in the cloud. `localhost:8088` and `localhost:8089` are the same site, so Lax holds across the redirects. CSRF uses Spring Security's SPA pattern (`csrf.spa()`) with a double-submit cookie `__Host-XSRF-TOKEN` (`SameSite=Strict`, readable by script) and header `X-XSRF-TOKEN`. Unsafe requests without a valid token get 403 problem+json, including anonymous ones. Login and logout clear the token; the SPA reads the cookie fresh before every unsafe request.

**Sessions in Valkey, no anonymous sessions.** Spring Session on Valkey (non-indexed repository). Only `/oauth2/authorization/**` creates a session before login; it lives 5 minutes, and the success handler sets 30 minutes. The request cache is a `NullRequestCache`, so anonymous 401, 403 and 404 responses never set a cookie. Timeouts: 30 minutes idle (Spring Session) and 8 hours absolute (`AbsoluteSessionTimeoutFilter`, which also clears the context so the expiring request runs anonymously; a session without `authenticatedAt` counts as expired). The session id rotates at login. Valkey runs with a password, no persistence and `--maxmemory 96mb --maxmemory-policy volatile-lru`; a restart signs everyone out.

**Session serialisation: JDK serialisation with an allowlist.** An `ObjectInputFilter` (JEP 290) allows the `java.*` value types the session uses, `org.springframework.security.**`, `org.springframework.session.**` and `dev.shop.api.**`, rejects everything else and limits depth to 20. A `SessionRepository` decorator catches `SerializationException` only, deletes the session and returns null, so an undeserialisable session (for example after a Spring Security upgrade) is "signed out", not a 500. JSON serialisation can wait for a real need.

**Revalidation with Keycloak.** Keycloak's SSO idle timeout (30 minutes) would otherwise expire while the app session lives on, and back-channel logout and role changes would stop reaching the app. If the last check is older than `shop.auth.revalidate-after` (5 minutes, injectable `Clock`), the next authenticated request refreshes through `IdentityRefresher` (the refresh-token client called directly; see deviations), re-maps roles from the new ID token, rebuilds the `Authentication` and records `lastRevalidatedAt`. `invalid_grant` or a disabled user invalidates the session (fail closed). If Keycloak is unreachable or answers 5xx, the session continues until `revalidate-grace` (15 minutes since the last success), then fails closed. A Valkey lock `shop:revalidate:{sessionId}` (SET NX, 10 s TTL) gives single flight; a request that loses the race proceeds with the current authentication. `revokeRefreshToken: true` stays on. A demoted admin therefore loses access within about 5 minutes. The realm keeps `ssoSessionIdleTimeout: 1800` and `ssoSessionMaxLifespan: 28800` and leaves client-session timeouts unset.

**RP-initiated logout.** `POST /logout` (CSRF required) invalidates the session, clears the cookie and answers `200 {"redirectUrl": ...}` with Keycloak's end-session URL (`id_token_hint`, `post_logout_redirect_uri`, `client_id`). A cross-origin redirect cannot be followed by `fetch`, and a form post would need Keycloak in `form-action`. The SPA then navigates with `window.location.assign`. `id_token_hint` and expiry: confirmed (C23) that Keycloak 26.8 accepts an expired ID token as hint, so there is no fallback without the hint. The compose e2e realm uses a 10 second access-token lifespan (`SHOP_ACCESS_TOKEN_LIFESPAN`) so `logout.spec.ts` can sign out with an expired token; that spec skips on kind, where it is a manual check.

**Back-channel logout with a Valkey registry.** Spring validates the logout token (signature, `iss`, `aud`, `events`, no `nonce`). Spring's default handler re-POSTs `/logout` to itself with a `JSESSIONID` cookie, which cannot work with `__Host-SESSION` behind our proxies, so a custom handler deletes sessions by id through `SessionRepository`. `ValkeyOidcSessionRegistry` replaces the in-memory registry (it must work with several replicas in slice 5). Contract: it stores only `{sessionId, sub, sid, iss}`, never the CSRF token, cookie or ID token. Tokens match on `sid` when present, and the stored `sub` and `iss` must match too; `sub` alone when `sid` is absent. Mappings are removed on RP-initiated logout and on the absolute timeout; a TTL equal to the absolute timeout covers the rest. We do not rely on `SessionDestroyedEvent`. The registry holds the post-rotation session id, which `BackChannelLogoutIT` proves, so no fallback in the login success handler is needed.

**Failure modes.** A filter ordered before `SessionRepositoryFilter` maps Valkey connection failures and command timeouts to 503 problem+json (`spring.data.redis` connect and command timeouts 2 s). A public GET without a session cookie never touches Valkey and stays 200 during a Valkey outage; a request carrying a cookie gets 503 (accepted). Readiness stays `readinessState,db`, so the catalog keeps serving. The token and JWKS `RestClient`s use 2 s connect and 5 s read timeouts. With Keycloak down, the catalog works, sign-in shows the failure page, and existing sessions continue until revalidation grace ends. Method-security denials map to 403 and 401 Problem Details rather than 500.

**Keycloak image, realm as code, and Recreate.** `deploy/keycloak/Dockerfile` builds a pre-optimised image (`kc.sh build`, `KC_DB=postgres`) so a read-only root filesystem works. `shop-realm.json` is the single realm definition, with `${VAR}` placeholders resolved from the environment at import: self-registration off, brute-force protection on, `sslRequired: external` (plain http from localhost and private addresses only), confidential client `shop-api` with an exact redirect URI, PKCE S256, no implicit, direct-grant, service-account, device or token-exchange flows. Test users live only in a local overlay file, never in the image. In kind, Keycloak uses its own CNPG cluster and an init container runs `import --override true` on every pod start, so the repo stays the source of truth. Keycloak needs all nodes stopped for an override import, so the Deployment uses `strategy: Recreate`. Consequence: each Keycloak restart re-creates the realm, with new signing keys and all SSO sessions lost. App sessions still end at sign-out because the app invalidates before redirecting, and the SPA tolerates Keycloak's error page at the end of logout. Compose Keycloak databases are tmpfs, so the realm is imported fresh on every start. Image updates come through Renovate (scoped rule, `timestamp-optional`, in the `cluster platform` group).

**Secrets.** Generated per checkout by `make secrets` into `.cache/secrets/shop.env` (mode 600, never printed, never committed): client secret, Valkey password, Keycloak DB and bootstrap-admin passwords, test-user passwords. The target is idempotent, adds missing keys and fails on values shorter than 32 characters. Compose passes `--env-file` and each service maps only the variables it needs (`VAR: ${VAR:?}`), with no `env_file`; the e2e runner gets only the two test passwords. Keycloak entrypoints fail fast when an imported placeholder is unset, instead of importing the literal `${...}`. In kind, `make deploy` creates the Secrets `shop-auth`, `valkey-auth` and `keycloak-test-users` outside Kustomize. `ShopAuthProperties` redacts the client secret in `toString`. This avoids widening the Postgres-password exception in `CLAUDE.md`.

**Image scanning.** `scan-keycloak` fails on fixable CRITICAL findings and reports HIGH (JSON and SARIF under `build/reports/trivy/`); exceptions need an `expired_at` in `deploy/keycloak/.trivyignore.yaml`. HIGH is gated in slice 6. The image is third-party code we only re-optimise.

**Deny by default.** One filter chain covers the app and management ports. Public: `GET /api/status`, `/api/categories`, `/api/products/**`, `/api/me`, the error dispatch and health probes. `/api/admin/**` needs `ADMIN`, with `@PreAuthorize` as defence in depth. Everything else is denied: unknown `/api` paths give 401 to anonymous and 403 to authenticated callers (previously 404). `/v3/api-docs/**` is permitted only when springdoc is enabled (`dev` profile and the contract test).

## Consequences

- The SPA never sees a token. Admin access depends on a Valkey session, so Valkey is a hard dependency for signed-in users (not for the public catalog).
- A Valkey restart signs everyone out; a Keycloak restart in kind re-creates the realm and drops SSO sessions. App sessions are not ended early by Keycloak SSO expiry, because revalidation refreshes them every 5 minutes and fails closed on rejection.
- Role changes and disabled users take effect within the revalidation interval, not instantly (back-channel logout is instant when Keycloak delivers it).
- Three stacks need three Keycloak configurations of the same issuer logic; `OidcLoginIT` and `keycloak.spec.ts` guard the consistency.
- Footprint grows: Keycloak needs 600 to 750 MB per instance.
- Local limits: `sslRequired: external`, no TLS or HSTS (cloud guide sets `all`), cookie separation only with distinct hostnames, no rate limiting until slice 5c. See `docs/threat-model.md`.
- Verified: `id_token_hint` with an expired token (compose e2e only; on kind revalidation refreshes the ID token before logout, so an expired hint is rare there and no manual check exists), the post-rotation id in the registry (`BackChannelLogoutIT`), the read-only-root Keycloak in kind (`cluster-e2e`).
- Footprint measured: the kind node uses about 3.5 GiB with everything running (was 2.5). Keycloak in kind needs about 89 s for the realm import and is ready 2 to 3 minutes after its pod starts. An existing cluster needs `make cluster-down cluster-up` for the 8089 port mapping.
- Valkey's image is pinned only in `deploy/versions.mk`. A secrets hash annotation restarts `api` and `keycloak` in kind when `.cache/secrets/shop.env` changes.
- Gateways: Envoy and the compose nginx access logs strip query strings on all paths, `X-Forwarded-Host` is removed on the shop and Keycloak routes, and the `ClientTrafficPolicy` sets `numTrustedHops: 0`. nginx's error log may still print a URL with a query in a buffering warning (residual).

## Deviations from the design

1. **Revalidation calls the refresh-token client directly** (`IdentityRefresher`) instead of `OAuth2AuthorizedClientManager`, which discards the ID token and refreshes only expired access tokens. The lock, the 15-minute grace and fail-closed behaviour are as specified.
2. **JWKS timeouts apply to ID-token decoding only.** The back-channel logout-token decoder is built inside Spring's `OidcLogoutConfigurer` and keeps Spring's default timeouts.
3. **The login callback response already sets a fresh `__Host-XSRF-TOKEN`.**
4. **Registry cleanup happens in `SafeSessionRepository.deleteById`**, not in the handlers. That covers logout, the absolute timeout and revalidation rejection, and the id it holds is the post-rotation one.
5. **On the management port `/actuator/env` and `/actuator/info` now answer 401** (deny-by-default); only health stays reachable.
6. **A `RequestRejectedHandler` returns 400 problem+json** for paths the Spring firewall rejects, instead of a bare container error page.
7. **Spring accepts back-channel logout tokens with a future `iat`**, and a token without `events` gives a 500 with the session left alive. Both are recorded as residual risks in the threat model (R17, R18).
8. **The revalidation lock is never deleted.** It expires after 20 s, which covers the refresh call and the session commit.
9. **A JWKS fetch error during revalidation uses the grace period**, like any other Keycloak failure. A refresh response without an ID token counts as Keycloak unavailable.
10. **Login start and login failure only affect unauthenticated sessions**, so they cannot overwrite a signed-in session. A refused revalidation also clears the CSRF token.
11. **The 503 for an unavailable session store is declared in the OpenAPI document.**
