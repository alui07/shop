# ADR 0013: Client IP, rate limits and request bounds

Status: accepted (slice 5c, 2026-11-25). Checked against the implemented code and manifests; the Deviations section lists where it differs from the brief. Threat model rows R1 to R3, R20, R24, R25, R34, R36, R37, R40, R52 and the residuals R65 to R77 are in `docs/threat-model.md`.

## Context

Until slice 5c nothing limited how often a client could call the shop. The threat model carried this as R1 (credential guessing, API abuse), R2 (pre-login session flooding), R3 (Keycloak lockout), R24 (admin write growth), R36 and R37 (free accounts, order churn), R40 (the public webhook) and R52 (registration spam); R25 (unbounded admin bodies) and R34 (no `statement_timeout`) were open too, and R20 said the client address from `X-Forwarded-For` could not be trusted, which any per-IP limit needs first. Slice 5c fixes these with the smallest set of moving parts, and adds the alert rules that slice 5a left out (ADR 0010).

## Decisions

**Client IP first (R20).** Envoy replaces the client address, it never appends to it. The `ClientTrafficPolicy` `shop` (`deploy/k8s/base/gateway.yaml`) removes `X-Forwarded-For`, `X-Real-IP`, `Forwarded`, `x-envoy-original-path`, `X-Forwarded-Port` and `X-Forwarded-Prefix` from every request in `earlyRequestHeaders`, before routing and before Envoy's own header handling, and Envoy then appends the TCP peer (`numTrustedHops: 0`), so the API sees exactly one entry. The policy targets the Gateway, so the `idp` and `loadtest` listeners are covered. `disableXForwardedForAppend` is not the fix: it does not sanitise an incoming header. In kind the API sets `SERVER_TOMCAT_REMOTEIP_INTERNAL_PROXIES=10.244.0.0/16` (the pod CIDR; the `api-from-gateway` NetworkPolicy already lets only Envoy pods reach port 8080), so Tomcat's `RemoteIpValve` trusts the gateway and nothing else. The compose e2e nginx replaces the header itself and keeps Boot's default. `application.yaml` has a comment naming both controls. `RemoteIpValveTest` runs Boot's customizer on a real Tomcat valve (`"1.2.3.4, 172.18.0.5"` from `10.244.0.9` resolves to `172.18.0.5`, the CIDR is accepted, loopback is not trusted) and `ClientAddressIT` shows a loopback peer cannot spoof its address. The Envoy access log uses `%REQ_WITHOUT_QUERY(:PATH)%`, which is the real path, so a forged `x-envoy-original-path` cannot rewrite what is logged.

**Two layers, keyed by what each knows (D42).** Envoy limits per client IP and the API limits per account (`sub`).

- Envoy sees the true peer without trusting any header, is the only layer in front of Keycloak (R3, R52) and runs before the webhook's HMAC (R40). Its limits are local to each Envoy replica (`BackendTrafficPolicy`, `rateLimit.type: Local`, `sourceCIDR: {type: Distinct, value: 0.0.0.0/0}`, so one bucket per source address per rule, with an LRU of 10 000 addresses per rule and replica).
- The API is the only layer that knows the account, and it runs in every stack, compose included. Buckets live in Valkey and are shared by all API pods.

Alternatives not taken: everything in the API (no Keycloak coverage, and per-IP needs R20 to be perfect); Envoy global limits (a ratelimit Deployment, a Redis, NetworkPolicies and memory, for exact cross-replica IP limits that one replica already gives locally).

**Envoy rules, per IP (`deploy/k8s/base/limits.yaml`).** Every path selector is `PathPrefix`: Envoy matches `:path` with the query string, so `Exact /api/checkout` would let `?x=1` escape (the design challenge's one blocker, C5c-1). No `RegularExpression` (`make/forbid-loadtest-env.awk`, run by `make k8s-loadtest-guard` over the non-loadtest renders, rejects it).

| Policy | Rule | Limit per IP |
|---|---|---|
| `shop` | any method, `/api` | 200 per second |
| `shop` | any method, `/oauth2/` | 200 per second |
| `shop` | any method, `/login/oauth2/` | 200 per second |
| `shop` | any method, `/logout` | 200 per second |
| `shop` | any method, `/oauth2/authorization/` (login start; HEAD and OPTIONS also create a pre-login session, R2) | 125 per minute |
| `shop` | `POST`, `/api/checkout` (R36) | 30 per minute |
| `shop` | `POST`, `/api/payments/webhook` (R40) | 20 per second |
| `keycloak` | any request | 150 per second |
| `keycloak` | `POST`, `/realms/shop/login-actions/` (password guessing R3, registration R52) | 125 per minute |

The flood rule covers only the API prefixes: static web assets are not counted (400 parallel `GET /` were all 200 in the live check; 400 parallel `GET /api/status` gave 249 x 429). The specific rules and the flood rules coexist. Both policies also set a 64 KiB request buffer (below) and `responseOverride` bodies for 429 and 413. `HTTPRoute` `loadtest` has no policy (the mint limiter, ADR 0011), nor does Grafana's route. IPv6 would need a `::/0` selector per rule; kind is IPv4 and none is added.

**API rules, per account (`RateLimitRule`).** Keys are `shop:rate:<rule>:<sub>` (no IP, no email), `sub` from the `OidcUser`, minted load-test sessions included. Refill is greedy, and a rule with two bandwidths enforces both. "Unsafe" means not GET, HEAD, OPTIONS or TRACE.

| Rule | Requests | Per account |
|---|---|---|
| `checkout` | `POST /api/checkout` | 30 per minute and 100 per hour (R36, R37) |
| `order-actions` | `POST /api/orders/{id}/payment`, `POST /api/orders/{id}/cancel` | 30 per minute |
| `cart-writes` | unsafe methods on `/api/cart/**` | 60 per minute |
| `admin-writes` | unsafe methods on `/api/admin/**` | 60 per minute and 600 per hour (R24) |

`RateLimitFilter` sits after `AuthorizationFilter`, so it sees the final principal, runs after CSRF and the role rules, and counts only requests that would be served: anonymous, CSRF-less and wrong-role requests are refused first and create no key. It matches with the same `PathPatternRequestMatcher` the security chain uses, so a path spelling the chain treats as another route is not counted as this one. The answer is 429 `application/problem+json`, type `tag:shop.dev,2026:rate-limited`, fixed detail `Too many requests; try again later`, `errors: []`, `Retry-After` in whole seconds rounded up from the bucket's wait (minimum 1), and the same security headers as every API response (`Cache-Control: no-store`). There are no `X-RateLimit-*` headers (the CTP sets `disableRateLimitHeaders: true`, so Envoy sends none either). Every operation a rule covers declares a 429 with its `Retry-After` header in the OpenAPI contract. The first rejection per rule per minute logs one INFO line with the rule name and route patterns only; `shop.rate_limit.rejected{rule}` counts the rest.

**Bucket4j on Lettuce, with its own client.** `bucket4j_jdk17-core` and `bucket4j_jdk17-lettuce` 8.22.0 (one `bucket4j.version` property; 8.23.0 was under the 7-day gate). The Lettuce module declares `lettuce-core` as `provided`, so Boot's Lettuce 7.5.2 is used; `dependency:tree` shows no second Jackson. Its compatibility with Lettuce 7 is proved by `RateLimitIT` against the real Valkey image. The limiter has its own `RedisClient` built from Boot's `RedisConnectionDetails` (the URI and options are never logged; TLS follows Boot's SSL settings: `spring.data.redis.ssl.enabled` (Boot then supplies the system default bundle) or `spring.data.redis.ssl.bundle`. A `rediss://` URL without those settings leaves the limiter in plain text, so its commands fail and it fails open permanently; set `ssl.enabled` with a TLS store. Only a standalone Valkey is supported: sentinel, cluster and master/replica make the limiter bean fail and the API refuse to start, never fail open), separate from the session store's, so its short timeouts cannot affect sessions: command timeout 500 ms, connect timeout 500 ms, `REJECT_COMMANDS` while disconnected, Bucket4j request timeout 1 s. The connection is created lazily on first use and never at startup or readiness (5b R1: no new Valkey startup dependency). Keys expire at the time the bucket needs to refill plus 10 s, so every key carries a TTL and stays evictable under `volatile-lru`; an evicted bucket starts full.

**Changing a rule reaches existing buckets (C32, deviates from A4).** Buckets use implicit configuration replacement with `TokensInheritanceStrategy.PROPORTIONALLY`, so a bucket created at the old capacity follows a later one. `RateLimitIT.aBucketCreatedAtTheOldCapacityFollowsTheNewConfiguration` creates an `admin-writes` bucket from a pod with scale 1 (60 a minute) and then drains it through a pod with scale 2 and a higher version: it allows about 120 requests, not 60, so the stored configuration was replaced. Bucket4j replaces a stored configuration only when the offered version is higher than the stored one, so a hash of the values (A4) would work about half the time. The version is the pod start time in epoch milliseconds: the newest pod always wins, and pods with an equal value replace a bucket with an equal one.

**Fail open (D43).** If the limiter's Valkey path fails, the request goes through unlimited. Only `RedisException`, `BucketExecutionException` and `TimeoutException` anywhere in the cause chain count as a backend failure; anything else, including a classpath mismatch, propagates. After a failed connect (D53, as the brief said) the limiter is skipped for 5 s on the application clock, so an unreachable Valkey costs one 500 ms connect timeout per 5 s, not one per request, and recovery needs those 5 s to pass. A command timeout or a Bucket4j request timeout (for example CAS contention on one key) fails open for that request only and starts no backoff, so a signed-in client cannot switch off every account's limit on a pod by causing timeouts; the timed-out request itself is not counted against the bucket, so an account flooding its own key can exceed its limit by those requests, bounded by the per-IP Envoy limits and about 1 s of thread time each (threat model R68); Lettuce's `REJECT_COMMANDS` already makes a disconnected connection fail fast. Each bypassed request increments `shop.rate_limit.backend.failures`, and a WARN naming only the exception class is logged at most once a minute. Signed-in requests already get 503 without Valkey (ADR 0006), so fail-open matters for blips and for the limiter's own connection; Envoy's per-IP limits and the K10 caps keep working. The alert `ShopRateLimitBackendFailing` (below) is the signal. Alternatives not taken: fail closed (a Valkey blip becomes a write outage) and an in-memory fallback (per-pod limits, more code). `RateLimitOutageIT` pauses the limiter's Valkey container (the suite's shared session Valkey stays up). With the connection already open, each signed-in write succeeds within 1.5 s, the counter rises once per write, there is one WARN, and the limiter works again as soon as the container resumes (no 5 s skip after a timeout). With a fresh backend whose first connect fails, the next call is skipped without a connect attempt until the 5 s skip ends on a mutable clock, then the store is used again. A second application context, which also uses that container for its sessions, starts and serves with it paused.

**Headroom rule.** Each limit must be at least 3 times the peak the e2e suites and k6 produce from their single source address, measured per second for second rules, per minute for minute rules, and over three back-to-back runs for hourly bandwidths. A limit that is too low is raised here, never worked around by changing the test. `rate-limit.spec.ts` is the only test that is meant to hit a limit, and it uses a freshly registered account no other spec uses. The shared `@IntegrationTest` context sets `shop.rate-limit.enabled=false` (many ITs check out repeatedly as one subject); only `RateLimitIT` and `RateLimitOutageIT` run the limiter.

**Load tests raise every limit (D44).** All k6 traffic shares one source address and virtual users check out faster than a person, so production values would measure the limiter, not the app. The `loadtest` component sets `SHOP_RATE_LIMIT_SCALE=1000` on the API (`shop.rate-limit.scale`, an integer of at least 1 that multiplies every capacity and refill; application.yaml binds it through an explicit placeholder because relaxed binding of that env name would not reach `rate-limit`) and a JSON6902 patch raises every Envoy rule to 100 000. The limiter code still runs, so its Valkey round trip is in the measurement. `make k8s-lint` runs `k8s-rate-limit-guard`: the `local` and `obs` renders must carry every line of the base `BackendTrafficPolicy` and `ClientTrafficPolicy` documents unchanged (`deploy/k8s/base/limits.yaml`, read by `make/rate-limit-policies.awk`, so the guard needs no copy of the numbers: units, path, method and source selectors, request buffer and response overrides are all compared, not only `requests`), must contain no API rate-limit setting in any spelling (`make/forbid-rate-limit-switch.awk`: `SHOP_RATE_LIMIT_*`, `shop.rate-limit`, also inside `SPRING_APPLICATION_JSON`), and the `loadtest` render must have every rule at 100 000 or more (threat model R70). It checks rendered manifests only. The word `loadtest` stays out of the base BTPs (the ADR 0011 guard rejects it). k6 counts any 429 outside `setup()` in `rate_limited` and fails the run on a non-zero count.

**Body limits (D46, R25, R40).** Envoy's `requestBuffer` is 64 KiB with `BufferAndLimit` on both policies; a larger body gets Envoy's 413 (`tag:shop.dev,2026:body-too-large` problem body on `shop`, plain text on `keycloak`, upstream `-` in the access log). 64 KiB is the webhook's own ceiling. In the API, `RequestBodyLimitFilter` keeps 16 KiB for customer routes and the webhook's own rule, and `/api/admin/**` now has a 32 KiB cap (`ADMIN_LIMIT_BYTES`; admin JSON at its validation maxima stays under 16 KiB) with the same counting stream and the 415 rule for non-JSON bodies. An oversized admin body gets 413 before authentication, as customer bodies do (C32). The cap holds in compose, where there is no Envoy.

**`statement_timeout` 5 s (D45, R34).** Hikari's `options` is `-c lock_timeout=3s -c statement_timeout=5s`, so every pooled connection, Flyway's included, carries both, in compose, Testcontainers and CNPG alike, with no role change. Migration rule: a migration that needs longer starts with `SET LOCAL statement_timeout = '<time>'` in its own transaction, as every migration already does for `lock_timeout`; `SET LOCAL` cannot leak into the pool. SQLState `57014` (query_canceled) maps to 503 Problem Details with `Retry-After: 5` and detail `The request took too long; try again shortly`; one WARN logs the exception class and SQLState only (SQL text can carry product data). The mapping also covers other cancellations that use 57014 (`pg_cancel_backend`, a JDBC statement cancel or query timeout); a 503 is the right answer for all of them, so the WARN says a statement was cancelled and does not claim `statement_timeout` as the cause. `QueryTimeoutException` counts only when a JDBC exception is beneath it, so Redis query timeouts stay 500. Margin: with Postgres logging every statement over 150 ms across the whole suite, including migrations and the seed IT, only two statements passed it (301 ms, a product search, and 296 ms, a `FOR UPDATE` lock wait), more than 15 times below the limit. `StatementTimeoutIT` checks `SHOW statement_timeout` on a pooled connection, that a statement under `SET LOCAL statement_timeout = '50ms'` with `pg_sleep` maps to 503 without SQL in the log, and that the same backend shows 5 s afterwards. The timeout bounds each statement, not concurrency (A14, R34).

**Keycloak forwarded headers stay off (D47).** Keycloak's `proxy-headers` is not set, so its events and its brute-force detection see the gateway address. Its lockout is per user whichever address it sees, and Envoy's per-IP limit on `/realms/shop/login-actions/` is the control. Turning on `xforwarded` with `proxy-trusted-addresses` would fix the address in events but changes origin and hostname handling under every e2e login. Recorded as a residual (R67).

**Cloud notes from the security review.** Bucket4j's refill uses each replica's wall clock (`isWallClockBased`), so clock skew between replicas shifts refill times: keep NTP in the cloud (R75). `statement_timeout` does not bound a transaction idle between statements, so a pool connection held by a slow non-SQL call stays held; `idle_in_transaction_session_timeout` is the option if that appears (R76). The Grafana route in `obs` shares the `http` listener without a per-IP limit or body cap (R77).

**Keycloak brute-force values, stated (A5).** `deploy/keycloak/shop-realm.json` sets `bruteForceProtected: true`, `permanentLockout: false`, `failureFactor: 30`, `waitIncrementSeconds: 60`, `maxFailureWaitSeconds: 900`, `minimumQuickLoginWaitSeconds: 60`, `quickLoginCheckMilliSeconds: 1` and `maxDeltaTimeSeconds: 43200`. All but the quick-login check equal the defaults in Keycloak's `RealmManager.setupRealmDefaults` at the pinned 26.8.2 (checked 2026-11-25 against the source at tag `26.8.2`): failure factor 30, wait increment 60 s, max failure wait 900 s, minimum quick login wait 60 s, quick login check 1000 ms, failure reset time 12 hours (`60 * 60 * 12`); permanent lockout is false by default. The quick-login check is the one deviation (D52): at the default 1000 ms, two failed logins less than 1 s apart locked any account for 60 s, which two requests a minute from one IP could sustain whatever the per-IP limit, so the owner set it to 1 ms, which switches that rule off. In effect: 30 failed logins for one user within 12 hours start a temporary lockout of 60 s that grows by 60 s per further failure to at most 15 minutes. Slowing guessing to 125 a minute per IP does not stop lockout of a victim: one IP can send 30 bad logins for an account in well under a minute and keep it locked while it continues (R3, residual C5c-5). A per-IP limit below `failureFactor` per window would be needed to prevent that, and it conflicts with the e2e headroom, so the residual is accepted; the remedy is the cloud guide's per-IP lockout awareness.

**What the Envoy 429 and 413 look like (C31).** Envoy sends `Retry-After` itself on local 429s, but `responseOverride` replaces the response and drops it, and `%RESP(RETRY-AFTER)%` in an override header did not render. Both 429 overrides therefore set a constant `Retry-After: 60`, the longest window; the per-second rules over-state the wait. Because the override replaces the headers, Envoy's own 429 and 413 carry no security headers (R74); the bodies are fixed. The web client reads `Retry-After` as delta-seconds only and shows `Too many attempts. Try again in N seconds.` (`a moment` when absent or not a number); `rate-limit.spec.ts` accepts either layer's 429.

**Notes for anyone tuning this (A13).**

- Envoy's buffer filter runs before its rate-limit filter, so a request that will get a 429 is still buffered up to 64 KiB first. Rate limits do not protect Envoy's memory; the 256 Mi limit and the buffer cap do.
- A checkout retried under one `Idempotency-Key` (the web retries once on `idempotency-in-progress`) consumes a token each time. At 30 a minute this is fine; do not "fix" it by limiting after idempotency.
- Envoy's per-IP buckets refill once per rule unit (a fixed 60 s step for the per-minute rules; the per-second rules refill every second), so a client can get up to twice a per-minute limit across a boundary.
- A real payment provider sends webhooks from a few addresses and retries in bursts after an outage, so 20 per second per IP can throttle its own redelivery. The cloud guide allow-lists the provider's ranges.
- Clients behind one NAT share per-IP buckets, and the Envoy limits are per replica and reset when Envoy restarts.

**Alert rules (R50, R53; ADR 0010).** See ADR 0010: five rules in `deploy/observability/alerts/shop.rules.yaml`, checked by `promtool` in `make lint`, kind only.

**Cloud upgrade path.** Envoy local limits are per replica; behind several replicas the effective limit is the value times the replica count. The upgrade is Envoy Gateway global rate limiting (the ratelimit service with its own Redis) for exact, shared per-IP counts, an allow-list for the payment provider, per-IP lockout awareness in Keycloak with `proxy-headers=xforwarded` and trusted addresses, and Alertmanager (ADR 0010). The limiter's own Valkey connection must stay standalone (with `spring.data.redis.ssl.enabled` if the store needs TLS), or the limiter needs a sentinel or cluster client first.

## Consequences

- A script that signs in can make 60 cart writes, 30 checkouts and 30 order actions a minute per account, and a single address 30 checkouts and 125 login starts a minute; legitimate use sits far below these.
- With Valkey trouble the per-account limits stop for as long as it lasts (plus up to 5 s after a failed connect), and only the alert and the counter show it (R68).
- Compose (`make dev`, compose e2e) has no per-IP limits and no Envoy body cap; only the API's limits and filters apply there (R72).
- An API pod's limiter version is its start time, so a rolling update changes every bucket to the newest rule values on first touch.
- `make cluster-e2e` runs `limits-test.js` and `limits-access-log-test.sh` from one k6 container address after the other steps, so its buckets are its own.

## Deviations from the brief

- Bucket configuration version is the pod start time, not a hash (C32).
- Envoy 429 overrides send a constant `Retry-After: 60` (C31).
- Oversized admin bodies get 413 before authentication, and the admin path also gets the 415 rule.
- Rule overrides per rule by env (`SHOP_RATE_LIMIT_<RULE>_...`) became one `SHOP_RATE_LIMIT_SCALE` (A12).
