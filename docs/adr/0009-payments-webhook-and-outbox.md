# ADR 0009: Payment, webhook, outbox, email and self-registration

Status: accepted (slice 4b). Checked against the implemented code; where the code differs from the original design, the Deviations section says so.

## Context

ADR 0008 (slice 4a) ends every order in `CANCELLED` or `EXPIRED`. Slice 4b adds the rest: a customer pays on a fake provider page, a signed webhook marks the order paid, late or refunded, one confirmation email reaches Mailpit, and customers can register with a verified address. It adds modules `payment`, `fakepsp` and `notification`, migrations V9 and V10, and the Spring Modulith event registry as an outbox. Lock order (ADR 0008, F6), body limit and Problem Details rules are inherited.

## Decisions

**Fake provider in-process behind a port (D24, F29).** `fakepsp` implements the `payment` module's `PaymentProvider` port (`createPayment`, `refund`) and delivers signed webhooks over real HTTP to the API's own `/api/payments/webhook`, so HMAC, dedupe and retries run for real without a new image. The alternative, a separate container, is a real trust boundary but costs an image, manifests and NetworkPolicies. Consequences: `shop.payment.provider` has no default and startup fails when unset or not `fake`; with `fake` one WARN says `fake payment provider: no money is taken`; `/api/fake-psp/**` is 404 when the fake is off. A cloud overlay must set a real provider, and `fakepsp` ships in the binary regardless. The fake signs with the verifier's own key, so the HMAC trust boundary is simulated (R47). `createPayment(paymentId, amountMinor, currency, returnPath, holdExpiresAt)` is idempotent by `paymentId` (`fake_psp_payment.merchant_reference UNIQUE`, `ON CONFLICT DO NOTHING`, then the existing session is returned), so a crashed payment start can be repeated (C1).

**Payment start and the stored session (F27, C1).** Start runs `PaymentOpening.open` under the order lock: it returns the order's open `CREATED` payment or inserts one (no provider id; the partial unique index `payment_one_open_per_order_idx` on `(order_id) WHERE status = 'CREATED'` is the backstop) and commits. Concurrent starts queue on the order lock, so the second sees the first's row. It then calls `createPayment` outside any transaction and stores `provider_payment_id` and `redirect_url` together. A repeat start returns the stored `redirect_url`, or calls `createPayment` again with the same id when none was stored. A payment found by neither `providerPaymentId` nor `merchantReference` gets a 404 problem and a `payment_webhook_unmatched` row written in its own transaction after the dedupe insert rolls back, so the provider retries. A real provider must retry on 404. A payment found by `merchantReference` whose stored provider payment id differs from the event's is a separate capture: the order is unchanged, a new `payment` row in `REFUND_PENDING` records it, `payment` publishes `RefundRequested` itself, and that capture is refunded (C1, C22; `WebhookIT`). A payment found only by `merchantReference` with no stored provider id adopts the event's id.

**Webhook format and verifier (F30, C8, C13).** Header `Shop-Signature: t=<unix seconds>,v1=<64 lowercase hex>`, `v1 = HMAC-SHA256(secret, t + "." + rawBody)`, in the style of Stripe. `WebhookVerifier` requires exactly one header, exactly one `t` (1 to 10 digits) and one `v1`, and refuses unknown keys; `|now - t| <= 300 s`; compares decoded bytes with `MessageDigest.isEqual`; only then parses JSON. Every failure is the same 401 `webhook-signature`; logs name the reason, never the header. The raw body is read through a counting stream capped at 64 KiB (413), `Content-Type` must parse as `application/json` (415); both refusals send `Connection: close`. The body-limit filter skips only `POST` with the exact URI `/api/payments/webhook`. Other forms of the path (trailing slash, `//`, case, other methods) keep the 16 KiB cap and then reach the main chain's `denyAll`. Percent-encoded variants such as `/api/payments/%77ebhook` are decoded by Tomcat and do reach the webhook controller; they get its stricter limits (64 KiB, 413 above) and are still HMAC-checked, so this is accepted and tested, not blocked (C13, `WebhookIT`). `PaymentProperties.webhookSecret` is `@NotBlank`; its 32-character minimum is checked in the record's constructor with a message that carries no value, and `toString` redacts it (C8, `PaymentPropertiesTest`). One secret serves both signing and verification (R39).

**Webhook chain and the CodeQL alert (D27, F5, F31, R3).** `WebhookSecurityConfiguration` is a separate `@Order(1)` chain matched only by `POST /api/payments/webhook`: `permitAll` (the HMAC is the authentication), session management and anonymous authentication disabled, null security-context and request caches, CSRF disabled (`.csrf(csrf -> csrf.disable())`), no `oauth2Login`, revalidation or timeout filters, and the usual Problem Details entry point. It is the only CSRF exemption in the application. The main chain, with no matcher, stays the catch-all at lowest precedence and keeps `denyAll`. A session cookie on a webhook request is ignored, and no `Set-Cookie` is sent. `ValkeyFailureFilter` and Spring Session's filter are servlet filters outside both chains, so they also see webhook requests. A stateless policy alone was not enough: with Valkey stopped and a cookie sent, the webhook still answered 503 through four session reads (`SessionManagementFilter`, `AnonymousAuthenticationFilter`, Spring MVC's request-handled event and `DispatcherServlet`'s flash-map read). The chain disables the first two, the application sets `spring.mvc.publish-request-handled-events=false` and registers a no-op `FlashMapManager` (`NoFlashMapManagerConfiguration`, C18). `WebhookValkeyIT` is the guard (still 200 and paid), and `WebhookIT` asserts the chain's filter list. The alternative, keeping one chain and `ignoringRequestMatchers` for the path, is also a CSRF exception, is flagged by the same query, and would share session filters.

CodeQL is skipped while the repository is private. When it goes public the owner dismisses `java/spring-disabled-csrf-protection` as "won't fix" with this text, citing the alert's file and line (`services/api/src/main/java/dev/shop/api/auth/WebhookSecurityConfiguration.java`, the `.csrf(csrf -> csrf.disable())` call, line 33 when this was written; take the alert's own line if it has moved):

> This chain matches only `POST /api/payments/webhook`, is stateless and sets no cookie, so there is no ambient credential for a cross-site request to ride. Every request must carry a valid HMAC-SHA256 signature over the timestamp and raw body, checked in constant time, with a 300 second window; without it the answer is 401. Every other unsafe route stays on the main chain with CSRF enforced (`CsrfIT`). See ADR 0009.

Never evade the query, for example with `requireCsrfProtectionMatcher(r -> false)`.

**Payment states and order transitions (F25, R4, C2).** Payment states are monotonic and are checked under the payment row lock before any order transition: `CREATED -> SUCCEEDED | FAILED`, `FAILED -> SUCCEEDED`, `SUCCEEDED -> REFUND_PENDING -> REFUNDED`. An event for a payment already in its target or a later state is a no-op: 200, logged at info. `orders.payment_status` mirrors the latest payment and is written only through `OrderPayments` under the order lock; `orders.paid_payment_id` names the payment that paid and is written only for an accepted payment. On a mismatch, or a refund-only outcome on an order that is not yet paid or refunded, `payment_status` shows `REFUND_PENDING` and then `REFUNDED` while the order status stays as it was; an extra payment on an order already paid or refunded is refunded without touching `payment_status`.

`OrderStateMachine` maps `(status, trigger)` to `Transition(next status, StockEffect)`, where `StockEffect` is `NONE`, `RELEASE`, `CONSUME` or `TAKE_LATE`. The caller computes the trigger from facts it reads under the locks, so the table stays pure. This replaces ADR 0008's line that every transition releases stock.

| From | Trigger | To | Stock effect |
|---|---|---|---|
| `PENDING_PAYMENT` | `CANCEL` | `CANCELLED` | `RELEASE` |
| `PENDING_PAYMENT` | `EXPIRE` | `EXPIRED` | `RELEASE` |
| `PENDING_PAYMENT`, before `expires_at` | `PAY_IN_TIME` (success, amount and currency match) | `PAID` | `CONSUME` |
| `PENDING_PAYMENT`, past `expires_at`, job not yet run | `PAY_LATE_TAKEABLE` (inside the late window, every product active) | `PAID`, `latePayment = true` | `CONSUME` of the held reservation |
| `PENDING_PAYMENT`, past `expires_at` | `PAY_LATE_NOT_TAKEABLE` | `REFUND_PENDING` | `RELEASE` |
| `EXPIRED` | `PAY_LATE_TAKEABLE` | `PAID`, `latePayment = true` | `TAKE_LATE` |
| `EXPIRED` | `PAY_LATE_NOT_TAKEABLE` | `REFUND_PENDING` | `NONE` |
| `CANCELLED` | success | `REFUND_PENDING` | `NONE` |
| `PAID`, `REFUND_PENDING`, `REFUNDED` | `PAY_OTHER_PAYMENT` (not `paid_payment_id`) | unchanged; that payment refunded | `NONE` |
| any | `PAY_MISMATCH` (amount or currency differs) | unchanged; payment refunded for the received amount | `NONE` |
| any | `PAY_FAILED` | unchanged | `NONE` |
| `REFUND_PENDING` | `REFUND_DONE` | `REFUNDED` | `NONE` |

`REFUND_DONE_PARTIAL` is the same trigger when another payment of the order is still `SUCCEEDED` or `REFUND_PENDING`: the payment moves to `REFUNDED`, the order stays. `OrderPayments.refunded` is idempotent. The outcome of a late success never depends on whether the expiry job has run (the second row). The late window is `shop.checkout.late-payment-window` (30 min after `expires_at`). Only `TAKE_LATE` can fail: the transition code applies the effect first, and when `TAKE_LATE` returns false it applies the `PAY_LATE_NOT_TAKEABLE` row instead and writes the status only after an effect has succeeded. `TAKE_LATE` appears only in rows with such a fallback (C2; `OrderStateMachineTest`, `LatePaymentIT`). A second payment for a paid order and a mismatch are refunded; the order never changes on them. Every move into `PAID` publishes `OrderPaid`; every move into `REFUND_PENDING`, and any extra capture, publishes `RefundRequested`.

**Stock effects (R8).** `StockReservations` gains `consume(orderId)` (`on_hand -= q, reserved -= q, version + 1`, reservations `CONSUMED`) and `takeLate(orderId, lines)` (lock stock rows by ascending product id, check `on_hand - reserved >= q` for every line, then `on_hand -= q, version + 1` and insert `CONSUMED` rows, or change nothing and return false). Both are `Propagation.MANDATORY`. Consuming bumps `stock.version`, so an admin's open stock form gets 409 instead of undoing a sale (ADR 0007).

**Lock order (F6, F26).** ADR 0008's order is inherited with `payment` rows after `orders` rows: idempotency row, cart row, `orders`, `payment`, product rows (`FOR SHARE`, ascending id), stock rows (ascending product id, once per transaction). The webhook reads `payment.order_id` without a lock, locks the order `FOR UPDATE` (`OrderPayments.lock`), then locks the payment. `payment.order_id` never changes, so no re-check of ownership follows (C22). `payable()` never locks a payment. The late rule locks products before stock. `PaymentRaceIT` races the webhook against the expiry job, payment start and a refund.

**Order access without a user (R7, C9).** The webhook and the listeners run with no signed-in user, so they cannot use `OrderService` (class-level `hasRole('CUSTOMER')`, owner-scoped locks). `OrderPayments` (named interface `order::payments`) and `OrderSummaries` (`order::summaries`) are separate beans without that guard. Only `payable(sub, orderId)` keeps `@PreAuthorize` and owner scoping; the others lock through `OrderRepository.lockById`, called only from `OrderPayments` (ArchUnit rule). `payment` depends only on `order::payments` and `notification` only on `order::summaries`, so the mailer cannot reach the payment transitions. Amounts cross modules as `long amountMinor, String currency`, not `Money`.

**Session lifetime and the late window (F28).** `fake_psp_payment.expires_at = order.expires_at + shop.payment.fake.session-grace` (5 min); completing after it gives 409 and the page says `This payment has expired`. A success that arrives more than the late window after `expires_at`, or for an order with an inactive product, is refunded rather than taken.

**Outbox on the Modulith event registry (F32 to F35, C6, C10 to C12).** `spring-modulith-starter-jdbc`; the schema comes from Flyway (V10), `schema-initialization` is off, `completion-mode: delete`, `republish-outstanding-events-on-restart: false` (so replicas do not all republish). Listeners are `@ApplicationModuleListener`s with explicit stable ids; renaming one orphans its open publications. Events carry an `eventId` and ids only, never personal data.

- Retry: `EventRetryJob` (in `web`, every 60 s, one replica at a time through a session-level advisory lock) first moves `FAILED` rows with `completion_attempts >= shop.events.max-attempts` (48, about a day at the capped backoff) to `event_publication_dead_letter` and logs a WARN per listener with the count (no personal data; nothing alerts until slice 5). It then resubmits with a backoff on `getLastPublicationDate()` of 1, 2, 4 and 8 minutes, doubling to a cap of 30, and admits at most 200 per run. The batch size is the count of `FAILED` rows, so a pile of publications inside their backoff cannot hide a newer one that is due. A Mailpit outage of up to about a day delays the email; beyond that the event is parked and logged. Manual resubmission is an `INSERT ... SELECT` back into `event_publication` (README). Modulith 2.2's abandonment can replace the dead-letter table once adopted.
- Recovery after a restart or a rejected task: a publication left `PUBLISHED`, `PROCESSING` or `RESUBMITTED` is marked failed by the staleness monitor after `staleness.published` (10 min; `processing` and `resubmitted` 5 min), and `EventRetryJob` then resubmits it after the first backoff step. Recovery therefore takes up to `staleness.published` plus the first backoff step, about 11 minutes. `EventRetryJobIT` asserts the bound `StalenessProperties` and the recovery of a stale `PUBLISHED` publication (C11). The registry's `completion_attempts` is used as it is, so 0 and 1 attempts both wait 1 minute.
- Async and scheduling (C12, R1): Modulith enables async execution for its listeners on its own. The application nonetheless declares `@EnableAsync` in an unconditional `web.AsyncConfiguration`, separate from the conditional `@EnableScheduling` class, because ITs set `shop.jobs.enabled=false` and a conditional `@EnableAsync` would run listeners on the request thread and pass tests for the wrong reason. The staleness monitor is scheduled, so it needs scheduling on; with jobs off, ITs call the monitor and the jobs directly. `@EnableAsync` together with Boot's `taskExecutor` alias is what routes listeners to the pool (removing it fails the test; removing `implements AsyncConfigurer` does not, as that interface only supplies the exception handler). `AsyncConfigurationTest` and `OutboxIT` assert that the listener runs on a `task-` executor thread, not the caller's, with jobs on and off. The staleness monitor is a `SchedulingConfigurer`, so it runs only when `shop.jobs.enabled` is true.
- Listener transactions and pools (F34): I/O listeners (`WebhookSender`, `RefundProcessor`, `OrderConfirmationMailer`) use `Propagation.NOT_SUPPORTED` and do database work in short transactions on a separate bean before and after the I/O, never during it. `spring.task.execution.pool.max-size` is 8 with `queue-capacity` 500 (a full queue throws and leaves the publication to resubmission); `hikari.maximum-pool-size` is 20. `spring.task.execution.shutdown` awaits running listeners for 15 s, inside the 20 s shutdown phase and the pod's 40 s grace. A hung SMTP server must not stall `GET /api/products` or checkout (`OutboxIT` with Mailpit frozen: both answer within 2 s, and the mail arrives once after it recovers).
- Listener errors (C7): listeners rethrow `ListenerFailedException` with a message of the order id and the cause's class name and no cause, and an `AsyncUncaughtExceptionHandler` logs the class and message without a stack trace, so a mail failure never writes a recipient address to the log (`OutboxIT`).
- `WebhookSender` builds its body from stored fields and signs at each attempt with the current time (C5), so a retry minutes later is not rejected for skew and a delivered event keeps its id (`fake_psp_payment.event_id`), which is what the receiver dedupes on.

**Email at least once (F34, F39, C6).** `OrderConfirmationMailer` loads the order through `OrderSummaries`. With no address it completes without sending. Otherwise it claims `order_email(order_id, kind, status 'SENDING', claimed_at)` and commits, sends, and sets `SENT`. On a send failure it releases the claim (`FAILED`, `claimed_at` null) before rethrowing. A retry claims a `FAILED` row, or a `SENDING` row older than 1 minute (a crash between send and commit); a fresh `SENDING` row makes the listener throw `RetryLaterException`, which leaves the publication incomplete. `SENT` completes without sending. A crash between send and commit can send twice. Mail goes only to `orders.email`, refreshed from the verified claim at payment start; the mailer parses it with `InternetAddress(email, true)` and refuses CR, LF and more than 254 characters. Plain text only; product names are catalogue data. Readiness never depends on Mailpit (`management.health.mail.enabled: false`).

**Mailpit and the Gateway listener (D26, F4).** Option A: the Mailpit UI sits on a Gateway listener `mail` (NodePort 30025, kind host mapping `127.0.0.1:8026`), and Mailpit, the listener, its route and its NetworkPolicies live in `deploy/k8s/overlays/local/` only, never in `base`. Pros: always on, no command to start, the same pattern as the shop and Keycloak, and the listener is needed for e2e anyway. Cons: one `make cluster-down cluster-up` that wipes the kind database, one more host port that can clash, a little more Gateway and kind configuration. Rejected, option B (`kubectl port-forward` make target). Pros: no rebuild, reachable only while deliberately opened, no new host port. Cons: must be started each time and holds a terminal, drops on pod restart, a second access pattern. Mailpit is an unauthenticated local mail sink: anyone who can read it controls every mailbox (R38). `cluster-up` warns when the host mapping is missing.

**Self-registration (D25, F39).** Keycloak registration is on with `verifyEmail: true` and SMTP to `mailpit`; the default role stays `customer`, brute-force protection stays on. Order mail goes only to a verified address, so nobody can register a stranger's address and send them order mail. With `verifyEmail` on, Keycloak 26.8 hides the password fields on the registration form: the user sets the password after following the verification link and is then signed in (C24). That is kept: it also means that registering someone else's address cannot preset its password. Changing the address in the account console resets `email_verified` and Keycloak requires verification at the next sign-in, so no token carries an unverified address; the session already in use keeps the old verified address. `payment.spec.ts` proves both (the fresh sign-in shows `Email verification`, no shop session results, and no confirmation reaches the new address; threat model R51). The fallback (remove `manage-account` from the default role) is therefore not needed. Registered users in kind are lost when Keycloak restarts (realm re-import, ADR 0006). Accounts are free, so the per-account caps of ADR 0008 do not bound an attacker (R36).

**Single replica (R14).** `deploy/k8s/base/api.yaml` runs one API replica. Multi-replica behaviour (the advisory-locked retry job, `SKIP LOCKED` expiry batches, concurrent webhooks) is proven only in integration tests against one Postgres, not in the cluster.

**Retention (C15, C21).** `PaymentMaintenanceJob` in the `payment` module (not `order.MaintenanceJob`, because `order` may not depend on `payment`) deletes `payment_webhook_event` and `payment_webhook_unmatched` rows older than 7 days, hourly, in batches of 1000. Replays older than the 300 s window are refused by the timestamp check anyway. Orders, payments and `order_email` rows are kept (R37).

## Deviations from the brief

What the code does differently from the brief and its amendments C1 to C15. Where code and brief disagree, the code and this section are right.

- **C16, C17.** `fakepsp` depends on `payment` and `web` only and carries `amountMinor` (long) and `currency` instead of `Money`; `FakePspPayment` also returns `expiresAt`, which the provider page shows.
- **C18 (session reads on the webhook).** The stateless policy was not enough; see the webhook chain above. `NoFlashMapManagerConfiguration` and `spring.mvc.publish-request-handled-events=false` apply to every request, so every request with a session cookie also loses a Valkey read.
- **C19 (`OrderPayments` members).** Besides `payable`, `paymentSucceeded`, `paymentFailed` and `refunded`, it has `lock(orderId)` (the webhook takes the order lock before the payment lock without exposing `lockById`) and `paymentCreated(orderId)`. `refunded(orderId, paymentId, otherMoneyHeld)` takes whether another payment still holds money, because `order` cannot see payments. `payable` takes the verified email.
- **C20.** `createPayment` takes `holdExpiresAt` so the fake sets its session expiry to the order's expiry plus the grace; `refund` takes an idempotency key.
- **C21.** The webhook-table purge is `PaymentMaintenanceJob`, not an extension of `order.MaintenanceJob`.
- **C22 (separate capture; two paths not built).** A signed success with another provider payment id creates a `REFUND_PENDING` row and `payment` publishes `RefundRequested` itself. F27's unique-violation fallback on concurrent starts and F26's ownership re-check after the order lock are not implemented: the order lock serialises starts and `payment.order_id` never changes, so neither path is reachable, and an unreachable branch cannot meet the 100% branch gate. The partial unique index stays as a backstop.
- **C23.** `ReservationExpiryIT` and `StockRaceIT` run the expiry job once more after the race, because `SKIP LOCKED` jobs leave skipped rows for the next run by design.
- **C24 (registration).** The password is set after email verification, not on the registration form. The realm carries no `authenticationFlows`, because supplying any drops all 21 built-in flows. Registered users also needed a fix in `shop-realm.json`: Keycloak's import handles the top-level `defaultRole` before it creates the realm roles in the same file, so `composites.realm: ["customer"]` on the default role was dropped and new users had no `customer` role. The realm keeps the top-level `defaultRole` and adds a role named `default-roles-shop` to `roles.realm` with `composites.realm: ["customer"]`, which Keycloak merges into the default role; `registration.spec.ts` asserts the role.
- **Staleness.** `staleness.published` is 10 minutes, `processing` and `resubmitted` 5, as in the Decisions above; recovery takes about 11 minutes.
- **D30.** The API runtime image runs `apk upgrade` like the web image, because the pinned Temurin base lagged Alpine fixes (README known limits; ADR 0001).
- **Round 1 review fixes.** Request-log masking works on the routed path; signed webhook payloads outside bounds get 400 (`amountMinor >= 0`, `currency` `[A-Z]{3}`, ids 1 to 100 characters); `SHOP_PUBLIC_ORIGIN` must be an http(s) origin without a path or startup fails.
- **Contract.** `WebhookEvent` and `WebhookEventData` carry `@NotNull` and `@Valid`; the generated OpenAPI is unchanged by it. `EventRetryJob` and its `runOnce` are public so integration tests in other packages can call them. `RetryLaterException` and `ListenerFailedException` live in `web`. `management.health.mail.enabled` is false.
- **Compose e2e gateway.** `tests/e2e/gateway.conf` forwards the browser's `Host` to Keycloak on the IdP server, because the account console's token call got 403 behind the gateway when Keycloak saw `keycloak:8080`.

## Consequences

- A payment is applied once whatever the retries: event id dedupe, monotonic payment states and the order lock agree. Effects are at least once; the email is the only one that can repeat (R41).
- Money never moves on a late or mismatched payment without a record: the extra capture is refunded and the order is unchanged, or the stock is taken again and the order is flagged.
- The public webhook costs a body read (up to 64 KiB) and an HMAC per request before it can refuse (R40).
- One secret signs and verifies; rotating it needs a deploy (R39).
- Mail outages up to about a day only delay confirmations; after that an operator resubmits from the dead-letter table.
- ADR 0008's deviation line on the state table's shape is replaced by the `Transition` table above.
- Residual risks are in `docs/threat-model.md` (payment and webhook section).
