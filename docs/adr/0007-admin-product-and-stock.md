# ADR 0007: Admin product and stock writes, with an audit log

Status: Accepted (slice 3b). Where the code differs from the first design, "Deviations from the design" at the end says so.

## Context

Slice 3a shipped sign-in, roles and a read-only admin product list. Slice 3b lets admins create, edit, deactivate and reactivate products, set stock and read an audit log. Slice 4 (checkout) will reserve stock against the same table, so the stock model and its locking contract are fixed here. Authentication, CSRF and the URL rule for `/api/admin/**` are unchanged from ADR 0006.

## Decisions

**Admin API and module split.** Endpoints, all `Cache-Control: no-store`: `GET` and `POST /api/admin/products`, `GET` and `PUT /api/admin/products/{id}`, `PUT /api/admin/products/{id}/stock`, `GET /api/admin/audit`. `catalog` exposes `ProductAdministration` with `ManagedProduct` records (renamed from 3a's `AdminProduct`); the new `inventory` module owns `StockManagement` and `StockLevel`; `customer` owns `CurrentUser`. The `admin` module composes them into the published `AdminProduct` (flat, with `stock: AdminStock {onHand, reserved, version}`) and may depend on all three. `catalog` never depends on `inventory`, and `inventory.StockLevel` is not in the OpenAPI contract. Spring Modulith (`ModularityTest`) enforces this. Records expose only the allowed input fields, so `id`, `version` on create, `reserved` and similar cannot be mass-assigned; unknown JSON properties are ignored.

**Slug is immutable after create (D14).** Public URLs and bookmarks stay valid, cache invalidation is by one key, and a freed slug cannot be reused to impersonate an old product. `PUT` takes no slug. A wrong slug means deactivate and create anew.

**Active is part of `PUT` (D15).** Deactivating and reactivating use an `Active` checkbox in the product form and `active` in the `PUT` body; the audit action is `product.updated` with `active` in the changes. An inactive product is absent from the public list, search, category filter and product page (404); reactivating brings it back. Public responses keep `Cache-Control: no-cache`.

**Optimistic locking with a row lock.** Product and stock each carry a `version`, sent in the request body (no `ETag` or `If-Match`). Every write is one `@Transactional` method at the default `READ COMMITTED`, stated explicitly: `SELECT ... FOR UPDATE` by id (404 if absent), compare `version` (409), validate (400), then `UPDATE ... SET version = version + 1`. A writer that waited for the lock then sees the new version and gets 409. `REPEATABLE_READ` would turn that wait into a serialization failure (500). Each change locks one row, so there is no lock-ordering deadlock. A `PUT` that changes nothing returns 200 with the current state, no version bump and no audit row (the version is still checked). Reads (`list`, `get`, audit page, and `CatalogService.search`) run in read-only `REPEATABLE_READ` transactions so count, page and stock levels come from one snapshot; Spring ignores `isolation` on a joined transaction, so it is set on the outermost read method.

**Lock timeout gives 503.** Connections get `lock_timeout = 3s` (`spring.datasource.hikari.data-source-properties.options`). `PessimisticLockingFailureException` maps to 503 problem+json with `Retry-After: 3` and no audit row. It is not a 409 because the version may still be current. The lock failure is recognised by `PessimisticLockingFailureException` or by SQLState `55P03` (`lock_not_available`) on the cause, because Spring does not translate every driver's failure. `ValkeyFailureFilter` now treats only a Lettuce `RedisCommandTimeoutException` (and `RedisConnectionFailureException`) as a Valkey failure, no longer any `QueryTimeoutException`, so a JDBC timeout is not misreported as a session store outage. Migrations V3 to V5 begin with `SET LOCAL lock_timeout = '5s'`, so a migration blocked by long reads fails and the pod restarts instead of stalling the catalog.

**Problem Details.** Every 400 and 409 is `application/problem+json` with `type` from a fixed set and `errors: [{field, message}]` (possibly empty): `tag:shop.dev,2026:validation` (400), `tag:shop.dev,2026:duplicate-slug` (409, `errors[0].field == "slug"`), `tag:shop.dev,2026:version-conflict` (409). Messages never echo input values. Unreadable or overflowing JSON keeps Spring's plain 400 without an `errors` array. `ApiExceptionHandler` overrides both `handleMethodArgumentNotValid` and `handleHandlerMethodValidationException` (with constraint annotations on any parameter, a bad body arrives as the latter). The override also applies to the public endpoints, so `/api/products?size=49` now returns the same `validation` type with `errors`. One `ProductNotFoundException` with the fixed detail `Product not found` serves slug and id lookups. The `DataAccessException` handler walks the cause chain to the first `SQLException` and logs the exception class and its SQLState only, never a message (with no `SQLException` it logs the class alone), because PostgreSQL's "Failing row contains" detail holds product text; it answers 500. The problem shapes come from one `Problems` builder in `web`, shared by the handler and the admin module. The product insert is `INSERT ... ON CONFLICT (slug) DO NOTHING RETURNING id`; an empty result raises `duplicate-slug`. No `DuplicateKeyException` is caught, so any other integrity error stays a 500 and the transaction is never left aborted.

**Validation and plain text.** Numeric and boolean fields are boxed with `@NotNull`, so a missing field is a 400, not a silent 0 or `false`. Bounds: slug `^[a-z0-9]+(-[a-z0-9]+)*$`, 1 to 100; name at most 120; description at most 2000; `priceMinor` 0 to 10 000 000; `onHand` 0 to 1 000 000; `version` 0 or more; currency fixed `EUR`. A Jackson 3 customizer disables float-to-int and scalar coercion, so `12.5`, `1.0e0`, `"1299"` for a number and `"true"` for a boolean are 400s. `name`, `description` and the audit display name use one `@PlainText(allowNewline)` constraint, checked on code points: control, format, surrogate, private-use and unassigned characters are rejected. Newline is allowed in descriptions; tabs and CR are not. The OpenAPI patterns are `^[^\p{Cc}\p{Cf}\p{Cs}\p{Co}\p{Cn}]*$` and, for descriptions, `^(?:\n|[^\p{Cc}\p{Cf}\p{Cs}\p{Co}\p{Cn}])*$`; the web schemas use the same patterns with the `u` flag. Java's and the browser's Unicode tables can disagree on newly assigned characters, so a name the browser accepts may get a server 400. "Not blank" means at least one character above U+0020 on both sides, so a name of only U+00A0 passes both. `CurrentUser.displayName` comes from Keycloak, so disallowed code points are removed rather than rejected, then the name is cut at 200 code points.

**Stock model now and the slice 4 contract.** `stock(product_id PK, on_hand, reserved, version)` with checks `on_hand >= 0`, `reserved >= 0` and `reserved <= on_hand`. Every product has a stock row: V3 backfills 0, `POST` creates one with `on_hand` 0, and `levelsOf` throws `IllegalStateException` (a 500, a bug) for a missing row. Admins set `on_hand` only; `reserved` is slice 4's. Rules fixed for slice 4:

- Every write that changes `on_hand` bumps `stock.version`. Writes that change only `reserved` do not, so checkouts do not make every open admin form conflict.
- `setOnHand` checks `onHand >= reserved` against the row it locked and answers 400 otherwise.
- Slice 4 must lock the stock row (`FOR UPDATE`) when it reserves, and must re-price and re-check stock under that lock, because an admin can change price and stock between the cart and the checkout.

**Seed interactions (D19).** V3 runs before the repeatable seed, so on an existing database every stock row starts at 0. The seed sets `on_hand` with `ON CONFLICT (product_id) DO UPDATE SET on_hand = EXCLUDED.on_hand WHERE stock.version = 0 AND stock.reserved <= EXCLUDED.on_hand`: rows an admin edited (version above 0) or that carry reservations are left alone, and the seed never touches `stock.version`, or the next seed change would stop updating the row. The product upsert updates only rows that differ (`IS DISTINCT FROM`) and bumps `product.version` when it does, so an open admin form gets a 409 instead of overwriting seed values. Consequence on dev and kind: when the seed file changes, it re-activates a seed product an admin deactivated, and it overwrites an admin-created product whose slug a later seed adds. `SeedProfileIT` runs the script directly and proves the guards and idempotency.

**Audit log.** One row per change in `admin_audit_event`, inserted in the same transaction as the change: if the audit insert fails, the change rolls back (`AuditRollbackIT`). Failed calls (400, 404, 409, 503) write nothing.

- Columns: `id` (identity), `occurred_at`, `actor_subject`, `actor_name`, `action`, `entity_type`, `entity_id`, `changes` (jsonb), `trace_id`. No foreign key to `product`, so the log outlives rows and fixture truncation.
- Actions `product.created`, `product.updated`, `stock.set`; entity types `product` and `stock` (entity id is the product id).
- The actor is `sub` (via `CurrentUser`), never the display name; `actor_name` is display data at the time of the change and is never used for decisions. The API returns both; the audit table shows the name, trace id and changes, not the subject. A non-OIDC principal is refused with 403.
- `changes` holds changed fields only, `{"field": {"from": x, "to": y}}` (`from: null` for every field on create). Fields: `slug`, `name`, `description`, `priceMinor`, `categorySlug`, `active`, `onHand`, `reserved`. `stock.set` also records `reserved` at the time as `from == to`, the one unchanged field recorded, as context for the `onHand` change. The API returns `FieldChange[]` sorted by field, values as strings.
- `occurred_at` defaults to `clock_timestamp()` (not the transaction start) and is displayed only. The page is ordered by `id DESC`, which the primary key serves; no secondary index.
- `trace_id` comes from the Micrometer `Tracer` and is `null` without a span. A client can send `traceparent`, so it is an untrusted correlation hint, never evidence. The audit view's column reads `Trace (unverified)` and the OpenAPI description says so. No server request id is added.
- Protection (D17, E3): insert-only code (the repository has `insert` and `page` only), plus triggers that raise on row `UPDATE`, row `DELETE` and statement `TRUNCATE`. The app's DB role owns the table, so `REVOKE` would not bind it. The owner role can drop or disable the triggers; a separate audit role belongs in the cloud guide. Tests never truncate the table; they read rows above a high-water mark taken at the start of the test.
- Personal data: `actor_name` is personal data in an append-only log. Erasure needs the owner role to disable the trigger, a manual and logged procedure for the cloud guide.

**Deny by default and method security.** The filter chain still sends every method on `/api/admin/**` through `hasRole("ADMIN")` and CSRF. In depth: `AdminProductController`, `AdminAuditController`, `AdminProductService`, `AuditLog` and `ProductAdministration` carry a class-level `@PreAuthorize("hasRole('ADMIN')")`; `StockManagement.setOnHand` and `createFor` carry method-level guards (slice 4 adds customer-facing stock methods), and `ProductAdministration.create` and `update` and both `StockManagement` write methods use `Propagation.MANDATORY`, so they cannot run outside the audited admin transaction (`MandatoryTransactionIT`). The `inventory` module may depend only on `web`. `AdminEndpointsAreProtectedIT` asserts every public method. Anonymous gets 401 and customers 403, including for a malformed 1 MiB body, which shows the body is refused before it is parsed.

**Overdue revalidation fails closed for admin writes (E5).** In `RevalidationFilter`, after the revalidation step: for an `OAuth2AuthenticationToken` with an unsafe method on `/api/admin/**`, if the last successful revalidation is absent or older than `revalidate-after` (5 minutes), the filter answers 503 problem+json ("Your access cannot be confirmed right now") with `Retry-After: 300` (the `revalidate-after` value) and stops the chain. The web shows this detail to the admin. The path is matched with `PathPatternRequestMatcher`, so encoded forms such as `/api/%61dmin/` are caught too. That is also the longest admin writes stay at 503 after Keycloak recovers. With Keycloak down, a demoted admin therefore stops being able to write 5 minutes after the last success, while reads keep ADR 0006's 15-minute grace. A successful refresh in the same request passes; a rejected one has already ended the session (401). A request that loses the single-flight lock while overdue also gets 503 and may retry. The filter runs before `CsrfFilter`, so such a request gets 503 even without a CSRF token. No audit row is written.

**Retries.** Writes are safe to retry: `PUT` carries a version and `POST` is unique by slug, so a repeated request that already committed gets 409. A write reported as 5xx may have committed; the web client never resubmits on its own, and refetches the product to show the truth.

**Web.** TanStack Form 1.33.5 with Zod schemas as Standard Schema validators (no adapter); every Zod import goes through `@/lib/zod` (jitless, for the CSP). One product schema serves create and edit. Server and client rules use the same boundary values. After a 200 the forms reset from the response with `keepDefaultValues`, so the next save carries the new `version`. The create form starts with `Active` unchecked, so a new product is hidden until an admin ticks it. Native form controls, no new files in `components/ui/**` (D18). The audit view renders every value as text and wraps actor names and values in `<bdi>`. Each audit row links to the product's edit page.

**E2E isolation (D16, E2).** The public specs assert counts on the persistent kind database (60 active products, 10 kitchen products), and Playwright runs spec files in parallel. Projects: `admin-cleanup` (setup, `specs/admin-cleanup.setup.ts`) deactivates every active product whose slug starts with `e2e-` (paging until `page + 1 >= totalPages`) and asserts none is left; `chromium` depends on it and ignores `admin-writes.spec.ts`; `admin-writes` depends on `chromium`. Every e2e product has a fixed description with none of the words the public specs search for, and a `finally` deactivates it. No seed product is ever written. Cost: if any `chromium` spec fails, `admin-writes` is skipped. Inactive e2e rows accumulate on kind by design; admin views never assert exact counts. Use `--no-deps` to run one file without its dependencies.

## Consequences

- Admin writes need Valkey (session) and Keycloak (revalidation) to be reachable and fresh; the public catalog does not.
- A demoted admin can write for up to 5 minutes while Keycloak is up; with Keycloak down, writes stop 5 minutes after the last success.
- The audit log growth is bounded by the `admin-writes` rule from slice 5c (60 a minute and 600 an hour per account, ADR 0013), and it has no export or filter. A future export must neutralise CSV formula prefixes (`=`, `+`, `-`, `@`, tab, CR).
- Admin request bodies are capped at 32 KiB by `RequestBodyLimitFilter` (413 before authentication) and at 64 KiB by Envoy's request buffer since slice 5c. Deep audit pages are not rate limited per account (`statement_timeout` of 5 s bounds each query, not concurrency, R34).
- Slice 4 inherits the stock contract above and must not weaken it.
- Residual risks are R21 to R31 in `docs/threat-model.md`.

## Deviations from the design

- One fixed-text `ProductNotFoundException` for all product lookups instead of separate slug and id variants.
- The catch-all logs the exception class and SQLState only. It does not log the constraint name: the PostgreSQL driver is a runtime-scope dependency, so the handler reads the standard `SQLException` and cannot use `PSQLException`.
- The lock timeout is matched by SQLState `55P03` as well as by Spring's `PessimisticLockingFailureException`.
- `Problems` is a shared builder in `web` rather than code in the admin module.
- In OpenAPI the CSRF header is ANDed with the cookie scheme in one security requirement (`CsrfHeaderCustomizer`), so generated clients see both are needed.
- One Zod product schema for create and edit, not two.
- `Active` is unchecked by default on create.
- Forms reset with `keepDefaultValues`: a plain reset was undone by `FormApi.update`.
- `ValkeyFailureFilter` was narrowed to Lettuce's `RedisCommandTimeoutException`.
- The OpenAPI document declares a 200 `AdminProduct` on `GET` and `PUT` by id (found missing during web work).
- The stub identity provider no longer consumes the refresh token on a 5xx, so a retry after a failed refresh works as it does against Keycloak.

Test counts are in `tests/README.md`. All gates stay at 100%.
