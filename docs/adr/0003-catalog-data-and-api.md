# ADR 0003: Catalog data and API

Status: accepted, 2026-11-17

## Context

Slice 1 adds a browsable product catalog: list, search, filter, sort, page and a product page, served by the API and shown by the web app. This ADR records how the data is stored and queried, and how the API contract reaches the web app.

## Decisions

**JdbcClient, not JPA.** The catalog is read-only, and its queries are the interesting part: full-text search, ranking, fixed sorts and a count. Plain SQL in one repository class says exactly what runs and is easy to review. An ORM would add mapping, a session and lazy loading with nothing to gain. Parameters are always bound, never concatenated. The sort is chosen from an enum whose values carry fixed SQL fragments, so user input never reaches the SQL text. Every sort ends with `slug` as a tiebreak, so paging is deterministic.

**Full-text search in Postgres.** `product.search_vector` is a generated, stored `tsvector`: the name with weight A and the description with weight B, using the `english` configuration. A GIN index serves it. Queries use `websearch_to_tsquery('english', :q)` and `ts_rank`, so a name match outranks a description match. This avoids running a separate search engine for a catalog of this size.

Known limit: search matches whole words (after English stemming). There is no prefix matching and no typo tolerance, so a search for `lamp` finds lamps, but `lam` or `lmap` finds nothing. The UI says so. Better matching (prefix queries, trigram similarity, or a search service) is out of scope for now.

**Offset pagination with a cap.** Requests take `page` (0-based) and `size` (default 12, max 48). `page` is capped at 10000, and the offset is computed as a `long`. A page past the end returns 200 with empty `items` and correct totals. Offset pagination is simple and lets the UI show page numbers, but deep pages cost more because the database still walks the skipped rows; the cap bounds that. A separate count query supplies `totalItems`.

**Sort indexes wait for measurement.** Only the search GIN index and a btree on `category_id` exist. We do not index for each sort yet: with about 60 seed rows an index changes nothing measurable, and indexes cost writes and space. Slice 5b measures the plans: `loadtest/sql/explain-catalog.sql` runs `EXPLAIN (ANALYZE, BUFFERS)` for each sort, a category filter, a text search and the count (the first round of `make loadtest-cache` writes `build/reports/loadtest/<run>/explain-catalog.txt`). The findings go in `docs/performance.md` (section "Catalog query plans") and an index is added only if a plan shows it pays off. The same slice puts a 30 s in-process cache in front of these queries (ADR 0012).

**Money is minor units plus currency.** Prices are `price_minor` (a non-negative `bigint`) and `currency` (a three-letter ISO 4217 code, checked by a constraint). The API returns `Money { amountMinor, currency }`. No floating point ever holds a price, and the web app formats it with `Intl.NumberFormat`.

**Seed data is outside the production schema.** The demo catalog (about 60 products, 6 categories, EUR) lives in `src/main/resources/db/seed/R__seed_catalog.sql`, a repeatable Flyway migration that upserts by slug. It runs only when the Spring profile `seed` is active, which adds `classpath:db/seed` to the Flyway locations. Production runs without the profile and never sees demo rows. Because a database migrated with `seed` must still start without it, Flyway is configured with `ignore-migration-patterns: "*:future,repeatable:missing"`: the applied seed migration is then reported missing, not an error. The cost is that this setting also hides a repeatable migration that disappears by mistake; the schema migrations (`V*`) still fail loudly.

**The OpenAPI document is committed.** `services/api/openapi/openapi.json` is generated by springdoc (`/v3/api-docs`, no Swagger UI) and checked in, so the web app can generate its client without starting the API. The endpoint is disabled by default and enabled under profile `dev` and in tests. Every property of every component schema is marked required, so generated TypeScript types have no optional fields, except `ProblemDetail`, whose RFC 9457 members are optional.

**Staleness is caught in two places.**
- The integration test `OpenApiContractIT` fetches the live document, normalises it and compares it with the committed file. The failure message says to run `make api-spec`. This runs in `make test`.
- `make lint` runs `generate:api:check` in `apps/web`, which fails if `src/api/schema.d.ts` differs from what `openapi-typescript` generates from the committed document. It likewise runs `generate:routes:check` for the generated route tree.

**`make generate`** rewrites everything in order: `api-spec` (runs only `OpenApiContractIT` with `UPDATE_OPENAPI=true`, no coverage gate), then `web-api-client` (regenerates `schema.d.ts`), then the route tree. Commit the results. Both generated files are excluded from Prettier and ESLint, since the staleness check compares raw generator output.

**springdoc updates can change the spec.** A springdoc upgrade may reorder or reword the document. Renovate groups springdoc packages in their own pull request; that PR is expected to need `make generate` before `make test` and `make lint` pass. The same applies to updates of `openapi-typescript` and the TanStack Router packages, which can change the generated client or route tree and then fail the staleness checks in `make lint`.

**Input the server rejects before Spring.** Query parameters that are not valid UTF-8 are mapped to a 400 Problem Details response. Requests that Tomcat rejects itself before they reach Spring, for example `%00` or an encoded `/` in the path, get Tomcat's plain `text/html` 400 page instead. That is acceptable while the API sits behind the gateway; revisit if API clients other than the web app appear.

**Count and page are separate statements.** `totalItems` and `items` come from two queries without a shared snapshot. The catalog is read-only in this slice, so they cannot disagree; when the admin starts writing products in slice 3, run both in one repeatable-read transaction or use a window count.

## Consequences

The contract is reviewable in a diff, the web client cannot silently drift from the API, and the data layer has no ORM to learn. Search quality is limited to whole words until a later slice. The seed approach needs care: a repeatable migration that is removed from the classpath is ignored by Flyway.
