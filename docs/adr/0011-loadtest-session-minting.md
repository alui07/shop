# ADR 0011: Session minting for load tests

Status: accepted (slice 5b, 2026-11-24). Checked against the implemented code; the Deviations section lists where it differs from the brief. Threat model entries L1 to L8 and residuals R59 to R63 are in `docs/threat-model.md`.

## Context

k6 has to drive checkout and the flash sale as signed-in customers, 150 at once. Real logins go through Keycloak, whose realm import takes about 90 s, whose login page is a browser flow with CSRF and redirects, and which would become the bottleneck being measured instead of the shop. Registering 150 users is worse: each one sends a verification mail. The load test needs customer sessions that look exactly like login sessions to the API, without Keycloak on the load path. Fixtures are created by SQL (`loadtest/sql`), not by the admin API, because the admin API needs a fresh Keycloak confirmation.

## Decisions

**A Spring profile, `loadtest`, adds one endpoint.** `POST /api/loadtest/sessions` with no body and a `Shop-Loadtest-Token` header answers `201 {"subject": "loadtest-<uuid>"}` and sets `__Host-SESSION`. The server picks the subject: the `loadtest-` prefix and hyphenated UUID cannot collide with Keycloak subjects, which are plain UUIDs. `LoadtestSessionConfiguration`, `LoadtestSessionController`, `LoadtestProperties`, `LoadtestGuard` and `MintLimiter` (package `dev.shop.api.auth`, because they need the package-private `SessionAttributes`) all carry `@Profile("loadtest")`, and the controller is `@Hidden`, so the OpenAPI document and the generated web client are unchanged (`OpenApiContractIT` asserts no `/api/loadtest` path).

**A minted session is a login session minus Keycloak.** The controller saves an `OAuth2AuthenticationToken` over a `DefaultOidcUser` built from a synthetic ID token (`sub`, `roles: ["customer"]`, `name`, `email` `<subject>@loadtest.invalid`, `email_verified: true`, expiry now plus `session-timeout`, registration id `keycloak`) by setting the session attribute `HttpSessionSecurityContextRepository.SPRING_SECURITY_CONTEXT_KEY` directly (the repository `saveContext` needs the response and defers the write, so it is not used) in a normal Spring Session in Valkey: same serializer, same JEP 290 allowlist, no new types. It stamps `AUTHENTICATED_AT` and both revalidation instants as `LoginSuccessHandler` does and sets `maxInactiveInterval` to `session-timeout` (default 5 minutes). Everything downstream (`CurrentUser`, method security, cart, checkout, the verified-email rule for order mail) sees an ordinary customer. Because `email_verified` is true, every paid order mails Mailpit, which is realistic load on the outbox (C25).

**Customer only.** The role list is fixed in code. There is no parameter, header or body that mints `admin` or `support`, so a leaked token cannot reach `/api/admin/**` (`LoadtestSessionsIT`).

**Fail closed after five minutes.** No authorized client (refresh token) is stored. The first revalidation after `revalidate-after` (5 minutes) finds none and ends the session, as it does for a revoked login (`aMintedSessionEndsAtTheFirstRevalidation...`). k6 therefore re-mints. It mints every session sequentially in `setup()`, honours `Retry-After`, and re-mints staggered by VU id in phases longer than 3.5 minutes (`SESSION_MAX_AGE_MS`).

**Its own security chain.** `@Order(2)` (the webhook chain is `@Order(1)`, the main chain last), `securityMatcher` a `PathPatternRequestMatcher` for `POST` on exactly `/api/loadtest/sessions`, `permitAll` (the controller authenticates the token), request cache off, CSRF off. CSRF is off on this route only: no cookie is read to authorise it, the credential is a custom header that a cross-site page cannot set, and the route creates a session rather than acting inside one. CSRF stays enforced on every request made with the minted session (`csrfIsStillEnforcedOnTheMintedSession`: `POST /api/checkout` without the CSRF header is 403, and a `PUT /api/cart/lines/{slug}` with it is 200). A GET, or a trailing-slash path, does not match the chain and is not minted (`onlyAnExactPostMints`).

**Token handling.** `SHOP_LOADTEST_TOKEN` is generated by `make secrets` into `.cache/secrets/shop.env` and reaches the API as Secret `shop-loadtest` (a new `SECRET_KEYS` entry; a `shop.dev/shop-loadtest-hash` annotation rolls the API when it changes). `LoadtestProperties` rejects a null, blank (whitespace only) or shorter-than-32-character token at startup, measured after `strip()`, by a custom `@AssertTrue` that never echoes the value, and its `toString` prints `token=<redacted>`. The controller hashes both sides with SHA-256 and compares with `MessageDigest.isEqual`, so the comparison takes constant time whatever the length. A missing or wrong token gives 401 Problem Details and one WARN line that names no header value. The Makefile reads the token into the recipe's shell and hands it to k6 as an environment variable by name; it is never on a command line or echoed, and k6 receives no other secret.

**A rate limit and a bound on Valkey.** `MintLimiter` is a per-pod fixed one-second window (`max-mints-per-second`, default 10, `Clock`-driven, no dependency); beyond it the answer is 429 with `Retry-After: 1`. The bound assumes 5 pods: the HPA's `maxReplicas` is 4 and a rollout with `maxSurge: 1` adds one. Five pods mint at most 50 sessions a second, so 5 minutes of non-stop minting is at most 15 000 sessions. One minted session measured 2 952 bytes in Valkey (keys, hash fields and values; Valkey's per-key overhead adds an estimated 20 to 30%), so the worst case is about 44 MB raw, about 55 MB with overhead, inside Valkey's 96 MB (`volatile-lru`, sessions carry a TTL). `LoadtestSessionsIT` asserts one session stays under 4 000 bytes, so the assertion fails well before the arithmetic does. The controller also invalidates any session that arrives with the request and always issues a new id, so a minted request cannot fix a session id (C14, `mintingWithAnExistingSessionIssuesANewId...`).

**Profile-leak guards.** The profile can only be on where someone put it there, and each layer checks:

- No `spring.profiles.group` includes `loadtest` and the Dockerfile sets no profile. Only `deploy/k8s/components/loadtest` sets `SPRING_PROFILES_ACTIVE=seed,loadtest`.
- `LoadtestGuard` fails startup unless `shop.auth.public-origin` has host `localhost` or `127.0.0.1`, so the profile cannot run behind a real hostname, a future cloud overlay included (`LoadtestGuardTest`).
- `make k8s-lint` runs `k8s-loadtest-guard` over every overlay whose name does not start with `loadtest` (so a later cloud overlay is covered without an edit). `make/forbid-loadtest-env.awk` scans the whole render and fails on any case-insensitive `loadtest` other than the two exact base Gateway lines (`value: /api/loadtest` and the `Shop-Loadtest-Token` header removal), on a second `value: /api/loadtest` line (the path may appear once, so another rule on it fails), on any `$(...)` dependent-variable expansion other than `$(POD_NAME)` (which could assemble the word from parts), and on `SPRING_APPLICATION_JSON`. It also fails on `\u` escapes, `${` in a `value:` line, `binaryData`, any `type: RegularExpression` path match (the real renders have none, so a regex rule such as `/api/load.est/sessions` routed to the API fails the guard; proved on a copy of the rendered `local` overlay, 2026-11-24), case-insensitive `spring.application.json` spellings and every `envFrom` (no overlay uses one). The `${` check covers `value:` lines only: the real renders carry legitimate `${...}` in Keycloak's args and realm JSON, so container `args` and ConfigMap data are not checked for it. This closes the spellings an `env:`-only scan missed: `args`, `envFrom` ConfigMaps, `$(P1)$(P2)` and the JSON variable (S2), and the encoded forms raised in round 2 (N1). The guard catches accidental enabling and the listed spellings; it is not a defence against a repo writer who hides the profile on purpose (for example in a base64 Secret). Behind it stand the 32-character token, `LoadtestGuard`'s origin check and Envoy's 404 at the front door. `make/require-notfound-rule.awk` also fails when the `shop` HTTPRoute of a guarded overlay is not in namespace `shop`, when a second HTTPRoute is named `shop`, or when no rule has `PathPrefix /api/loadtest`, no method match and the `not-found` `ExtensionRef` filter (R6, N2); it is a fast static backstop, and the proof is the `cluster-e2e` Gateway 404 test. `make compose-lint` fails if a rendered compose config (including `--profile '*'`) contains `loadtest` in any case, a `\u` escape or a `spring.application.json` spelling, or if `docker compose config` itself fails. The guards were proved with planted manifests for each spelling.
- `LoadtestAbsentIT` runs in the shared test context (profile off): there is no `LoadtestSessionController` bean, and `POST /api/loadtest/sessions` with a valid CSRF cookie and header is refused by `denyAll`, so the refusal is proven to come from authorisation, not CSRF (C21), and sets no `__Host-SESSION`.

**Why the code stays in the production image (D35).** The same image runs every overlay; a second build with the classes removed would be a different artifact from the one measured and tested. The classes are inert without the profile: no bean exists, the path falls to the main chain's deny-by-default, and the absent-profile test proves it. The residual (dormant code ships) is R59.

**Never on the front door.** The base `shop` HTTPRoute gains a `PathPrefix /api/loadtest` rule with the existing `not-found` filter (the longest prefix wins over `/api`), and its `/api` rule also removes `Shop-Loadtest-Token`, so a path variant that slipped past Envoy's matching would still reach the API without a token. The `loadtest` component adds a Gateway listener on port 8090 (NodePort 30090, JSON6902 `add` on the EnvoyProxy port list, since a strategic merge would replace the list) with an HTTPRoute that matches only `POST` `Exact /api/loadtest/sessions`. There is no host port mapping. The k6 container joins the `kind` Docker network and mints on `http://shop-control-plane:30090`. That is the only intended client, but NodePort 30090 is reachable from any container on the `kind` network and from the WSL host through the node container's IP, and the token is the only barrier there (C22, R60). `make loadtest` runs a front-door probe first (`probe-front-door.js`): with the valid token it tries the exact path, trailing slash, `%6C`, `%2F`, `//`, `/./`, upper case, `;jsessionid=x`, GET and HEAD against port 30080, and any 2xx or `__Host-SESSION` fails the run. The probe also requires that ten spellings Envoy normalises (exact, trailing slash, `%6C`, `//api`, `/api//`, `/./` forms, `;jsessionid`, `/api/loadtest`, `/api/loadtest/`) answer exactly 404 for all five methods, so removing the `not-found` rule fails it, since the `/api` rule's token strip alone would give 401 (R6). `routing.spec.ts` asserts, in `make e2e` and `make cluster-e2e`, that nine variants are not 201 and set no session cookie (true for nginx and Envoy). In `make cluster-e2e` only (`E2E_UPSTREAM` is the kind node) a second test asserts that the Gateway answers 404 with an empty body, not the API's problem+json, for the exact path, trailing slash, `%6C`, `//`, `/./` and `;jsessionid` forms, so CI pins the rule too (S5). Case variants, `%2F` and a mid-path `;` are not caught by the prefix rule and fall to the API's deny rules.

**The endpoint is only deployed for the run.** `make loadtest` and `make loadtest-cache` deploy `overlays/loadtest*` and, from an exit trap, always `deploy OVERLAY=obs` afterwards. The trap is set before the first deploy, so a failed deploy also returns to `obs`. The cleanup ignores further INT, TERM, HUP and PIPE in the shell, and runs the teardown and the closing `deploy OVERLAY=obs` in their own session (`setsid -w`, stdin from `/dev/null`, output to `teardown.log` and `restore-obs.log` in the run directory), so a terminal Ctrl-C, which signals only the foreground process group, cannot reach them, and a dead output pipe (`make loadtest 2>&1 | tee x` after Ctrl-C) or a hung-up terminal (EIO) cannot fail them. Every cleanup message is non-fatal and `s=1` is set before it is printed. `make loadtest` and `make loadtest-cache` refuse to start without `setsid` on the host; ignoring signals in the shell alone was not enough, because the Docker CLI re-enables SIGINT and forwards it to its container. Tested from a job-control shell on 2026-11-24: a first SIGINT stopped k6 (exit 130), and further SIGINTs to the process group during the cleanup and during the closing deploy did not stop it; the `loadtest` route and NodePort 30090 were removed and the smoke checks ran. Round 4 tested piped output with Ctrl-C and a pty hangup on a stand-in with the same cleanup shape (restore completed, and a forced restore failure wrote both markers), and a real `make loadtest SCENARIO=browse 2>&1 | tee` run on kind with SIGINT to the process group during browse and during the closing deploy (the restore completed, no `loadtest` route or NodePort 30090 remained). A SIGKILL, a host or WSL shutdown or a failed restore leaves the overlay deployed: no trap can handle the first two. The tools containers run with `--init` so the first Ctrl-C reaches the scripts. The credential check also runs from the cleanup, so it covers every exit: it fails the run if a file in the run directory holds `__Host-SESSION`, `XSRF-TOKEN` or `"xsrf"` (case-insensitive) followed by `=`, `"`, `:` or `%`, and prints a count only; k6 console output is not scanned. If the closing deploy fails or is killed, the run prints an error naming NodePort 30090 and the recovery command `make deploy OVERLAY=obs`, writes `RESTORE-FAILED` in the run directory and in `build/reports/loadtest/`, and exits non-zero (R4). A successful restore removes the fixed marker, and so does the manual recovery: any successful `make deploy` of a non-`loadtest*` overlay (such as `make deploy OVERLAY=obs`) removes it with a one-line notice; the run-directory marker stays as a record. `make cluster-e2e` fails while that marker exists, while HTTPRoute `loadtest` exists in namespace `shop` or while any Service exposes nodePort 30090, so a SIGKILL or shutdown mid-run is caught by the next `cluster-e2e` (R60).

## Consequences

- With the profile off, `POST /api/loadtest/sessions` answers 401, not 403: an anonymous request refused by the main chain's `denyAll` goes through the entry point, while a CSRF failure would be 403. `LoadtestAbsentIT` sends a valid CSRF pair and asserts 401, which proves the refusal is authorisation (C31).
- k6 summaries hold no session values: `handleSummary` drops `setup_data` (which carried every minted cookie and XSRF token), and `make loadtest` and `loadtest-cache` fail from the cleanup (every exit) if any file under the run directory matches `__Host-SESSION`, `XSRF-TOKEN` or an `"xsrf"` key followed by `=`, `"`, `:` or `%`, case-insensitive. Only the count is printed (S1).
- Results exclude Keycloak: the login flow, token refresh and realm are not exercised, and the summaries say so. Mint requests carry no `load:shop` tag, so thresholds on latency and failures ignore them.
- Order mail for minted users goes to Mailpit (C25); `@loadtest.invalid` is not a real domain, so nothing leaves the cluster.
- Minted sessions are customer sessions with a fake verified email. Orders, carts and idempotency keys they create stay in the kind database until `make cluster-down` (products are deactivated, not deleted, by the exit trap).
- While `overlays/loadtest*` is deployed, anyone holding the token on the `kind` network can mint customer sessions. The window is the length of a run; the token is per checkout, mode 600, git-ignored (R16, R60).
- Every `make deploy` creates Secret `shop-loadtest` in the cluster (the apply step is shared), but no pod references it unless the `loadtest` component is in the overlay.
- A future cloud overlay is protected by the origin guard even if someone adds the profile by mistake; a lint guard for that overlay belongs with slice 6.

## Deviations from the brief

- The summary files are `<scenario>-summary.json` and `.md`, not bare `summary.json` (`loadtest/README.md`).
- Rate limiting of the front door and the gateway's body limits are not part of this slice (D38). The mint limiter is per pod and was the only limiter in the cluster until slice 5c, which added the per-IP and per-account limits of ADR 0013; the runs in this ADR's measurements were taken without them.

## Slice 5c addition: limits in load-test overlays

Status: accepted (slice 5c, 2026-11-25). Every `overlays/loadtest*` render (through the `loadtest` component) sets `SHOP_RATE_LIMIT_SCALE=1000` on the API and raises every Envoy per-IP rule to 100 000 per unit by a JSON6902 patch, because all k6 traffic shares one source address and virtual users check out faster than a person (ADR 0013, D44). The limiter code still runs, so its Valkey round trip is in the numbers. `make k8s-lint` runs `k8s-rate-limit-guard`: it fails if a `local` or `obs` render differs from base in any `BackendTrafficPolicy` or `ClientTrafficPolicy` (limits, units, selectors, body buffer, overrides) or carries an API rate-limit setting in any spelling (`SHOP_RATE_LIMIT_*`, `shop.rate-limit`), or if a `loadtest` render has any Envoy rule below 100 000. The guard reads rendered manifests, so it cannot see a limit changed outside them (ADR 0013), and k6 fails a run on any 429 outside `setup()` (counter `rate_limited`). Minted sessions are limited per account like login sessions: a virtual user cannot hit a limit at the load test's rates, which the scale and the 429 threshold prove. The mint limiter stays per pod (R61). Residual: the real limits are untested under load (R70).
