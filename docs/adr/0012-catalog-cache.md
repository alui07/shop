# ADR 0012: Catalog cache

Status: accepted (slice 5b, 2026-11-24). Checked against the implemented code. Measured results are in `docs/performance.md`.

## Context

Every anonymous page view runs catalog queries: categories, a product list with a count, a product page. The catalog changes only through admin writes, so almost every read repeats an earlier one. With two to four API replicas and a Hikari pool of 15 each, the database is the shared resource. D34 adds a short-lived cache and slice 5b measures it, cache off against cache on, rather than assuming it helps.

## Decisions

**Caffeine in the API process, not Valkey.** A hit costs a hash lookup, with no network hop and no serialisation. Valkey is already the session store with a 96 MB budget and is a hard dependency only for signed-in users, never for startup; routing catalog reads through it would make the public catalog depend on it too (ADR 0006: the public catalog works with Valkey down). Settings in `application.yaml`: `spring.cache.type=caffeine`, caches `categories`, `product`, `productPage`, `maximumSize=2000,expireAfterWrite=30s,recordStats` (the stats feed Micrometer's `cache.gets`). The responses are immutable records, so sharing them between requests is safe.

**What is cached.** `@Cacheable` on `CatalogService.categories()`, `product(slug)` and `search(...)`. The search key is `(categorySlug, sort, page, size)`, and the entry is made only when `text` is blank: free-text search has an unbounded key space, an easy way to churn the cache, and a low hit rate. A product-not-found exception is never cached. Stock does not appear in catalog responses, so stock writes do not invalidate anything; checkout recomputes prices from the database, and the `price-changed` problem already covers a cart that saw a stale price.

**The cache sits outside the transaction.** `@EnableCaching(order = Ordered.HIGHEST_PRECEDENCE)` makes the cache interceptor wrap `@Transactional(REPEATABLE_READ)`, so a hit returns before a transaction (and a pooled connection) is opened. `CatalogCacheIT` asserts that a hit on a listing (`/api/products?category=office`, which goes through the `@Transactional` `search()`) leaves `hikaricp.connections.acquire` unchanged (C11). A single-product read would not prove it, because `product()` has no transaction. The same order puts caching ahead of method security: a future `@Cacheable` method on a bean with `@PreAuthorize` would return cached results without the authorisation check, so cached methods must stay on public, unsecured reads.

**Invalidation after commit, local first, then by Valkey pub/sub.** `ProductAdministration.create` and `update` call `CatalogCacheInvalidation.afterCommit()`, which registers a `TransactionSynchronization`. Its `afterCommit` clears this pod's three caches and publishes to channel `shop:catalog-changed` over the existing Redis connection factory. Every pod runs a `RedisMessageListenerContainer` subscribed to that channel and clears its local caches on any message (its own included, which is harmless). The container has `autoStartup=false`: `CatalogChangedSubscriber` starts it on `ApplicationReadyEvent`, on a daemon thread, and retries `start()` with backoff (1 s doubling to 15 s, one WARN naming only the exception class, one INFO when subscribed). Valkey is therefore not a startup dependency: a pod that starts while Valkey is down (restart, HPA scale-up, rollout) becomes ready, serves the catalog, and subscribes when Valkey returns. After the first success the container re-subscribes by itself after a dropped connection. A rollback clears nothing and publishes nothing, and a no-change update (no write) registers nothing (C3, C24). This uses `TransactionSynchronizationManager` directly, not an application event and `@TransactionalEventListener`, so Spring Modulith writes no `event_publication` row and no module API is added; `ModularityTest` stays green.

The message carries no data and its payload is never read, so whatever someone with Valkey access publishes to the channel can do nothing but clear caches (R62). Pub/sub stores nothing, so it does not compete with sessions for the 96 MB. Catalog reads never touch Valkey and readiness does not include the listener or the subscription.

**Failure is bounded by the TTL.** A failed publish (Valkey down) logs one WARN with the exception class and is swallowed; the admin write has already committed. Other pods stay stale for at most 30 s, the time to live; the same bound covers a pod that has not subscribed yet. `CatalogCacheOutageIT` proves the write still commits with Valkey stopped and the other context is stale for at most the TTL (its test TTL is 15 s, well above the 2 s publish timeout). `CatalogCacheValkeyDownAtStartIT` pauses Valkey, starts a second context (`SecondApiContext`), asserts `/api/products` answers 200, unpauses, and asserts an admin update in the main context reaches that context within 5 s. `CatalogChangedSubscriberTest` covers the retry, first-try, interrupt and off-thread cases.

**The snapshot race, and its bound.** A read that took its database snapshot before an admin commit can finish after the invalidation and put the old row into the cache. That entry lives for up to 30 s on that pod, and the same can happen on any other pod. The local clear and the broadcast narrow the window but cannot close it without tying invalidation to snapshots (versioned keys), which is more machinery than a 30 s staleness bound on a product page justifies. A stale price on screen never charges the wrong amount: checkout re-prices under `FOR SHARE` (ADR 0008). A deactivated product can still be shown, and bought only if checkout accepts it, which re-checks `active`. This is residual R63.

**The `productPage` key space is bounded only by `maximumSize`.** The key is `(categorySlug, sort, page, size)`; `category` (any value up to 100 characters), `page` (0 to 10 000) and `size` (up to 48) make it effectively unbounded for an anonymous caller, the same churn argument that excludes free text. Memory stays bounded by `maximumSize=2000` per cache, and Caffeine's admission policy limits how much one-off keys evict popular ones. Accepted; not-found products are never cached, but unknown categories and out-of-range pages are.

**Cache off without new code.** `SPRING_CACHE_TYPE=none` selects Boot's no-op cache manager: cache-off and cache-on runs use the same image and the same code path. Overlay `loadtest-nocache` sets it on top of `loadtest-pinned`.

**Why the integration tests run with the cache off.** The shared `@IntegrationTest` context sets `spring.cache.type=none` (C12). About ten ITs change `product` rows by direct SQL or truncate and reseed through `CatalogFixtures`, and a 30 s cache would make them read stale rows or depend on timing. Only `CatalogCacheIT` (own context, `caffeine`) exercises the cache. It proves, in order: a direct `UPDATE` is not visible within the TTL (so `@Cacheable` applies to the package-private proxied methods); an admin update and create are visible right after commit; a rolled-back update clears nothing and publishes nothing; a text search and an unknown product are never cached; a hit on a listing does not touch the pool; `cache.gets` reports hits and misses; and an admin update in one application context is visible in a second context on the same Valkey container within 1 s (`SecondApiContext`, the "second pod"). The 100% line and branch gate has no exclusion.

**Measurement design.** `make loadtest-cache` alternates `loadtest-nocache` and `loadtest-pinned` (HPA min = max = 2, so both modes have the same replica count) for three rounds each, off then on. Each run starts with a separate 30 s warm-up k6 run (`CACHE_WARMUP`, reports in `<run>/warmup`, not gating), then snapshots `pg_stat_database` around the measured run only (transactions per request), saves `kubectl top pods`, and the first round records `EXPLAIN (ANALYZE, BUFFERS)` for each catalog sort (`explain-catalog.txt`, referenced from ADR 0003). Medians go in `docs/performance.md`.

## Consequences

- Public reads of the three cached catalog calls can be up to 30 s old on any pod after an admin write that missed the broadcast or lost the snapshot race (R63). The web admin pages read through `ProductAdministration`, which is not cached, so an admin sees their own change at once.
- `cluster-e2e` runs two API pods, so `admin-writes.spec.ts` can read from the pod that did not write. Its reads after an admin write poll with a reload for up to 5 s: that covers pub/sub delivery, not the TTL, which a missed broadcast would need.
- Heap cost is bounded: at most 2 000 entries per cache of small records.
- Result (`docs/performance.md`, three runs per mode, 30 it/s browse on two pods): database transactions per request fell from 1.44 to 0.34 and p95 from 3.76 to 3.28 ms (medians).

## Deviations from the brief

- None in semantics. `CatalogCaches` holds the cache names as constants; the names and sizes still come from `application.yaml`.
